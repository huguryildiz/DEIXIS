## Why

After B1 a review can be described and stored but not started: there is no run, no route, no model call. B2 makes a review run: the owner previews what will be sent, starts it with a chosen model, the worker sends the frozen snapshot in groups, findings are stored apart from the main data, and the owner can read the review and record a decision per finding. It also gives the one path by which an accepted finding reaches report text (the existing human edit, checked against its dependencies in the same transaction). No real model is called (B4) and no screen is built (B3).

14. **Content-bound idempotency** (section 15 item 13). The request hash is SHA-256 of canonical JSON over the route name, research id, target kind and id, and the request content (start: focus, owner note, connection, model, effort, submitted `snapshot_sha256` and preview fingerprint; tests: an identical replay, and a replay that changes only `snapshot_sha256`, which is 409 `idempotency_key_reused`; decision: finding id, decision, reason, expected ordinal; apply: finding id, text, link ids, note, expected version, dependency fingerprint). 15. **Apply: the only path from a finding to report text** (section 15 item 1, design 5.2 guard 4). `POST .../findings/{finding_id}/apply` body `{text, link_ids, note, expected_version, dependency_fingerprint}`, header `Idempotency-Key` required. Only for a finding whose target is a report claim (else 422 `not_applicable`). `dependency_fingerprint(reader, content, claim_ref)` in `run.py` (read-only, through `ReviewReader`) hashes the **live** state the editor was opened on: the report id, `report_version` and status; the claim's live current revision id and `version`; its effective citation link ids; the research's `selection_revision` and included source-version set; and every dependency of **all original citations** of the claim (the editor may restore any of them, `report/store.py:277–285`), not only the effective ones: for each cited cell its id and live `current_revision_id` (as B1's markers, `review/stale.py:37–38`, `reader.py:125–128`), and for each passage cited directly or through a cell's evidence the passage id, text digest, asset id and hash, current extraction id and evidence status (the tokens B1's manifest compares). The read route returns it per report-claim finding. The apply route runs **one transaction** opened in `api/app.py`, in exactly this order: (1) the finding belongs to the review and the research, and targets a report claim; (2) the command key is looked up (the decision row's `idempotency_key`): a row with the same request hash returns the stored decision and its revision and writes nothing; a different hash is 409 `idempotency_key_reused`; (3) only for a new request: recompute the fingerprint (mismatch → 409 `dependencies_changed`); (4) `ReportStore(...).edit_claim(research_id, report_id, claim_id, text=..., restore_from=None, note=..., expected_version=..., idempotency_key="review-apply:{finding_id}:{key}", link_ids=...)` (its version check gives the existing 409; its own replay check binds the key to the content); (5) `ReviewStore(conn, reader).add_decision(finding_id, "accepted", applied_ref=revision_id, idempotency_key=..., request_hash=...)`. Both rows commit together or neither does (a test injects a failure after `edit_claim` and shows no revision and no decision). Tests: an exact replay after its own write, and after a later independent edit of the same claim, returns the stored result and writes nothing; a cell value edit (new cell revision) with unchanged passages gives `dependencies_changed`; a change in a dependency behind an original citation that is currently omitted, then restored by the submitted `link_ids`, gives `dependencies_changed`. The review package never calls `edit_claim`; only this route does. The response says whether the saved text equals the suggestion (`applied_matches_suggestion`).
