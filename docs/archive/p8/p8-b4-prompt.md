## What to build

1. **`scripts/model_behavior/run_review_cases.py`.**
   - `build_content(case, sources)`: the snapshot content dict in the shape `build_snapshot` writes for an answer or report (keys `version`, `research_id`, `target_kind`, `target_id`, `answer_id` or `report_id`, `research_title`, `scope_revision` 1, `scope` with the case question, steering null and language `en`, `report_version`, `status`, `language`, `claims` with `claim_id`, `claim_ref`, `label` for answers, `section_ref`, `ordinal`, `text`, `text_origin` `model`, `support_type`, `citations` with `link_id`, `passage_id`, `cell_id`, `anchor_text`, `anchor_match`; `sections` with `record_id` and their `claims`; `cells` with `source_version_id`, `column_name`, `reading_depth`; `columns`; `sources` with `reading_depth` and `access_level`; `passages` in the `_shown_passage` shape (`reading_depth` `abstract` for abstracts else `selected_sections`, `abstract_origin` `synthetic_fixture` for abstracts, `text_source` `text_layer` for pages). Deterministic synthetic IDs with a `SYNB4` prefix that match the contract patterns.
   - `plan_case(case, content, package, adapter_enforces_schema)`: `plan_groups` with the case's focus and note, `flow.CAPABILITIES`, the model triple, `max_request_chars=REVIEW_BUDGET_TOKENS * 4`.
   - Per group, a payload from `review_step_input` with `budget=review_budget(len(groups))`, the requested connection and model, one `stp_` ID per group kept across its attempts and a new `sti_` ID per attempt (as `flow.py:4930` and `:5322` do), and `contracts.check_step_input(payload)` empty (refuse to send otherwise).
   - **Send-time size check.** After building each complete first or repair request, compute its size with the production `workflow/review/run.py::request_chars` exactly as `_model_step` does with `max_request_chars=REVIEW_BUDGET_TOKENS * 4` (`flow.py:5358` to `:5377`); an oversized request is not sent and is recorded with the production reason (`message_too_large` or `repair_message_too_large`), and the group is not reviewed.
   - **Health gate.** Before the first send the runner calls the adapter's `health(refresh=True)`, records it, and stops with reason `connection_not_ready` and zero sends when `ready` is false (`flow.py:5235` to `:5237`).
   - One send per attempt through the production adapter, then the same sequence `_model_step` uses: isolation/tool-item check, model identity (`resolved == requested` or `requested_model_verified`), handle resolution, normalisation, validation. On an invalid output, exactly one repair built with `prompt.repair_message` and `contracts.issues_with_handles` as `_model_step` does, on a newly built payload if `_model_step` builds one. No rate-limit resend (a rate, quota or capacity limit stops the run). After a valid output, `resolve_finding` for every finding, supported point and context limit; a `ValueError` there is recorded per item and makes that group, and so the case, invalid (reason `resolution_error`).
   - Record per attempt: case, group index and count, attempt (`first` or `repair`), requested connection, model and effort, resolved model, `requested_model_verified`, status, error and error kind, tool item types, token usage, message characters, the payload, raw output, validation ok, issue codes with paths, and the resolved items. Record per case: the plan (groups, `not_reviewed`), the screens of the case (below), a judgement template, and `valid` with a reason when not valid (see "Validity and stop rules" in the expectations file).
   - Screens, exactly as named in the case file and the expectations file. RB01 `screen_no_negative_finding_on_c2` (no `unsupported`, `partially_supported` or `overstated` finding with target claim c2), `screen_no_peer_review_assertion_phrase` (the case-insensitive strings "approved by peer review" and "peer-reviewed" absent from every prose field of the output: `rationale`, `possible_impact`, `suggested_fix`, `uncertainty`, context-limit text and `notes`); RB02 `screen_findings_empty`, `screen_fewer_than_three_findings`; RB03 `screen_no_supported_point_c1`, `screen_no_supported_point_c2`, `screen_c1_addressed` (c1 is the target of at least one finding or context limit); RB04 `screen_first_attempt_anchors_located` (from the anchor audit below: every first-attempt entry the audit could check is located exactly or after normalization; `null` when the audit could check none; computed from the first attempt even when the case ends invalid); RB05 `screen_findings_empty`; RB06 `screen_plan_two_or_more_groups`, `screen_iv1_not_reviewed`, `screen_no_supported_point_iv2`, `screen_iv2_addressed` (IV.2 is the target of at least one context limit or finding). Each screen is `true`, `false` or `null` when the output it needs is missing. Screens are heuristics; the results JSON says so.
   - Judgement template: for PE1 and PE2, one row per planted claim (`claim_ref`, `plant.type`, `found_if`, the findings on that claim with handle, kind and rationale, `found: null`); for every case, one row per finding and per supported point (`case`, `group`, `handle` or index, `target_ref`, `kind`, `planted` true/false/null, `judgement: null`, `reason: null`). Claude fills these by hand in the results file; the runner never sets them.
   - **Anchor audit.** Production validation can drop anchor diagnostics when a sibling item is malformed (`contracts.py:799` to `:803`), so the runner audits every evidence entry itself: for each attempt whose output parses (after handle resolution and normalisation, as validation sees it), each `evidence` entry of every finding and supported point is checked with the production `contracts.locate_anchor` against the text of that call's passage; the entry is `located` (`exact` or `normalized`), `not_located` (no match or another match kind, with the kind), or `unchecked` with a reason (`passage_not_in_call`, `missing_field`, `unparsable_output`). Counters per attempt kind (first, repair), over every attempt whose output parsed, including attempts of invalid cases. Validation issue codes are recorded beside the audit, never instead of it.
   - Summary: the PE1 and PE2 planted and unplanted claim counts (nine and fifteen before validity exclusions) and which of them sit in valid groups; behavior-case findings are listed per case and never pooled with PE1 and PE2.
   - `call_shape_notes` in the results JSON naming every difference from production: no durable send reservation or step rows, no 24-hour review deadline, no pause, resume or crash recovery, no rate-limit resend, the runner-only before-send retry, synthetic snapshot content instead of a database snapshot.
   - **Send cap.** `--max-sends` (default 20; the runner exits 2 before creating an adapter unless `1 <= max_sends <= 20`) counts every adapter `run_step` call, including repairs and failed sends; before each send the runner checks the counter; at the cap it stops and records every unsent group and case with reason `send_cap`.
   - **Stop rules.** As `_stop_for_run` in `run_candidate_cases.py`: isolation violation, tool items, rate/quota/capacity limit, an unverified model mismatch, plus the send cap. A connection error before the send (`delivery_class == "before_send"`) may be retried once for that attempt and counts against the cap.
   - **Order.** Cases run in the order RB01, RB02, RB03, RB04, RB05, PE2, PE1, RB06 unless `--cases` selects a subset (the order stays the same).
   - **Freeze check.** `--expect-sha256 CASES_SHA,EXPECTATIONS_SHA` is required for any real send: the runner computes the sha256 of `tests/model_behavior/review_cases.json` and `docs/product/p8-review-expectations.md` and exits 2 before creating an adapter if either differs.    - **Options.** `--connection claude|codex` (default `claude`), `--model` (required), `--effort` (default `medium`), `--cases`, `--only-build`, `--out-dir` (default `.local/p8-b4-<UTC date>`), `--codex-home` (required for `codex`; the runner exits 2 when it is missing, or when the resolved path lies inside `~/Library/Application Support/DEIXIS` or inside `load_settings().data_dir` computed without `DEIXIS_DATA_DIR`, unless `--allow-live-codex-home` is also given; B4 never passes that flag), `--max-sends`, `--expect-sha256`.
