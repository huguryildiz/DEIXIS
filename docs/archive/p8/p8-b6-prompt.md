## Why

B6 adds the opt-in interval: while DEIXIS runs, a once-a-minute tick queues a check when a watch is due, and after DEIXIS was closed or asleep across due times it says so and makes one bounded catch-up check on the next start. ## Decisions taken where the design is open (use these; never ask)

Items marked **(owner-level)** were settled by the orchestrator (Claude Opus 5.5) and confirmed by the plan reviewer (gpt-6.1-sol medium, round 1: A–F confirmed, A as an explicit amendment, B with the corrected wording of decision 8); the decision text records who agreed.

0. **Execution rule (binding; D186's round-1 high was this defect).** Every watch store call and every `tick()` runs synchronously on the application's event-loop thread, where the worker shares the one SQLite connection. The new route is `async def` like the nine B5 routes; nothing in this batch uses `run_in_executor`, `asyncio.to_thread`, a thread, or a plain `def` route; there is no `await` inside a transaction. `watch/store.py::transaction` joins an open transaction and cannot tell nesting from another thread's transaction, so this rule is what keeps it correct. Threaded `TestClient` tests call `tick()` through `client.portal.call(...)`, as `tests/watch_helpers.py::turn` does for `_turn`. A test asserts the route is a coroutine function and that `tick()` executes on the loop thread (B5's `test_create_check_and_dismiss_store_calls_use_the_app_event_loop_thread` pattern).
1. **Module split.** New `backend/deixis/workflow/watch/scheduler.py` with `WatchScheduler(store, wake, clock=utc_now)`: a synchronous `tick() -> dict` (one pass; returns what it recorded, queued and skipped, with reasons, for tests and logs) and an async `run_forever(stop_event)` that calls `tick()` at once and then every `WATCH_TICK_SECONDS`, logs an exception from a tick once per exception type (as `Worker.run_forever` does) and continues, and ends only on the stop event or cancellation. Pure due-time arithmetic goes into `watch/check.py` (no `.execute`). Queueing stays in `watch/store.py` (`_queue` gains parameters; it does not move).
   **Two clock domains.** The scheduler's injected `clock()` returns an aware UTC `datetime`; one reading per tick decides due times, gaps, the queue time, `period_start`, `requested_to`, the check's `created_at` and the run's `deadline_at`. The send gate keeps its own clock (`Callbacks.clock`, which defaults to `deixis.storage.db.now` imported into `watch/run.py`; `flow.py` passes no clock), and runs, steps and events keep `db.now()`. Ordinary scheduler tests therefore use fake times at or after the real `now` so the 1,800-second send deadline stays usable; the tests that need an expired deadline or a resume across it patch `deixis.workflow.watch.run.now` (the existing seam) with `monkeypatch` and show that neither a restart nor a resume renews usage or the deadline. The decision states both domains.
2. **Constants** (in `check.py`, policy, unmeasured): `WATCH_TICK_SECONDS = 60`; `WATCH_GAP_SECONDS = 300` (two consecutive ticks further apart than this, by wall clock, mean the scheduler did not run in between: a sleep, a suspended process or a forward clock jump; it shows an interruption of scheduling, not that the computer was closed); `WATCH_CATCH_UP_RESEARCHES = 3`. Interval lengths are `timedelta(days=interval_days)` in UTC.

4. **Interval watches on create and rebind** (design Q6, section 15 item 12: cadence and catch-up are two explicit settings). `Create` gains `interval_days: Literal[1, 7, 30] | None = None` and `catch_up: bool | None = None` (strict booleans). `mode='manual'` requires both absent or null; `mode='interval'` requires both given (422 `schedule_invalid` otherwise, no write). `interval_not_built` is removed. An interval watch is created with its first (baseline) check queued in the same transaction as today and `next_due_at = queue time + interval`. Rebind copies `mode`, `interval_days` and `catch_up` and sets the new watch's `next_due_at` the same way. The request hash already binds the whole body.
5. **Changing the schedule of a watch** (section 15 item 9: "a change of cadence, budget or catch-up keeps the continuation"). New `async def` route `POST /api/researches/{rid}/watches/{wid}/schedule` with body `{mode, interval_days, catch_up, expected_schedule_version}` (`extra="forbid"`, the coherence rule of decision 4, `Idempotency-Key` header). In one `BEGIN IMMEDIATE`: exact replay first (through `watch_schedule_changes.request_key`, added to `_replay`), then 409 `watch_disabled`, 409 `schedule_changed` when `expected_schedule_version` differs; then update `mode`, `interval_days`, `catch_up`, `schedule_version + 1` and `next_due_at` (manual: NULL; interval: `now + interval`, a fresh cadence from the change, never a due time in the past) and insert the `watch_schedule_changes` row. **It does not touch `state_version`, `baseline_json` or any check**, so a running or paused check still completes (`complete_check` compares `state_version` only), and an already queued check's `config_json` stays byte-identical (test both). The response is the watch view. No other route changes the schedule.
6. **Due times and the one-period rule.** For an enabled interval watch with `next_due_at = d0` and interval `I`, the due times passed at tick time `t` are `d0, d0+I, ...` up to `t` (none when `t < d0`). A scheduled or catch-up check is queued in one transaction (decision 9) that moves `next_due_at` to `queue time + I` whatever the check's later outcome (design section 7: a failed check does not retry sooner). A manual "Check now" on an interval watch also sets `next_due_at = queue time + I` in its queue transaction. `period_start` for a scheduled check is the stored `next_due_at` it serves, for a catch-up the last missed due time; both stay below any later check's `period_start`, because that one is at least the new `next_due_at`. A due time the scheduler could not serve because a run was active is not "missed": it stays due and is served later as `scheduled` (design R10), with `due_times_passed` in the schedule block.
7. **Openings, gaps and catch-up (owner-level; A, C, E, F confirmed).** An **opening** is the scheduler's first tick in this process, or a tick more than `WATCH_GAP_SECONDS` after the previous one by wall clock (a wake from sleep or a forward clock jump). A due time is **missed** when it lies in the gap: before the first tick of this process, or after the previous tick and up to this one.
   - **Accounting is one transaction per opening.** At an opening the scheduler computes, for every enabled interval watch of a visible research with at least one missed due time, its gap row, and writes **all gap rows and all `next_due_at` moves of that opening in one `BEGIN IMMEDIATE`**. The opening id (`new_id("wop")`), the reference times (`observed_until`, `noticed_at`) and the **detected episodes** (per watch: watch id, `schedule_version`, `next_due_at`, first and last missed due time, `missed_periods`) are fixed when the opening is first seen and kept in memory; the allocation (outcomes and ranks) is computed inside each accounting attempt; the scheduler's previous-tick marker and its "opening done" state advance only after that transaction commits. If it fails, nothing of it is stored, and the next tick repeats the same opening with the same id and the same reference times and re-reads each detected episode's watch inside the new transaction. An episode whose watch is still enabled, interval, at the same `schedule_version` and the same `next_due_at` takes part in the allocation, which is **recomputed among those episodes only**; an episode whose watch changed between the attempts (a schedule change, a Check now, a disable or a rebind) is still recorded, from the stored episode, with outcome `changed_before_record` and an `outcome_reason` (`schedule_changed`, `next_due_changed`, `disabled`), its watch row is not written, and it creates no pending choice: the missed time stays in the history and no live schedule is overwritten. Each gap row records the `schedule_version` of its episode. Every row is written once (`UNIQUE(watch_id, opening_id)`). Test: a failure injected after the first gap row inside the transaction, then, before the retry, a schedule change on one watch, a Check now on a second, a disable of a third and a rebind of a fourth: the retry writes one row per detected episode under the same opening id (the four with `changed_before_record` and the reason), leaves the four watches as their commands left them, creates no pending choice for them, and gives the unchanged episodes their outcomes.
   - **Outcomes**, decided in this order: `not_eligible` with `outcome_reason` `watch_follows_old_scope` or `check_paused` when the watch follows an old scope (section 14 item 2) or has a paused or `outcome_unknown` check (section 15 item 6): it takes no research slot and its `next_due_at` stays, so it is served as `scheduled` after the owner rebinds, resumes or cancels; `catch_up_off` when its `catch_up` is 0: no check, `next_due_at` moves to the first due time after the tick on the watch's own grid (`d0 + k·I > t`); the remaining watches are ranked by `first_missed_due`, then `research_id`, then kind (`protocol_queries` before `citing_works`), then watch id; the first watch of each research is chosen and that research's other watch gets `one_per_research`; of the chosen ones the first `WATCH_CATCH_UP_RESEARCHES` researches get `catch_up_chosen` and the rest `opening_cap`. `one_per_research` and `opening_cap` move `next_due_at` like `catch_up_off`. The decision states plainly that "one combined check per research" (section 15 item 12) is implemented as one catch-up check of one watch per research per opening, an explicit amendment: the research's other watch kind is not checked at that opening, and nothing calls this combined coverage.
   - A `catch_up_chosen` watch keeps its `next_due_at` until its catch-up check is queued (decision 9 moves it then). Each pending choice keeps in memory the gap id, the watch's `schedule_version` and the `next_due_at` seen at accounting. If the process ends before it is queued, the next opening finds the same missed due times and records them again under a new opening; the earlier row stays, and the read model says no catch-up check was queued for it.
   - The catch-up check has `trigger='catch_up'`, `period_start = last_missed_due`, `missed_periods` from the gap row and the schedule block of decision 9. It uses the same caps and budget as any check (design: "the same page budget"), so its coverage can be `partial` and says so.
   - A backwards clock jump is not an opening: a later `next_due_at` simply waits (design section 7), and the read model shows `next_due_at`.
8. **Who goes first (owner-level, B confirmed; a stated departure from design section 7's per-research rule).** The scheduler queues a scheduled or catch-up check **only when no run of any research is queued, running or pause-requested**, and at most one per tick, so **at most one automatic check is outstanding at any time**. Work the owner submits after that check was queued waits behind it; the queue never holds two automatic checks, and an automatic check is never queued while owner work is waiting. The 1,800-second limit is a send deadline (`watch/run.py:51`): it stops new requests, not an in-flight request, a page wait or completion, so it is not a completion-time bound. A library that is often busy can delay a due check for many ticks (R10 widened to the whole library); the decision says so. Within a tick: pending catch-up choices in rank order first, then due scheduled watches ranked by `next_due_at`, then watch id; a choice that is **stale** (decision 9 step 2: schedule revision or due time changed, disabled, not interval, old scope, research gone) is dropped and the next candidate is tried in the same tick; a choice that is only **blocked for now** (a run active anywhere, or `check_paused`) stays pending with its gap id and is tried again at later ticks, so an opening during owner work still serves its catch-ups, as `trigger='catch_up'` with the original gap id, once the library is idle. "Check now" is unchanged (the owner's own request).
9. **Queueing a scheduled or catch-up check is one transaction** (design "Atomic queueing"). `WatchStore.queue_scheduled(watch_id, trigger, period_start, missed_periods, schedule, expected_schedule_version, expected_next_due_at, ts)` in one `BEGIN IMMEDIATE`, in this order:
   1. **Period replay first**: a stored check with the same `(watch_id, period_start)` is returned as it is, with its check and run ids, before any other test, and nothing changes (design: "a replay of the same period returns the stored check"; otherwise `create_run` would return the stored run by its idempotency key and the check insert would abort).
   2. Admission, each a skip reason with nothing written, returned as either `stale` or `blocked` (decision 8 keeps blocked choices): stale are watch disabled; not `mode='interval'`; `schedule_version` or `next_due_at` differs from what the caller saw (a schedule change, a Check now, a disable or a rebind since the choice made it stale); follows an old scope; research trashed or unknown. Blocked are: the global idle rule of decision 8 no longer holds; `_idle(research_id, watch)` (`check_paused`), so a watch with a `paused` or `outcome_unknown` check gets no new check and **its paused check is never cancelled or superseded** (section 15 item 6 replaces design section 7's superseding sentence; the design row's test "a paused scheduled check superseded by the next one" is written the other way round).
   3. `create_run(research_id, "watch_check", budget, f"watch:{watch_id}:{period_start}", target)`, the `watch_checks` row with the trigger, `period_start`, `missed_periods`, `request_key` and `request_hash` NULL, and `next_due_at = ts + I`.
   **Frozen schedule block.** The check's `config_json.schedule` is complete and frozen: `{"trigger", "mode", "interval_days", "catch_up", "schedule_version", "due_at" (the served `next_due_at`), "due_times_passed", "opening_id", "gap_id", "first_missed_due", "last_missed_due", "missed_periods", "tick_seconds", "gap_seconds", "catch_up_researches"}` (the gap fields null for a scheduled check). `_queue` is generalized for this (queue time `ts`, trigger, period, missed periods, schedule block); manual commands keep their behavior, and a manual check on an interval watch records `schedule` with `trigger: "manual"`. After a commit the scheduler calls `wake()`.
10. **Writes on a tick.** Opening accounting (decision 7) may write gap rows and `next_due_at` moves; a queue attempt writes only when it queues; everything else writes nothing. Skip reasons in the tick result, none of them a write: research trashed or unknown; watch disabled; manual watch (no scheduler for manual watches, design section 7); not due; global run active; `check_paused`; `watch_follows_old_scope`; stale choice. A tick that has no opening and queues nothing writes nothing at all (no row, no event, no `updated_at`), which keeps the authorizer tests of other batches that start a real worker valid.
11. **Lifespan hook** (`api/app.py`, a few lines). The scheduler runs **only in the process that owns the worker** (design section 7): when `start_worker` and the local `owner` are true it starts beside `worker.run_forever()`; in `take_over_when_released` it starts after the takeover's recovery, legacy cancellation, reconciliation and `app.state.owner = True` (`app.py:708–712`). Order at start: `recover()` and `cancel_legacy_discovery()` first, then the first tick, so a check left `running` by a crash is already `paused` (`backend_restarted`) when the first tick looks at it. On shutdown the scheduler is stopped and awaited before `worker.stop()` and `worker.release()`. `app.state.watch_scheduler` holds it; with `start_worker=False` none exists. A test shows each case on a temp library with a fake clock: the owner starts it (its first tick ran), a non-owner does not start it until takeover, and shutdown stops it.
12. **Read models** (`watch/view.py`). `watch_view` adds `catch_up` (bool or null), `schedule_version`, `next_due_at`, `waiting_reason` (`check_paused`, `watch_follows_old_scope` or null; not "busy", which changes every second), the latest five gaps (newest first: dates, `missed_periods`, outcome, `outcome_reason`, and the catch-up check id queued for it, found through `config_json.schedule.gap_id`, else `catch_up_queued: false`), and the standing line "DEIXIS checks only while it is running.". `check_view` adds `schedule` from the config and, for a catch-up, `gap = {"from": first_missed_due, "to": noticed_at, "missed_periods"}` with the sentence "Not checked between {from} and {to}." built from stored values. No wording says "up to date" or that nothing happened while DEIXIS was closed.
13. **Tests with a fake clock** (`tests/test_watch_scheduler.py`; `WatchScheduler.tick()` with a fake clock on the B5 helpers' temp library and mocked provider transport, called through `client.portal.call`, and `worker._turn()` for runs). Each is a named test:
    a. due versus not due (one second before and at `next_due_at`); a manual watch is never queued;
    b. one period gives one check: queue a scheduled check, **complete it**, then tick again inside the same period (and call `queue_scheduled` again for that period): no second check; the replay returns the original check and run ids;
    c. the queue transaction is atomic: a failure injected after `create_run` inside `queue_scheduled` leaves no run, no check and `next_due_at` unchanged;
    d. a crash after the queue commit and before the worker picks the run: a new `WatchScheduler` (a new process, a new opening) and the worker run that check once; no second catch-up from the old due time (`next_due_at` already moved);
