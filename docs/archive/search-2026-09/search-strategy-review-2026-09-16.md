# Search strategy revision — technical review

**Status:** proposal; no search behavior has changed. **Date:** 2026-09-16.
This is a design review of discovery, not an executed search or a claim of improved recall.

## What the active code establishes

- The literature model proposes concepts, synonyms and provider-specific query strings in `SearchPlan.v1`. The backend validates the selected provider, request budget and query syntax, then executes the accepted strings in order. It does not revise a plan in response to search results (`contracts/research/search-plan.schema.json`, `backend/deixis/domain/contracts.py`, `backend/deixis/workflow/flow.py`).
- OpenAlex requests search titles and abstracts. Current OpenAlex shape checks reject more than two required parts or five Boolean operators. Standard and detailed effort request up to 25 results per query; quick requests up to 10 (`backend/deixis/providers/openalex.py`, `backend/deixis/domain/rules.py`).
- The screenshot's four counts, `7 / 295`, `7 / 33`, `7 / 45` and `7 / 49`, are the historical run documented in D9. Its seven-per-query limit and the later change to 25 are recorded there. Three screenshot queries fail the active shape check. The screenshot is therefore not evidence that the current validator accepts those queries (`docs/decisions.md`, D9 and D11).
- `search_runs` already stores the requested page limit, returned count, provider total, query, provider, status and request description. The API view exposes `page_limit`, but the timeline shows returned/provider total without it (`backend/deixis/workflow/views.py`, `apps/web/src/Transcript.tsx`). Provider total is a match count, not inspected literature.
- Candidate records retain one best `search_run_id` per research and source version. When a work appears in several queries, that field does not preserve every query-to-work hit. The raw provider responses remain stored, but exact per-query unique or exclusive contribution would need a reliable hit mapping before it is shown as a product metric (`backend/deixis/workflow/store.py`).
- Embedding similarity currently ranks records or passages already obtained. It cannot discover a paper excluded by the provider's top-K cut (`backend/deixis/workflow/flow.py`, D27 and D30).

## Revised implementation sequence

1. **Establish the baseline.** On an isolated application-data copy, run the current pipeline on the same question, provider access, model and effort, and stored budgets. Freeze the current code revision, provider request strings, requested K, returned records and a user-reviewed known-paper set. The D9 screenshot itself needs no rerun to explain its seven-result limit. Compare found, unique, screened, included, given and cited separately.
2. **Make the current search legible.** Show `requested K / returned / provider-reported total` for each query, with status and rationale. Label the provider total as matches reported by the provider. Do not derive per-query exclusive contribution from `candidates.search_run_id`, because it keeps only one best search. This UI change must preserve the existing dirty worktree and pass desktop/narrow visual checks.
3. **Evaluate query construction before changing it.** Compare the current model-written, validated plan with focused OpenAlex queries built from the same question and fixed budget. Measure known direct and adjacent paper coverage at the *actual* K, unique works, screening workload and human-labelled relevance. Use several questions or domains; D11's one-question result cannot justify a general compiler. Keep model proposals and source decisions separate.
4. **Only if the comparison earns it, implement an OpenAlex compiler.** Define a domain-neutral facet contract and version it as `SearchPlan.v2`. Compile one essential anchor plus one optional concept family per query, with explicit alternatives within a family; do not make every optional facet mandatory. Pass the resulting literal query through the existing validator. Persist the exact submitted string, compiler version and originating plan step without altering historical v1 runs. Update method instructions, fixtures, adapters, views and tests together.
5. **Defer automatic second-pass search.** If step 3 shows a recoverable top-K gap, design a separately recorded, budgeted revision step with explicit parent query and checkpoint/replay rules. Its trigger must be evaluated against known relevant papers; zero results, overlap and provider totals alone are insufficient. Keep any semantic *discovery* connector separate from the current post-retrieval embedding score.

## Evaluation gate

Before implementing steps 4 or 5, pre-register the comparison questions, user-labelled known works and strata, provider access, model and effort, query/request budgets, actual top-K, source-version matching rules, and measures. Report per-stratum known-work coverage, human-labelled precision among retrieved works, unique contribution where a complete hit map exists, screened workload, provider failures and cost. Compare against the unchanged current pipeline under the same budget. An empty search or model agreement is not evidence of novelty, completeness or a research gap.
