## D37 — An uploaded PDF takes its title, authors and abstract from the OpenAlex record it names itself as
Status: accepted · Date: 2026-10-15 · Writer: Claude
Context: An uploaded PDF became a source whose only field was a title made from the file name. The source panel said no abstract was stored, "Copy as BibTeX" gave `@misc{Multipartynd, title = {...}}` with no authors, and the title could be wrong: the owner's file "Multiparty Entanglement Routing in Quantum Networks" is the paper "Multi-Entanglement Routing Design over Quantum Networks" (owner's screenshots, 15 Oct). Only seed PDFs were ever matched to OpenAlex (D2, D3).
Decision:
- When a research or Library upload creates a new source, `documents/upload_record.py` asks OpenAlex which work the file is, by D3's seed rule: the DOIs (and arXiv identifiers) on the first two pages first, else one meaning search with the head of page 1 (at most 1,500 characters). A work counts only when its title, four words or more, stands in the head of page 1. One change from the seed rule: a found title contained in another found title gives way to the longer one. Two works with the same title still decide nothing.
- A match replaces the file-name title and fills authors, year, venue, type, DOI, landing page, volume/issue/pages, citation count and the retraction flag on the upload's own source row, adds the record's abstract as the source's abstract, and lets an author key replace the title key (old D59). The match, its basis (`doi_title` or `title`) and the file-name title it replaced are kept in `source_versions.record_match_json` (migration 0012). No identifier mapping is written, so a search that later finds the same record keeps its own source version.
- No match, or a failed request, changes nothing and never fails the upload. The source panel's ⋯ menu offers "Find the paper's record" for an upload without a match (also for files uploaded before this decision), and its footnote says which rule matched.
Limits: The title route takes whichever record OpenAlex holds under that title. The owner's arXiv preprint was filled with the INFOCOM 2022 record (its DOI, venue and year); the file's own version label stays "uploaded file". Each new upload sends one or two OpenAlex requests carrying the DOIs or the first 1,500 characters of page 1, also in an "attached files" research. Checked live on one file (the owner's, through "Find the paper's record" on a copy of the data folder); the tests use a scripted OpenAlex and SYNTHETIC records. How often real uploads match was not measured. A seed's own matching (D3) is unchanged and does not use the containment rule.

## D36 — arXiv PDFs take their numbered equations from the authors' LaTeX source by default
Status: accepted · Date: 2026-10-15 · Writer: Claude
Context: Without Marker a PDF's display equations show as broken text layer (the owner's screenshot of a source's details panel, 15 Oct). The arXiv source route (old D104, slice 22) places the authors' numbered display equations on the page, needs no model and took a median 0.47 s per paper in its acceptance, where 40 of 40 sampled placements read right by eye. It shipped behind `DEIXIS_ARXIV_SOURCE`, off until a later measurement that never came.
Decision: `load_settings` now defaults `DEIXIS_ARXIV_SOURCE` to `auto`, so the route runs whenever Marker is neither installed nor installing (POSIX only). `off` still turns it off. The `Settings` dataclass keeps `off`, so tests that build settings by hand request no source.
Limits: Only arXiv versions whose source has `.tex` benefit, and only numbered display equations; inline math and unnumbered displays stay as text layer. Each arXiv PDF now costs one or two requests to arxiv.org (3 s apart). The route's accuracy numbers are the slice 22 ones (one library, one reader); nothing was measured again for this change.

## D34 — Direct API keys for Claude and OpenAI research steps; OpenRouter, MiMo and a generic local server
Status: accepted · Date: 2026-10-15 · Writer: Claude
Context: The owner approved a Settings redesign in which each company card offers either an account sign-in or an API key. Claude ran only through the Claude Code CLI with a Claude account, and `OPENAI_API_KEY` served only embeddings, so the key half of those two cards had nothing behind it. Two policy points were checked today on the companies' own pages. Anthropic's legal page forbids third-party apps from offering Claude.ai login or from intermediating subscription credentials, and explicitly allows an end user to sign in to the unmodified Claude Code binary with their own subscription. DEIXIS runs `claude` as published and never reads its tokens, so the Claude account path stays, and the API key is added next to it. Google's Gemini CLI FAQ forbids third-party software from harvesting or piggybacking on Gemini CLI OAuth, and recommends an API key for third-party agents and for headless mode. DEIXIS runs the official `gemini` binary and never reads its tokens (D23), but headless use is a gray area, so the Gemini account path stays and the API key is the recommended default.
Decision:
- `anthropic` (`models/anthropic_api.py`, `ANTHROPIC_API_KEY`): one Messages API request per step with no tools, no tool choice and no server-side fallback model. The step schema goes in `output_config.format` (structured outputs), so `enforces_schema` is true. The API rejects numeric bounds, string lengths, `maxItems` and `minItems` above 1; `models/schema_subset.py` removes those (and lowers `minItems` to 1) before sending, keeps patterns, and DEIXIS still validates the output against the full schema. The model list comes from `GET /v1/models`, keeping only models whose capabilities say structured outputs are supported; effort levels are offered per model from the same capabilities and sent as `output_config.effort`. A non-text content block (a tool or server-tool item) fails the step as an isolation violation; a stop reason other than `end_turn`, `refusal` included, fails it.
- `openai` (`models/openai_api.py`, `OPENAI_API_KEY`): one Responses API request per step with `store: false`, no tools, and the schema as a strict `json_schema` text format, sent unchanged (Codex already sends the same schemas to OpenAI). Any output item other than a message or reasoning fails the step as an isolation violation; a refusal or an incomplete response fails it. The model list keeps GPT-4o and later and the o-series, without audio, realtime, image, search, embedding, moderation and `latest` models. No reasoning effort was sent (D35 adds one). The embeddings use of the key is unchanged.
- For both, the answering model is reported, and a different one stops the step with `model_mismatch`. One exception, shared by both through `adapter.is_dated_snapshot`: an alias answered by its own dated snapshot (`gpt-4o` → `gpt-4o-2024-08-06`, `claude-haiku-4-5` → `claude-haiku-4-5-20251001`) counts as the requested model; the snapshot id is still what is recorded.
- `openrouter` (`https://openrouter.ai/api/v1`, `OPENROUTER_API_KEY`) and `mimo` (Xiaomi MiMo, `https://api.xiaomimimo.com/v1`, `MIMO_API_KEY`, from Xiaomi's "First API Call" page) are new `CompatConnection` entries. OpenRouter sends the schema subset as a strict `json_schema` response format with `provider.require_parameters: true`, so it routes only to providers that take every parameter sent. Its model list keeps only models whose `supported_parameters` include `structured_outputs`, sorted by id, shown with OpenRouter's model name. Its model list answers any key, so its key test reads `/key`. MiMo documents only JSON-object mode and no model list, so it uses JSON-object mode like the other compatible connections and offers `mimo-v2.6-pro` and `mimo-v2.6-flash` when the list answers 404.
- `local_server`: a keyless OpenAI-compatible connection (llama.cpp, Jan, LocalAI, vLLM) whose base URL is set with `PUT /api/connections/local_server` (`{"base_url": ...}`) and stored as the `local_server_url` setting. Only `http`/`https` on `127.0.0.1`, `localhost` or `::1`, with no credentials, query or fragment, is accepted; the address is checked again at every call, so no other host is contacted. `/api/connections` shows the address as `base_url`. No UI in this change.
- After Sol's review of af41a88: (1) Ollama and the local server use their own client with `trust_env=False` and no redirects, because the shared client honours `HTTP_PROXY`/`ALL_PROXY` and would carry a loopback request through a proxy; (2) every chat-completions connection (the compatible ones and DeepSeek) fails a step whose answer holds `tool_calls`, a legacy `function_call` or a tool-call finish reason, as an isolation violation, before the finish reason is read; (3) the OpenAI list leaves out models without strict JSON-schema output (`gpt-4o-2024-05-13`, `o1-preview`, `o1-mini`).
- The same proxy leak was open for the other requests to this computer: Ollama and LM Studio embeddings (which carry passage text), the local tool checks and Zotero's local API used the shared client. They now go through one `loopback_client()` made at startup (`app.state.local_http`, `FlowDeps.local_http`, chosen by `embeddings.client_for` and `zotero_http`); remote APIs keep the shared client and the person's proxy.
- The Claude Code connection now empties `ANTHROPIC_API_KEY` in the CLI's environment, so a key saved for the API connection never turns the account path into API billing.
- Keys: `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY` and `MIMO_API_KEY` join the managed model keys, each tested before it is kept.
Limits: Every test uses mocked transports; no request has been sent to the Anthropic, OpenAI, OpenRouter or MiMo APIs or to a real local server, so it is not shown that they accept these requests. Anthropic's schema limits (24 optional parameters, 16 union-typed parameters per request) were checked against today's step schemas (at most 9 unions, none optional), not against a live call; a pattern the API finds too complex would fail the step with HTTP 400. `MAX_TOKENS` is 16000 for a non-streamed request, thinking included, so a long report section on a high effort could stop at `max_tokens`. OpenAI reasoning efforts were not offered here; D35 adds them from a fixed table. OpenRouter providers differ in how strictly they follow a schema, and their answering-model ids were not observed. MiMo's model ids are fixed in the code and will go stale; Xiaomi says old ids are routed to newer models, which the flow will stop as a mismatch. An empty `ANTHROPIC_API_KEY` was run once on 15 Oct (Claude Code 2.1.300, a fake key in the parent environment): the CLI reported `apiKeySource: none` and answered on the signed-in account, while the same call without the override used the key and got HTTP 401; so the CLI treats an empty value as unset. Policy: Anthropic allows the user's own sign-in to the unmodified Claude Code binary and forbids third-party Claude.ai login or credential intermediation; DEIXIS stays on the allowed side by running `claude` as published and never reading its tokens. Google forbids harvesting or piggybacking on Gemini CLI OAuth and recommends API keys for third-party and headless use; DEIXIS's headless use of the official binary is a gray area, so the Gemini API key is the recommended default.

## D24 — GitHub Copilot CLI runs research steps with the account signed in to it, every Copilot tool off
Status: accepted · Date: 2026-10-14 · Writer: Claude
Context: Settings listed Copilot CLI and nine other coding CLIs as "detected only". The owner asked for them to run steps on macOS and Windows. A documentation check found only Gemini CLI and Copilot CLI with a headless mode, a way to turn tools off, a reported model and account sign-in; Gemini CLI went to another session. Qwen Code, OpenCode, Goose, Kimi, Mistral Vibe, Aider, Cline and Amp stay detected only: tools cannot be turned off, or the answering model is not reported, or neither could be confirmed.
Decision:
- `models/copilot_cli.py`, connection `copilot_cli`: one `copilot -p --output-format json` run per step, the prompt (base, developer text with the schema, message) on stdin, in its own `COPILOT_HOME` and an empty workspace in the data folder. The environment is an allowlist; `GITHUB_TOKEN`, `GH_TOKEN` and `COPILOT_GITHUB_TOKEN` are left out, so Copilot uses the signed-in account and not the GitHub Models key of D22.
- Tools: an empty `--available-tools` does not turn them off (measured: the model read a file and ran `pwd`). The only available tool is a name that does not exist (`deixis_no_tool`), and shell, write, read, url and memory are also denied; with that the same probe made no tool request. Built-in MCP servers and AGENTS.md-style instruction files are off. An MCP server configured in the DEIXIS Copilot home stops the step before Copilot starts; a tool request, a tool run or a connected MCP server in the event stream fails it as an isolation violation.
- A step completes only with an answer, no error event and the run's closing `result` event with exit code 0. A failure counts as sent once `model.call_start` or an answer was seen, and as not sent before that. The answering model is read from each `assistant.message`; a different one is kept and not verified. The model list comes from the account through Copilot's ACP mode (`initialize`, `session/new`), which sends no prompt; "auto" and models the plan has not enabled are left out.
- npm's `copilot` is a node launcher that runs the platform binary as a child with the same pipes; DEIXIS runs the binary itself (`copilot-<platform>-<arch>/copilot[.exe]`) in its own process group and does not run a launcher whose binary it cannot find. A timeout or a cancelled step stops the group (`killpg`, also when the binary itself has already exited; `taskkill /T` on Windows), and waits at most 10 s for it.
Reviewed by Sol (gpt-6-sol, medium): round 1 found four blocking issues (a cancelled step left Copilot running, no tree kill on Windows, an error event after an answer counted as completed, a configured MCP server was only caught after start), all fixed; round 2 found that the group was not stopped once the binary had exited and that a failed `taskkill` ended only the binary, fixed.
- Settings: Copilot CLI is an account tile under "On this computer", below the mockup's five tiles; sign-in is `copilot login`.
Limits: Live checks were run once on the M1 Pro (Copilot CLI 1.0.98, gpt-5-mini): catalogue, one JSON step, the tool probe, an unknown model. Windows was not run; the binary lookup and process group code there is covered only by unit tests, and `taskkill /T` cannot reach a child whose parent has already exited (in the measured runs, prompt mode with tools and MCP off started no child). Copilot adds its own system prompt, which DEIXIS cannot remove. No reasoning efforts are offered: the CLI accepts them but does not say per model which ones it supports. Each step uses the Copilot plan's requests at the rate GitHub sets per model.

## D23 — Gemini CLI connection with a Google account
Status: accepted · Date: 2026-10-14, landed 2026-10-15 · Writer: Claude
Context: People without an API key or a paid subscription should still be able to run DEIXIS. The Gemini CLI (`gemini`) signs in with a Google account, so a connection through it needs no key. The Gemini API connection (`gemini`, API key) stays as it is.
Decision:
- New connection `gemini_cli` in `models/gemini_cli.py`. Each step runs `gemini -m <model> -o stream-json -e none --approval-mode default -p ""` with the message on stdin, in a new home under `<data>/gemini-cli-home` that is deleted when the call ends. `GEMINI_CLI_HOME`, `GEMINI_CLI_SYSTEM_SETTINGS_PATH` and `GEMINI_CLI_SYSTEM_DEFAULTS_PATH` point at DEIXIS's own files, so the person's `~/.gemini` settings, hooks, extensions and GEMINI.md, and any system-wide Gemini CLI settings, are never loaded. Only an allowlist of environment variables is passed on; API keys are not.
- The generated settings register no built-in tool (`tools.core: []`), no MCP server, skill, hook, subagent, todo tool, extension or context file, and no directory tree. `GEMINI_SYSTEM_MD` replaces the CLI's own agent prompt with the step's base and developer text. The working directory is an empty folder, so an `@path` in passage text finds nothing to read.
- The sign-in stays the CLI's own. `GOOGLE_APPLICATION_CREDENTIALS` points the CLI at the person's `~/.gemini/oauth_creds.json`, which the CLI reads itself. DEIXIS checks only that the file exists and never opens, copies or links it. The CLI writes a refreshed token and the account email into the per-call home, and both are deleted with it. `NO_BROWSER=true` makes a missing sign-in an error instead of a browser window.
- Fail closed: any `tool_use` or `tool_result` event, or a non-zero tool call count in the result, is reported as a tool item, so the step stops with `model_isolation_violation`. The per-model stats of the result name the model that answered; any model other than the requested one is reported as the answering model, so the step stops with `model_mismatch`. The CLI has no JSON-schema mode, so the adapter does not enforce the schema: the flow adds the schema appendix to the developer text and the bounded repair applies.
- Health runs the CLI with an empty prompt. The CLI then signs in and sets up the account but stops before any model request, so the check sends no prompt. "No input provided" means ready; an IneligibleTierError or an authentication error is reported with Google's reason.
- The CLI cannot list models. The catalogue is fixed in DEIXIS from the ids Gemini CLI 0.60 accepts (2.5 Pro, 2.5 Flash, 3 Pro Preview, 3.1 Pro Preview, 3 Flash Preview, 3.5 Flash), and the sheet says the list is fixed. No reasoning effort is offered.
- A step completes only when the closing event says success, no error event came and the process exited 0. A sign-in refusal with no answer and no model stats counts as not sent, also after the `init` event.
- Reviewed by Sol (gpt-6-sol, medium): round 1 found that a non-zero exit with a success event counted as completed, fixed.
- Each run gets its own process group (`models/cli_process.py`, shared with Copilot CLI, D24): the CLI relaunches itself as a child, so a timeout or a cancelled step stops the whole group and waits at most 10 s. The version shown in Settings is read with a 60 s limit and its failure does not fail the check (`gemini --version` took over 20 s on 15 Oct).
- The UI shows a Gemini CLI tile under On this computer, below the mockup's five tiles next to Copilot CLI, with the terminal sign-in command (`gemini`, then Sign in with Google) and a copy button. The shared Sign in button comes later.
Limits: Measured on 14 Oct with the owner's signed-in account and Gemini CLI 0.60.0 through the adapter: Google refused the account before any model request, with "This client is no longer supported for Gemini Code Assist for individuals", reason UNSUPPORTED_CLIENT and tier free-tier. Health reports this and a step stops before sending. The same refusal was seen on 15 Sep, and again on 15 Oct through plain `gemini` and through this connection, whose check and step both report it. So no real step has run through this connection. Answer quality, the model check, the tool-free answer and the fixed model list are tested only with a fake CLI. The CLI version available today, 0.64.0, was not tried. Whether a paid Google AI plan or a Workspace account with Gemini Code Assist Standard (`GOOGLE_CLOUD_PROJECT` is passed on) is accepted is not known. Google's terms for using the CLI's sign-in from another program, and its free-tier limits, were not checked. That tool registration is empty is read from the CLI 0.60 source, not observed in a run; a tool the model calls anyway is still caught by its event.

## D29 — A key saved in Settings wins over the same key set in the shell; removing it brings the shell key back
Status: accepted (session coordinator, which the owner left the choice to, 15 Oct 2026) · Date: 2026-10-15 · Writer: Claude
Context: D19 kept a key set in the shell ahead of everything, and Settings hid the key field for such a key ("change or remove it there"). The owner found Semantic Scholar's card with no way to enter a key. In the packaged app (P10) Settings is the normal place for keys, and a saved key that is silently not used reads as a bug.
Decision:
- A key from the shell shows the key field, with the note that a key saved here replaces it. Saving stores the key in the keychain and puts it into the process environment over the shell value; the shell value is remembered.
- At startup a keychain key is loaded over a shell value too, but not over a key still kept in `.env` (no keychain, or the move failed).
- Remove key deletes only the keychain copy and puts the remembered shell value back (`shell_fallback` in `/api/credentials` says one is waiting). A key that comes only from the shell has no Remove button, and `DELETE` on it is still refused (409): DEIXIS never changes or removes the shell key itself.
- When no keychain is available, a shell key keeps the old note and cannot be replaced.
Limits: Supersedes D19's "a key set in the shell still wins". Tested with an in-memory keychain and fake shell values; the real macOS Keychain and a real shell override were checked only by hand in the browser.

## D32 — The library's folder can be changed in Settings; the move happens at the next start
Status: accepted · Date: 2026-10-15 · Writer: Claude
Context: The owner asked for a "Data location" card like Claude Science's: where DEIXIS keeps its library, how big it is, free disk space, and a way to move it. Until now only `DEIXIS_DATA_DIR` could move it.
Decision:

Symlinks and `pyvenv.cfg` files under `tools/` that named the old folder are pointed at the new one.
- A folder that already holds `library.sqlite` is opened as it is; the old library stays where it was and nothing is merged. The confirmation says so first.

The tool environments' relinking was tested on a synthetic layout only, so a moved Marker or built-in model install may still need reinstalling.

## D31 — A run's OpenAlex and Semantic Scholar requests are stored one row each and counted in its Usage box
Status: accepted · Date: 2026-10-15 · Writer: Claude
Context: The run's Usage box gave OpenAlex's day budget but no count of the run's own requests (S27, COPY_CHANGES usage-box-openalex). The steps store traces of some requests, but a retried search replaces its step's trace and the planning requests (term counts, routing, seed lookups) and the OpenAlex PDF lookups keep none.
Decision:
- Migration 0011 adds `provider_requests`: one row per attempt of `providers.common.send` made for a run (each 429 retry is its own attempt) and per OpenAlex PDF lookup by DOI (`documents/acquisition.py`). The row is written just before the attempt is handed to the HTTP client, as "not known whether sent", and settled when the attempt ends; a refused attempt is settled before the retry wait. The run is the one whose work is running (`Flow.execute`, or the background full-text fetch it queued), passed through a context variable; a request made outside a run is not stored.
- A settled attempt has `sends` 1 when it went out; one closed before sending (`before_send`, or a timeout waiting for a pooled connection) is not, and a stop during a local wait (start gate, pacer) never reaches the client and has no row. `refusals` is 1 when the provider answered without executing: a 429 (retried or not) and any final `rejected_not_executed`; for a PDF lookup, any 4xx but 404. This is R19's reading: a refused request was sent. An attempt cancelled while out, still out, or out when the process stopped stays `unknown`; the next start marks the last kind `backend_stopped`. Unknown attempts are named apart, never counted as sent.

Architecture
- A FastAPI backend (`backend/deixis`) serves a React UI (`apps/web`) on loopback only. The API checks Host and Origin against an allowlist, and every mutation needs the double-submit CSRF token (`deixis_csrf` cookie, `x-deixis-csrf` header).
- A research has scope revisions. Each run is a list of steps keyed by `operation_key`. A step that already succeeded returns its stored output, so pause, resume and crash recovery never repeat a model call or a provider request that finished.
- A run stops at its next checkpoint on pause, cancel or a newer scope revision.
- One worker owns execution through an OS advisory lock (`flock`). At startup it marks half-finished steps and model sessions `outcome_unknown` and the runs that held them `paused`; it does not retry them on its own. The user resumes.

Model boundary
- Each model step gets a stored `StepInput` (records, allowlisted IDs, `step_input_id`, `scope_revision`, `skill_package_hash`) and a strict JSON output schema. Everything sent is stored before the call.
- The model has no tools. A tool item in the output fails the step with `model_isolation_violation`.
- Output from a model other than the requested one is recorded and never used (`model_mismatch`). No other model or connection is tried in its place.
- Schema repair is bounded: one repair call (`MAX_SCHEMA_REPAIRS = 1`), none for `vocabulary_labels` and `abstract_screening`. The answer step has one exception: when only the several-sources rule for a `source_stated` claim (and anchor defects code may salvage) still fails after that repair, it makes one more call, `grounded_answer_resplit` (old D249), if the model-call budget still allows it. If repair fails, the answer is stored as an unverified draft and is not shown as a cited answer.
- Answer and review steps see short citation handles instead of record IDs (old D12). Code resolves them back to record IDs before validation.
- Editing a runtime file of `methods/deixis-research/` changes `skill_package_hash`. The app refuses to start when the package fails its integrity check.

Evidence rules
- Every published claim cites passages that were given to that model step, and each claim-passage link needs a contiguous anchor that code locates in the stored passage text. The UI highlights only that located anchor.
- A `source_stated` claim cites one source; two versions of one work count as two sources and are not independent evidence. When more than half of at least four claims are `analyst_inference`, the answer step makes one optional rewrite call.
- `structurally_valid` means the answer passed these deterministic checks. It does not mean each cited passage supports its claim. The `answer_review` run is a separate recorded model assessment and never edits the answer.
- Reading depth stays visible: metadata, abstract, selected PDF passages and full text are different evidence levels. Abstract screening never includes a source by itself, and a user's own inclusion or exclusion overrides the model's.

Fast-path policy (`fast_path.py`, `fast_path_v1`)
- Every new discovery run freezes this policy into its budget, with a `policy_hash`. Later code changes do not rewrite a frozen policy.
- The numbers per depth, from `fast_path.MODES` (stage seconds for plan, search, ranking, read and answer):
  - Quick: 30/30/30/60/30 (180 s); N 25, K 10; keyword record cap 450; 10 chain seeds, 2 backward and 2 forward chain requests.
  - Standard: 30/45/60/120/45 (300 s); N 50, K 20; cap 1000; 20 seeds, 4 backward, 8 forward.
  - Detailed (policy mode `deep`): 45/90/120/270/75 (600 s); N 100, K 40; cap 2000, of which 500 are reserved for Semantic Scholar; 30 seeds, 8 backward, 16 forward.
- N is how many works of the frozen list are screened and looked up; K is how many of them can reach full text.
- Stage time is active wall time that survives pauses and restarts. Unused time carries to the next stage, overrun is recorded as debt, and each stage keeps at least 25% of its base.
- Search, ranking, read and answer have soft deadlines. Submitted model calls drain; a read-stage call still out 5 s after the deadline is cut (`model_read_cutoff`).
- Plan:
  - code takes search words from the question, three optional `vocabulary_labels` calls sort them into blocks, and OpenAlex count requests check the terms;
  - a `search_query` model call writes the query blocks (`DEIXIS_SEARCH_QUERY=model` by default); if it fails, the run stops with `search_query_failed`;
  - at most one OpenAlex request routes the sources (none when no domain source needs it);
  - three optional `criterion_proposal` calls vote the inclusion criterion;
  - the approval is recorded as `unattended`, and nobody is asked.
- The protocol, with its search plan, freezes after these planning requests and before the first request that fetches search results.
- An empty vocabulary (`vocabulary_empty`) or a too-broad one (`vocabulary_too_broad`) ends the run with that message. There is no approval card; the user rewrites the question, which makes a new scope revision.
- Search: one OpenAlex semantic page (up to 50 records) and OpenAlex keyword pages of 100, read page by page across queries under the keyword cap. Detailed also sends one Semantic Scholar bulk query. No other provider is searched and there is no second search round.
- Chain: one round, OpenAlex only (backward references and the first cited-by page per seed), overlapping the search and cut off before the ranking deadline.
- Ranking embeds the pool and freezes the list.
- Read: Semantic Scholar and Crossref look up missing abstracts for the top N; when Scopus is in scope, configured, its institutional COMPLETE view is confirmed (`complete_view_entitled`) and the lookup budget allows, it completes the abstracts still missing. Each batch of abstracts is screened by two model calls. At most K works get full text; a slot whose work found no text passes to the next work in list order.
- PDF retrieval uses 12 shared slots. At the read cutoff, fetches already running are handed to the background lane and go on; queued works start from the background queue only while fewer than 4 background fetches run.
- When discovery completes, one answer run starts on its own. It answers from the evidence the read stage owned at its cutoff, then queues a separate `answer_review` run.
- Late full text can produce one new answer revision (`max_revisions: 1`). The first answer stays as it was.
- An answer over attached PDFs only (no completed discovery) uses the inspection route: PDF fetch, lexical and semantic passage ranking, then `grounded_answer`.

Providers
- All connectors in `providers/registry.py` stay: OpenAlex, Semantic Scholar, Crossref (lookup only), arXiv, bioRxiv (through OpenAlex), PubMed, IEEE Xplore, Scopus, CORE, SerpApi (supplementary), plus the Zotero collection import. Keys come from the untracked `.env` or the system keychain.
- The research search uses only OpenAlex and Semantic Scholar. Abstract lookups use Semantic Scholar and Crossref, then Scopus under the conditions above. The other connectors stay registered and configurable.

Storage
- One SQLite connection is shared by the API and the worker on the event-loop thread. Writes are short synchronous transactions with no `await` inside, and a UI-visible event is written in the same transaction as the state it describes.
- The schema starts from `storage/migrations/0001_baseline.sql`. A schema change is a new numbered file from `0002_` on. A migration that has been applied is never edited, the baseline included, and tables are not dropped.
- Runtime data (database, PDFs, provider payloads, Codex home) lives in `DEIXIS_DATA_DIR`, never in the repository.

One-time reset (old D261)
- The 77 old migrations were squashed once into the baseline, and the code that kept earlier libraries working was removed. A library written before the reset is refused at startup, and its app data folder is to be deleted. This reset is not repeated.

Limits:
- This entry restates decisions made, reviewed and tested under their old numbers and adds no behavior. The commit that wrote it also removed two method files no step loaded and corrected method and project docs to match the code.
- The tests run on synthetic records and a scripted model. They show workflow behavior, not answer quality or live latency. Live measurements are in STATUS.md and the old log.
- The anchor locator accepts a near match at a provisional 0.9 ratio over one contiguous region.
- Stage deadlines are soft, so a run can exceed its target time.
- The startup refusal of an old library says "newer DEIXIS", which is misleading for an older library (old D261).
