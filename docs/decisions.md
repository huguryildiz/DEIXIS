## D92 — A model writes the sw search query once per scope revision, and the code's own query is searched beside it

**Status:** accepted; implemented 2026-09-23 (slice 13h). **Date:** 2026-09-23.

**Context:** After slice 13g the owner decided that the model should write the query, not the code rule. Two
measurements with `gpt-5.6-luna` on the vocabulary experiment's three questions settled how
(`.local/sw-model-query-experiment-2026-09-23/`, `…-2026-09-24/result.md`). With the revised prompt (a topic term in
every task block, method names only beside one), the model's query alone found 17, 19 and 19 of the quantum question's
31 verified works over three separate calls (rule, fixed before running: at least 18 on every call) and 4 of the
packet-size question's findable 4 on every call. The model's query and the 13g code query together, each read to 1,000
records, found 23 and 4 on every call (rule: at least 20 and 4). The two queries find different works: the model's
brought 5 works the code's missed on every call, the code's 6 to 9 the model's missed.

**Decision:** (1) A new model step `search_query` (`references/search-query.md`, contract
`contracts/research/search-query.schema.json`, `deixis.search_query.v1`, a literature task) returns at most six terms
for the setting and task blocks, each with a `kind` (topic, method, population, other) and a short `why`, and up to
three backups per block. The StepInput carries the question alone, not the code's word list. One call per scope
revision, stored with its StepInput, and one schema repair; nothing is voted on. The contract's checks refuse more
than six terms, an empty block, a term given twice and a term with query syntax or more than four words. (2) Code
counts every chosen term alone and with the other block's chosen terms (at most 24 count requests). A term no record
holds alone is replaced by the next backup of its block; a term that finds nothing with the other block stays and
carries a warning; no count removes a term for being large (the one-million rule does not apply). Every term enters
the query as its whole phrase. (3) The proposal's vocabulary holds the model's terms (`block_assignment` and origin
`search_query`), the question's claim, exclusion and outcome phrases, and the 13g code vocabulary whole under
`code_query`. The first round sends, per provider, the model's query and then the code's, cut to
`max_provider_requests`, so the OpenAlex pair survives every effort; each query carries `origin` (`model` or `code`),
and a code query identical to the model's is not sent twice. Each query reads the effort's `SW_READ_LIMIT` with its own
D89 share, so the round's request allowance grows with the second query. The second round is built from the model's
terms, and its candidates come from the model query's own records; the code's query has no second round. What orders
and closes records (ranking blocks, the abstract stage's code rules, the survey title words, the criterion's sought
terms) reads both queries' terms. (4) A failed call, a second invalid answer, or an answer left with an empty block
after the counts stops the run with `search_query_failed`; the code's query is never searched in its place unless the
user chooses it. Resuming asks the model once more (two attempts); `POST /api/runs/{id}/search-query-choice` searches
with the code's query alone. The user's own key terms skip the step. (5) The approval card shows the model's terms with
their kind, reason, two counts, backups and warnings, the compiled queries, and the code's query with a switch that is on
by default; term corrections act on the model's terms as whole phrases, and switching the code's query off is a
correction (`edits.code_query`). (6) A run is given `SEARCH_QUERY_CALLS` (4) on top of its preset. (7) The setting
`search_query` (`DEIXIS_SEARCH_QUERY`) is `model` in the product; `code` keeps 13g's query alone with no model call, for
tests and measurements. `legacy` is unchanged.

**Protocol body (version note):** `deixis.protocol.v1` gains, for a model-written query only, `search_query`: status,
the prompt (`files`, `schema_version` and the `skill_package_hash` of the StepInput the model was sent, which can
differ from the body's own when the package changed before approval), the model, attempts, `step_input_id`,
`resolved_model`, the model's answer, every count and warning, each term's kind and reason, `code_query_searched` (a
code-origin query is among `compiled_queries`), `code_query_switched_on` (the card's switch, which the request limit or
an identical model query can leave with nothing to send) and the code's `code_concept_blocks`; `compiled_queries` entries gain `origin`; `thresholds` gain
`search_query`. A run whose model failed and whose user chose the code's query records `search_query` with status
`failed`, its attempts and `choice: code_only`. A body without these fields was frozen before this decision or by a run
on the `code` setting; the fields' absence means they did not exist then. `concept_blocks` and `vocabulary` describe the
model's terms. `skill_package_hash` changed from `sha256:b35b4f4960276c535452847693f76ea973f5e5a2417d51bf93527b9b82bb5e7c`
to `sha256:7d4e238c3e9feebd451c77fb997aff717a3617008bd4165be56f9fba46bf6fca`.

**Acceptance (2026-09-23, `.local/sw-slice13h-acceptance-2026-09-23/`):** the product's `_search_query` step on fresh
copies of the 13g acceptance library, three separate calls per question (9 calls, all valid on the first answer),
447 OpenAlex requests (all 200). Model and code first rounds and the model's second round, first 1,000 records each:
quantum 23, 23, 23 verified works (threshold 20); packet size 4, 4, 4 (threshold 4). The model's first round alone
found 19, 19 and 20 quantum works and 4, 4, 4 packet works.

**Limits:** One model and three questions; the packet-size answer list is weak (6 works from model labels, 2 not
findable with the question's words) and sepsis has none; only OpenAlex order was counted, not what the model later reads
or includes, and OpenAlex's search and count were the only provider behavior tried. Wall clock and the cost of the
second first-round query were not measured; `quick` and `standard` with two queries were not measured. The automatic
backup for a term that finds nothing with the other block was not measured and is only a warning. `kind` is unstable
across calls. On the packet-size question the second round, built from the model's terms by the 13g rule, added "data
aggregation" and "routing protocol" and grew to 6,858–21,511 records with no verified work; its candidates come from the
model query's titles only, and a candidate list drawn from both queries' records was not run. The acceptance read titles
only for the candidates, where the product also reads author keywords.

## D90 — Repair the sw search query: fit two blocks evenly, let the second round only add and keep its task block, and read 1,000 records per `detailed` query

**Status:** accepted; implemented 2026-09-23 (slice 13g, Tasks 1 and 2 and the `detailed` limit of Task 4). Task 3
of the slice (two code bounds on the block labelling) was implemented, failed the live acceptance and was removed by
the owner. **Date:** 2026-09-23.

**Context:** The vocabulary experiment (`.local/sw-vocabulary-experiment-2026-09-23/`) found three faults in how the sw
query is built. `_fit_blocks` fitted OpenAlex's five operators by dropping terms from the last block first, so a long
task block fell to one term (`(5 setting terms) AND "optimization models"`, 12 records). The second round replaced the
task block with the accepted phrases, and the field probe accepts setting synonyms by its nature, so the second query
was `(setting) AND (setting synonyms)`: 166,353 records and no verified work on the packet-size question, 12,559 on
the quantum one. And "quantum network" stayed a candidate beside the queried "quantum networks", which OpenAlex counts
as one term. The experiment's arm C (setting synonyms to the setting block, task block kept) found 4 of the 4 findable
works on the packet-size question.

**Decision:** (1) `_fit_blocks` drops a term from the end of the block that holds the most terms, the last such block
on a tie; every block keeps at least one term. 5 + 4 terms become 3 + 3 (were 5 + 1); 2 + 8 stays 2 + 4. (2) A
candidate phrase that holds a queried, claim or exclusion word sequence with a final `s` taken off every word is not a
candidate (`domain/expansion.stem`). (3) `second_round_vocabulary(vocabulary, terms, first_queries)` sorts each
accepted phrase: a phrase sharing a non-general word (plural `s` aside) with a setting term is a setting synonym, every
other one a task addition. With a setting synonym the second round searches `(synonyms) AND (first round's task terms
OR additions)`, the synonyms cut to as many as the first round's OpenAlex query kept of its setting block; with task
additions only, `(first round's setting block) AND (additions)`; with neither, no second round. Neither form sends the
first round's query again. Where each phrase went is stored in the expansion step's output as `second_round`; the
protocol body is unchanged (its `compiled_queries` carry the result). The count thresholds of the field probe are
unchanged. (4) `SW_READ_LIMIT["detailed"]` falls from 2,000 to 1,000 records per query; `quick` 400 and `standard`
1,000 are unchanged.

**Acceptance (2026-09-23, `.local/sw-slice13g-acceptance-2026-09-23b/`, 170 OpenAlex requests, labels read from the
experiment's library):** first and second round together, first 2,000 records of each: quantum 20 verified works
(threshold 19), packet size 4 (threshold 4); the second round's count fell from 12,559 to 583 and from 166,353 to
1,176; on neonatal sepsis from 2,344 to 482. The first run with Task 3 (`…-2026-09-23/`) failed: quantum 15, packet 0.
Its head-phrase bound kept "mathematical optimization models" first in the task block and the 2 + 4 fitting dropped
"routing" (first round 18 → 13 works); its compare bound put "channel" back in the task block, where as an OR term it
opened the query just the same (37,018 records).

**Limits:** Three questions, one run each; the packet-size answer list is weak (6 works from model labels, 2 not
findable with the question's words) and sepsis has none. The count thresholds still refuse task words ("resource
allocation", 140 of 213,947). There is no "read the setting block alone when it is small enough" rule: today's broken
second round did that by accident on the quantum question and found 6 works that carry no task word in their abstract
(24 against the new 20). The labelling still puts "channel" and "error model" in the setting block of the packet-size
question, and its first round still finds 1 of 6 works; the owner's next step is a measured arm in which the model
writes the query (2026-09-23). Halving `detailed`'s read cost one verified work per round in OpenAlex's order on the
quantum question; its effect on what the model reads and includes is not measured, nor is the wall clock. A run
resumed after this change reads its stored queries, but a `detailed` read still in progress stops at 1,000. English
questions only. `ranking.query_vocabulary` still ranks every accepted phrase in the task block.

## D91 — Scopus leaves the sw search and becomes the last abstract source, asked only on an institutional network

**Status:** accepted; implemented 2026-09-23 (slice 13g, Task 4). **Date:** 2026-09-23.

**Context:** In the 2026-09-22b measurement Scopus alone made 80 page requests of the `standard` run's provider search.
Scopus's search view (`STANDARD`) carries no abstract; the complete view does, and Elsevier entitles it by the caller's
IP range (a campus network or university VPN, `scopus.complete_view_entitled`).

**Decision:** A new connector field `sw_searchable` (Scopus: `False`) and `registry.search_providers(providers,
workflow)` decide where a new sw query may go: the block compiler, the sw protocol's `providers` /
`verification_providers`, the research view's `search_providers` and the StepInput's `enabled_providers` read it.
`searchable` is unchanged, so a legacy research searches Scopus as it did (`compile_queries` output is byte for byte
the same) and an sw run resumed with a stored Scopus query still reads it. In the lookup stage Scopus comes after
Semantic Scholar and Crossref: `lookup_plan:scopus` spends one request on the access check; without entitlement the
plan is `skipped: no_institutional_access` (or `access_unknown`) and no DOI is sent; with it, only the records the
first two sources left without an abstract are asked, one `view=COMPLETE` request per DOI (`query=DOI(<doi>)`), the
check and the requests counted within `MAX_LOOKUP_REQUESTS`, answers written as D77's (`record_lookups`,
`abstract_origin = "lookup_scopus"`). A research without Scopus in its scope or without its key opens no Scopus step.
`record_lookups` accepts `scopus` (migration 0048). Whether a record's abstract is settled is still decided by the
first two sources only, so a record Scopus could not be asked about is not left waiting for it.

**Limits:** Scopus's contribution to the search was measured on one topic (18 September). How many abstracts it fills
on an institutional network is not measured. The connection view still reports Scopus's role as `search`, which is
true for a legacy research only.

## D89 — Split the request allowance per sw query before the read starts, read discovery searches on several hosts at once, and write what they read in query order

**Status:** accepted; implemented 2026-09-22 (slice 13f). The wall-clock gain is not measured. **Date:** 2026-09-22.

**Context:** After slice 13e the provider searches of discovery are the largest item of a run (`standard`: about 6.5
of its 13.6 discovery minutes), because the queries were read one after another: 1.5 to 1.9 requests in flight on
average. 13e left the search parallelism out: before each page `_search` compared the run's shared request counter
with a run-wide allowance and paused the whole run with `budget_exhausted` when it was reached. Read in parallel,
which query spent the counter first would depend on which host answered first, so the same input could pause at a
different page.

**Decision:** (1) Every sw query gets its own request allowance before its read starts, `page_allowance(query,
effort, budget)`: the pages its provider needs to reach the effort's read limit (or the provider's own reachable
depth), times the requests one page may take (`1 + PROVIDER_WAIT[effort] + MAX_TRANSIENT_NETWORK_RETRIES`), plus
the run's `retry_provider_requests`, which a "search again" action raises by one per failed search and which every
query gets alike. Nothing in it reads another query's count. (2) Each query's requests are counted under
`usage["query_requests"]["search:<index>"]`, written in the same transaction as the run's `provider_requests`, so a
resumed run finds them. The run's own counter and what the user sees are unchanged. (3) A query that has spent its
share ends its own read: the page after which no request is left carries `stop_reason: "budget_exhausted"` and its
`unread_count`; when the share is already spent before a page is asked (a run resumed after a crash, or asked to
search again), that page's step is closed `cancelled` with `error_code: "budget_exhausted"` and no request is sent.
The run no longer pauses with `budget_exhausted` in the sw search stage, and the other queries go on. D18 is
unchanged: a run pauses only when no search of its first round succeeded. (4) A round's queries are grouped by the
host their requests go to (`Connector.host`, taken from the URL each module sends to; bioRxiv shares OpenAlex's
host). A host is asked one request at a time, its queries and pages in query and page order; at most
`SEARCH_PARALLEL_HOSTS = 4` hosts are read at once, whatever the effort. Page gaps, arXiv's interval, the Semantic
Scholar gate and the effort's 429 waiting run inside each host's task, as before. (5) A host's task writes nothing
but request counts. The pages are written by the round itself, in query order: a query's pages are written once its
read has ended and every query before it has been written, each page's step, search run and records in one
transaction. With no query at its allowance the rows, records, versions, candidates, work heads, step outputs and
events are those the one-by-one read wrote, in the same order (`tests/fixtures/search_parallelism/`, recorded on the
sequential code). A page's step carries the request's own start and end, not the time it was written. The
expansion round starts after the first round is written. (6) A stop is looked at before each request and written
once the requests in flight have finished; every page read is written, in query order, and a resumed run goes on
from the stored cursors without asking a page twice (owner's choice, 2026-09-22). A page read but not written when
the process dies has no step, and is asked again.

**Deviation from the run-wide allowance:** the shares add up to the old run allowance minus `max_provider_requests
+ MAX_TRANSIENT_NETWORK_RETRIES + MAX_RATE_LIMIT_RETRIES − n`, n the queries the run reads (plus `(n − 1) ×
retry_provider_requests` after a retry action). With at most `max_provider_requests` queries per round, the sum is
4 to 6 requests below the old allowance for `quick` (3 per round), 4 to 11 below for `standard` (8), 4 to 15 below
for `detailed` (12) when only the first round reads, and at most 1 below, 4 above and 8 above when both rounds read
all their queries. An OpenAlex query's own share is 6, 20 and 50 requests by effort, so the difference is small, and
no measured run reached the old allowance.

**Limits:** The wall-clock gain, whether 4 hosts is the right bound, and whether four providers at once draw more
429 or 406 answers are not measured (the third run of the 13ö measurement does). Whether a query's share ever runs
out on a real run is not known. A run paused in the middle of a round and then resumed can write the queries in
another order than an uninterrupted run: the pages of a later query read before the pause are written before the
rest of an earlier, half-read query. The records, pages and unread counts are the same, but when two providers
return the same DOI, which provider's record first creates that version can differ (the chosen trade: no page is
asked twice). The legacy workflow is unchanged: one request per query, one after another, against the run-wide
allowance. The per-query count sits inside `usage_json` as a map, while the web client types `usage` as numbers
only; the client reads only `model_calls` and `provider_requests`.

## D88 — Bound what an effort collects, not how long it runs: per-query read limits and provider waiting by effort, with 5 / 10 / 15 minute targets measured afterwards

**Status:** accepted; implemented 2026-09-22 (slice 13c), except the timeout wait, which is unchanged: only the
rate-limit wait is by effort. **Measured 2026-09-22** (below), and **re-measured after slice 13e** the same day; the
targets were not met and the constants have not been adjusted yet. **Targets revised by the owner (2026-09-22):**
`quick` at most 10 min, `standard` 15, `detailed` 20. **Date:** 2026-09-22.

**Context:** The owner wants a `quick` research to finish in about 5 minutes, `standard` in 10 and `detailed` in 15. Today no effort has a time bound and the three efforts collect the same amount: every `sw` query is paged to `SW_READ_LIMIT` (2,000 records) whatever the effort; the efforts differ only in how many works the model reads afterwards (40 / 100 / 300 abstracts, 20 / 50 / 150 full texts). On the slice 13 smoke run (`quick`, one topic) discovery took 28 minutes: about 20 of them in providers, of which 12 in Semantic Scholar's rate-limited abstract lookups for records Crossref had returned without abstracts, and 3 in the code stage. Model calls took under 3 minutes.

**Decision:** The efforts bound collection, by count, not by wall clock. (1) `SW_READ_LIMIT` becomes a per-effort constant, hand-picked as a starting point: `quick` 400, `standard` 1,000, `detailed` 2,000 records per query. (2) How long a run waits on a provider that answers 429 or times out is also by effort: `quick` does not wait on a rate limit (a rate-limited page or lookup batch ends that read, the records stay `unread` / `abstract_not_found` and are counted), `standard` waits the current bounded retries once, `detailed` as today. A skipped provider is recorded on the search or lookup step, never silently. (3) The minute figures are targets, not limits: nothing in the product stops a run at a time. After slices 13a–13d the three efforts are run once each on one topic and the measured durations are written next to the targets; the constants are then adjusted from the measurement, not before. A wall-clock cut-off was rejected because the same question would then see a different number of records on a slow day, which breaks the reproducibility the protocol record exists for.

**Measured (2026-09-22, `.local/sw-measure-2026-09-22/`):** one topic, three efforts, one after another, `codex` / `gpt-5.6-luna` · medium, protocol approved as proposed, embeddings off, frozen expectation in `protocol-luna.md`. From creating the research to the answer run ending: `quick` **12.1 min** (1,027 records), `standard` **29.9 min** (5,207), `detailed` **55.5 min** (6,301) — against targets of 5 / 10 / 15. Every answer was `structurally_valid`. The `detailed` figure is a partial reading: one adjudication call exceeded the adapter's 300 s turn limit (`client_timeout`) and paused the run at 119 of 300 calls. A first campaign on the same topic with `deepseek-flash` · high measured `quick` at 16.5 min and then ran out of DeepSeek balance mid-`standard`; the two campaigns' durations are not compared.

What the measurement changes: the collection limits did their job — provider waiting is no longer the cost (`quick` discovery made 11 provider requests and 47 lookups, against 81 and 214 on the slice 13 smoke run). The wall-clock cost has moved to two other places. First, `code:fulltext_work` is the whole of the retrieval stage and runs at parallelism 1.0 (300 steps, 16.4 min in `detailed`); its sequential order was a deliberate choice whose cost was unmeasured, and it is now the single largest item. Second, discovery's provider searches overlap each other only partly (parallelism 1.6–1.9). Full-text adjudication is the largest *model* cost (51.1 min of calls in `detailed`) but runs at parallelism 4.6–5.5, so it is 11.1 min of wall clock. The per-effort constants are therefore left as they are until those two are addressed; adjusting collection alone cannot reach the targets, and the fixed stages (protocol proposal about 3 min, answer about 3 min) already spend 6 of the 10 minutes a `standard` run is meant to take.

**Also found:** every arXiv search of all four runs answered HTTP 406 with an empty body and no `Retry-After`, so arXiv contributed zero records, and after D87 removed Crossref a run could fall back to OpenAlex alone. The commit that recorded the measurement read this as arXiv reporting a rate limit with 406 instead of 429. **That reading is a hypothesis, not a measurement:** replayed the same afternoon (review, 15:50 UTC), the stored query got 406 from the product's own client while `curl` with the same User-Agent and the same URL got 200 in the same second, and a minute later the product's client got 200 too; the encoding of the query made no difference. So it is intermittent and client-dependent, not a plain per-IP limit, and its cause is not known. `providers/common.py::send` now takes which statuses read as a rate limit (429 everywhere, `(429, 406)` for arXiv), which gives the bounded retries a second chance at it at a cost of at most 45 s per search on `standard` / `detailed` and none on `quick`; whether that recovers arXiv's records is **ölçülmedi** and is checked on the next measurement.

**Re-measured after slice 13e (2026-09-22, 18:44–20:05 UTC, `.local/sw-measure-2026-09-22b/`):** same topic, same three efforts back to back, same model and settings, commit `8fa06b4`, `skill_package_hash` unchanged, constants unchanged. The owner revised the targets the same day to `quick` ≤ 10 min, `standard` 15, `detailed` 20.

| effort | D88 target | revised target | first measurement (`7df0102`) | after 13e (`8fa06b4`) |
|---|---|---|---|---|
| `quick` | 5 min | ≤ 10 min | 12.1 min | **9.1 min** |
| `standard` | 10 min | 15 min | 29.9 min | **26.2 min** |
| `detailed` | 15 min | 20 min | 55.5 min (partial, reading paused at 119/300) | **45.7 min** (complete) |

Retrieval is no longer the cost: `code:fulltext_work` now runs at parallelism about 3.8 (was 1.0), and the retrieval stage fell from 8.1 to 2.2 min (`standard`) and from 16.4 to 7.4 min (`detailed`, with twice as many PDFs downloaded). PDF text extraction is a small part of it (0.5 s median per PDF, and it runs in parallel threads). Discovery is now the largest item and did not change (`standard` 13.6 min: protocol proposal about 3, provider searches about 6.5 with Scopus alone making 80 page requests and providers overlapping only 1.5–1.9 at a time, abstract lookups about 2, abstract screening about 2); search parallelism was left out of 13e by the owner. Roughly 15 of `standard`'s 26 minutes are model calls. In `detailed` one reading call hit the Codex turn limit after 307 s, was resent once and succeeded; the run did not pause. The two campaigns did not see the same input: the same question collected a different number of records and found a different number of PDFs (`quick` 720 vs 1,027 records, `detailed` 117 vs 58 PDFs), so the reading-stage durations also carry a difference in work.

Two findings. **arXiv still returned nothing:** all six arXiv searches failed, now as `rate_limited`, so the `(429, 406)` retry did not recover it; the cause is still unknown. **The answer repair path does fire, and the first measurement misread it:** in all three new answer runs, and on re-reading the first campaign's database in all three of its Luna answer runs too, the first draft failed rule checks (`missing_citation_anchor`, `duplicate_citation_anchor`) and the single repair round produced a valid draft; the answer run's two model calls were answer + repair, not answer + review. No schema error occurred, so the part slice 13a added (schema and rule errors reported together) is still **ölçülmedi** with Luna. The repair round is about half of the answer stage (46–134 s).

**Evidence and limits:** The figures come from one `quick` run on one topic (`.local/sw-smoke-2026-09-22/result.md`); the per-effort limits and the wait rule are hand-picked; the measurement above is one run per effort on one topic, with the three efforts run back to back from one network, so the spread and any rate-limit carry-over between them are **not measured**, and label, phrasing and answer quality are not measured either. The targets may not be met by collection limits alone: the code stage (slice 13d) and Crossref (D87) are the other two known costs. The abstract read limits (D81), full-text limits (D83, D85) and the model-call budgets are unchanged. `legacy` researches are unchanged.

## D87 — Search academic sources through OpenAlex and Semantic Scholar; Crossref verifies a DOI's metadata and links but is no longer searched

**Status:** accepted; implemented (slice 13b, 2026-09-22). **Date:** 2026-09-22.

**Context:** Crossref is the DOI registry: the widest bibliographic index, but abstracts are optional deposits and its search ranks loosely (2.8 million "matches" for the smoke run's query). On the slice 13 smoke run (third run, `quick`) Crossref's two queries returned 4,000 records, 3,438 works found by no other provider; 1,977 of those had no abstract at all and every one was sent to Semantic Scholar's abstract lookup, where 8 of 21 batches waited 40–88 s on rate limits (705 s in total). Asking Crossref itself for abstracts filled 0 of 200. After the code stage, of the 3,438 Crossref-only works 51 were `candidate`, 1,797 `no_abstract`, 1,115 `both_blocks_missing`, 154 `abstract_not_found`. OpenAlex, which is built on Crossref's records plus other sources and carries abstracts, returned 3,921 records in 131 s with no rate limiting; 2,399 of its 2,665 own works had an abstract. Whether the 51 Crossref-only candidates would have been found through OpenAlex with the same query was not checked.

**Decision:** Crossref leaves the search: it is not compiled a query in `sw` discovery and not offered as a search provider in the plan. It stays for what it is good at: `record_lookup:crossref` (metadata and links for a record whose DOI is known) and the DOI-based checks in acquisition. The connector remains registered so that a `legacy` research and an existing protocol record that names it keep working as they were. Semantic Scholar stays as the abstract lookup for records without one. A fallback ("search Crossref when OpenAlex and Semantic Scholar both fail") was discussed and not adopted: a search that only runs on a bad day would make two runs of the same question differ; it can be reopened with a measurement.

**Evidence and limits:** One topic, one run. The recall cost, the works only Crossref would have found, is **ölçülmedi**; the measurement step after slice 13c compares the same topic with and without Crossref on the candidates the code stage keeps. `legacy` unchanged.

## D86 — A model connection that cannot enforce the output schema is still usable: the step shows it the schema and a skeleton, code normalises a recorded alias table before validation, and repair no longer empties the run's budget

**Status:** accepted; implemented (slice 13a). **Date:** 2026-09-22.

**Context:** The user picks the model connection, and DEIXIS must work with the one they picked. Codex, Claude and Gemini receive the output schema through their APIs and cannot return JSON that violates it. DeepSeek's API offers only a "valid JSON" mode (a `json_schema` response format was refused with HTTP 400 on 2026-09-22), and the DeepSeek adapter does not even show the model the schema it receives: `run_step` takes `output_schema` and ignores it, so the model knows the field names only from the method file's prose. On the fourth slice 13 smoke run (`deepseek-flash`, `quick`) the full-text reading step got 34 invalid outputs out of 40 calls (`name` / `verdict` for `part` / `label`, or no `passage_id`), the repair attempts consumed the run's whole call budget and the run paused `budget_exhausted` with 1 work read; the answer step wrote `C1` where the schema requires `c1`, twice, and the answer was stored as an unverified draft. Everything up to those steps ran.

**Decision:** Three things, all recorded, none silent. (1) An adapter says whether it enforces the schema (`enforces_schema` on the adapter). For one that does not, the step appends the output schema and a one-item skeleton with the exact field names to the developer instructions; the stored StepInput keeps that text, and the DeepSeek adapter passes the schema on as text. (2) Before validation, code maps a small, named alias table onto the output — field renames (`name`→`part`, `verdict`→`label`, `status`→`label`) and claim-label case — and writes what it changed into `validation_json.normalised`; the raw output is stored untouched as it always was. Nothing that carries meaning is changed: a label value, a quote, a passage id or a missing required field is left for validation to reject. (3) A repair attempt is still paid from the run's budget, but a step that fails its repair is closed as `invalid_model_output` and the run goes on with the next work, as the abstract stage already does; the reading run and the answer run no longer pause `budget_exhausted` on repairs alone, and the summary counts the works the budget did not reach as before.

**Evidence and limits:** Deterministic tests with the fake adapter (skeleton present only for a non-enforcing adapter; alias normalisation recorded; an unmapped field still rejected; an enforcing adapter's StepInput unchanged, so `skill_package_hash` and the stored inputs of existing researches do not move). Whether DeepSeek follows a skeleton is **ölçülmedi** until the fifth smoke run, which is this slice's acceptance condition. The model boundary holds: the model has no tools, output from another model is still refused, and no alias is applied that changes what the model said.

## D85 — Follow an sw retrieval run with a full-text reading run: two model runs propose a label and a verbatim quote per criterion part, code checks every quote on the page, and only agreement with every quote verified includes a work

**Status:** accepted; implemented for `sw` researches. **Date:** 2026-09-22.

**Context:** SW1 point 2, SW11, and the open point D83 left: a retrieval run can fetch a PDF, but nothing reads it, so an `sw` research still includes no work until a person does. This slice reads. The model proposes. Code decides.

**Decision:** A completed `sw` `fulltext_fetch` run queues one `fulltext_adjudication` run (migration `0046`). Two model calls per work each return a label and a verbatim quote for every criterion part. Code verifies every quote on the page text the call was shown (`exact` or `normalized` only) and writes one full-text decision. A work becomes `included` with origin `code_rule` only when both runs label every part `present` and every quote verifies. Anything else stays unresolved, except two `not_met` runs, which write `criterion_absent` and derive `excluded`. The user's selection is never overwritten. `legacy` researches are refused this run kind. `CAPABILITIES.supported_tasks` and `TEST_EFFORT_BUDGETS` are unchanged.

1. **The queue is the next run, not a parallel one.** `execute` queues it in the same turn that marks the retrieval run `completed`, with no await between the two, only when the research is `sw`, `Settings.fulltext_adjudication` is `auto` (`DEIXIS_FULLTEXT_ADJUDICATION`, default `auto`), a criterion is frozen, and `read_plan` holds at least one work. The idempotency key is `fulltext_adjudication:after:{fetch_run_id}`. A manual start with no criterion stores `reason: no_criterion`, calls nothing, and completes.
2. **The budget is the run total.** `read_budget` gives `2 * N` model calls and `N` reads, `N` = 20 / 50 / 150 by effort, and no provider request. No share is reserved for repair. A work is sent only when every call it still owes fits; a work at the end of the plan that no longer fits is `not_reached` and gets no decision. A stored answer is not charged again.
3. **The plan is frozen, and identity is computed at read time.** The criterion comes from `store.frozen_criterion` and is stored on `code:adjudication_plan`. An unconfirmed PDF is written `pdf_identity_unconfirmed` with no model call and does not consume the read limit. A file the user supplied (`origin` `user_upload` on the source or the asset) is exempt. Only versions in `work_versions` of this research are read. A fresh model code stays out of the next plan; a stale one re-enters. A human full-text decision and a user exclusion are not read. A user inclusion is read, and its selection stays the user's even when the code is `criterion_absent`.
4. **The call shows a selection, built when it is sent.** At most 12 pdf pages. Fewer than 12 means the whole text. Otherwise up to 8 criterion passages in rounds by part (`criterion_order`), then the same topic terms `_retrieve` uses, then page order. Abstracts are not given. The two runs see the same pages. The model has no tools. Schema repair stays the existing one attempt and is paid from the same total.
5. **A label writes nothing by itself.** Both runs back, on the event loop, one short transaction, no await inside: proposals stored per part, quotes checked on the shown pages only, then one code on the read version, then `derive_selection`. One run missing, including an invalid output, writes no decision; that output is an answer for this run and is not retried, and the next run reads the work with two new calls. A call that did not answer pauses the run; resuming makes only the missing call. A response that arrives after the run stopped or the scope moved is stored as a step and writes no decision.
6. **`work_outcome` no longer lets a stale non-human full-text decision speak.** A human full-text decision still speaks, stale or not. A fresh non-human full-text decision still speaks. Otherwise the abstract decision does.
7. **The summary is totalled from stored steps and decisions**, so a resumed run matches an uninterrupted one. `model_calls` is `usage["model_calls"]`, which counts every `start_model_session`, including a repair and a failed call.

**Evidence and limits:** Deterministic tests in `tests/test_adjudication.py`, `tests/test_adjudication_flow.py`, the migration test, the contract fixtures, and the `adjudication` replay stage. Records are SYNTHETIC and from two fields. No live model call, no network, no dry run, no timing.

Limits, by name: `sw` only. **The prompt, the work limit, 12 passages per call, the 8 / 4 split, and the quote floor were tried with no model and measured nowhere** (slice 13 is the first model trial, slice 24 the measurement) — **ölçülmedi**. The model sees selected passages, so `criterion_absent` means "absent from the passages shown" and code may exclude on that; the user can override it, the work stays visible in its group (SW11.2), and no screen shows that yet. A verbatim quote shows the span is on the page, not that it supports the label (SW1). Two runs are two runs of the same model: they show consistency, not correctness. The gate stays off and nothing is saved by it. `abstract_promise_absent`, a gate-versus-model contradiction, the queue screen, and an immediate response to a PDF the user adds (SW11.9) are not built. There is no third run. A repair or a failed call can leave the works at the end of the plan unread. ## D84 — In an sw research, fill the answer input's criterion quota from the approved cue phrases, in rounds across sources, and fall back to the topic order when there are none

**Status:** accepted; implemented for `sw` researches. **Date:** 2026-09-21.

**Context:** SW12 points 1 to 3 and 5, SW15 point 4 and its 21 September addendum. The answer input already reserved room for "criterion passages", but it filled that room with `FORMULATION_TERMS`, one list written by hand for the quantum-optimization topic, so every other research paid for a vocabulary that says nothing about it. Since D78 and D80 each `sw` research has cue phrases a model proposed and the user approved or replaced. This is the first slice that uses them for anything.

**Decision:** An `sw` answer run gains one code step, `code:criterion_phrases`, which reads the phrases and compiles them, and `flow._retrieve` gains an optional `patterns` argument that only an `sw` run passes.

1. **The phrases come from `protocol_records` alone**, through `store.frozen_criterion(rid, question, steering)`: the newest frozen body whose criterion is not null and whose question and steering are this run's. So a revised question leaves the old phrases behind, a body frozen with a null criterion does not hide an older filled one of the same question, and a proposal still waiting on the approval card is not read at all. An approved **empty** phrase list is a valid answer and is recorded as `no_phrases`.
2. **The step is frozen like a plan.** A resumed run recompiles what its own step stored and does not read the protocol again, so a protocol frozen between the pause and the resume does not change the run underneath itself. A second answer run opens its own step and reads the protocol afresh; the answer the first one published is not made invalid, because an order is not evidence.
3. **Patterns are literal.** Every phrase is normalised with `criterion.norm` — no second normaliser — and compiled as `(?<!\w)` + its words through `re.escape` joined by `\s+` + `s?(?!\w)`, case-insensitively. Text a model or a user wrote is never compiled as a regular expression. A phrase under `min_phrase_chars` (3) or repeating another is dropped with its reason. This is the form measured in `.local/generalized-criterion-2026-09-20/`.
4. **The score is a pair and is never stored**: how many separate phrases a passage holds, and how many occurrences in all. It is computed in memory from the passages `_retrieve` already loaded for this research's included works — passages, chunks and embeddings are rows every research shares, while phrases belong to one research, so no shared row is opened and no library-wide phrase search is made. `criterion_passages.criterion_order` sorts by `(-distinct, -total, physical_page, id)` and is the one place that ranks by phrases; slices 12 and 16 will call it.
5. **Two quotas, and the criterion one fills in rounds.** In the wide case every source still gives its first passage, then `limit // 4` places — the same number the formulation quota had — are filled round by round: round *r* takes each source's *r*-th criterion page in the answer source order, so the quota is never spent on one source's pages and every source holding a criterion page is represented. The rest is filled from the topic order as before. In the crowded case (D55) a source still gives its abstract and `PDF_PAGES_PER_SOURCE` pages, but one of those pages now comes from the criterion order; a source with no criterion page gives two topic pages, as it did.
6. **No phrases means the topic order.** An `sw` research with an empty pattern list adds nothing from the criterion quota and fills the whole input topically. It does **not** fall back to `FORMULATION_TERMS`: a word list written for one topic does not steer `sw` code.
7. **Nothing decides.** No `stage_decisions` row, no selection, no reason code; a passage no phrase matches is not deleted and not hidden, it merely does not enter the criterion list. Quote verification still runs on page text and `domain/contracts.py` is untouched. No model call and no call share are added, `max_model_calls`, `max_answer_passages` and the embedding step are what they were, and criterion passages are never found by embedding (SW12.5). No migration, no contract change, `skill_package_hash` unchanged. The `sw` protocol body gains `thresholds.criterion_passages` and loses `formulation_score_threshold`, which it no longer applies; a `legacy` body is byte for byte what it was.

**Evidence and limits:** 33 deterministic tests — `tests/test_criterion_passages.py` (the pattern, the score pair and the order, 12) and `tests/test_criterion_passage_flow.py` (the run's record through `create_app` and the two quotas through `_retrieve`, 21) — plus a new replay stage `criterion_passages`. Every phrase, record and page is SYNTHETIC and from two fields; no test touches the network and no model is called anywhere in this slice.

Limits, by name: `sw` only; `legacy` still uses the hand-written list, until slice 24. **The effect of the two quotas on the real multi-source 48-passage input, the quota share (`limit // 4`), the 1 + 1 split in the crowded case and the threshold-free list were all measured nowhere** — that is slice 24, and this slice deliberately measured nothing (**ölçülmedi**). The one number in hand comes from one topic and from inside single papers: the phrases produced by slice 06's prompt put a verified quote among the first 6 chunks for 37 of 53 papers (the hand list 49, BM25 plus embedding 20), and since those target quotes came from cue-selected passages SW12's circularity note still applies. The cost of a wrong or missing phrase list is that criterion passages fall back to the topic order, which that measurement puts near chance — and no screen shows the phrases, what was dropped or why there were none (slices 18 and 20), so a bad list weakens an answer silently. Symbol counting (`FORMULATION_SYMBOLS`) is not part of the phrase score: the measured phrase ranker did not count symbols and the signs are topic-specific. **No backward chunk overlap was built** (SW12.2 allows one "if cheap"; it is not): re-cutting the shared passages would change passage identifiers that evidence links, table cells and stored embeddings carry, and the measured gain is 12 of 205 quotes at a boundary with no ranking improvement. The phrase score is not stored anywhere. The three other consumers of SW12.4 — the passages the full-text model reads, the cue sentences of the human queue and the pages sent to Marker — are not built; the first two will call `criterion_order`, the third has no consumer yet. The passage selection of table cells (`_cell_passages`) did not change. The per-source cap of six is counted from one after the crowded pass in the `legacy` branch, as it was before this slice: when short sources leave the crowded selection unfilled, a long `legacy` source can reach eight passages. The `sw` branch counts what the crowded pass already gave (review, 22 September 2026); `legacy` stays byte for byte until slice 24. An `sw` answer without a criterion has **lost** the formulation quota it used to get. The pattern's `s?` catches the English plural alone, so in a suffixing language a phrase is found only as it was written — unmeasured. Whether phrases that occur in every paper blur the order, which SW15's addendum warns about, has no threshold and no inverse-document-frequency weight here and was not measured.

## D83 — Follow an sw discovery run with a full-text retrieval run that fetches once per work in rank order, records the version read, and leaves a work without text unresolved

**Status:** accepted; implemented for `sw` researches. **Date:** 2026-09-21.

**Context:** SW10 points 1 to 5, SW11 point 1, SW6 points 4 and 5. Full text is fetched today only for the works the user included, in an `answer` or a `pdf_collection` run. Since D81 an `sw` research includes no work from an abstract, so the text slice 12 is meant to read never arrives at all: the corpus stops at the abstract stage and waits for a person. This slice closes that gap and nothing else — it fetches and records, it does not read.

**Decision:** A `sw` discovery run that completes queues a run of the new kind `fulltext_fetch` (migration `0045`, the run kind's `CHECK`). The run freezes a plan of works, makes **one** retrieval attempt per work through the routes an answer run already uses, checks the file's identity, and writes one full-text reason code per work. No model is called, no contract and no method file changes, and `skill_package_hash` is what it was. `legacy` researches, `answer` runs and `pdf_collection` runs are untouched.

1. **"Background" is a queued run, not a parallel one** (owner's decision, 2026-09-21). One worker executes one run at a time and a research cannot hold two active runs, so while the retrieval runs the user can work with the list — include, exclude, open a PDF — but starting an answer or a new discovery run means pausing or cancelling the retrieval first; what it has fetched stays. **Named deviation from SW10 point 1:** the retrieval starts after the whole discovery run, model screening included, not "right after the code stage". `Settings.fulltext_fetch` (`DEIXIS_FULLTEXT_FETCH`, default `auto`) turns the queueing off; the idempotency key `fulltext_fetch:after:{run_id}` keeps one discovery run from ever opening two retrieval runs, and a paused, cancelled or failed discovery run queues nothing.
2. **The unit is the work, the order is three groups, and the limit is per run.** Eligible, in this order: the works the user included themselves, the works the abstract stage left as candidates, and the works it left `unresolved` with `fulltext_fetch` as their next step (`runs_agree_unresolved`, `abstract_not_found`). Inside a group the order is D79's inspection order. `FULLTEXT_WORK_LIMIT` is 40 / 100 / 300 by effort, hand-picked and **not measured**; a work outside it is counted as not reached, keeps every decision it had, and the next retrieval run starts from it. **Named deviation from SW10 point 1:** a work whose abstract the model has not read is *not* fetched, because `work_outcome` lets the full-text stage answer before the abstract stage, so a full-text code written now would hold a work `pending` even after its abstract turns out to be out of scope.
3. **One attempt, and the result table has four rows.** Text on any version of the work → `not_read_yet`; a PDF attached but no passage anywhere → `text_unreadable`; every route answered and no text → `no_fulltext`; at least one route that did not answer (a timeout, a lost connection, a 429, a 5xx) → **no decision at all**, the work's step closes `failed` with `fetch_not_settled` and a later run plans it again. That is D35's distinction between a link that refused and one that timed out, applied to the work. The lookup rows (`pdf_discovery_runs`) are the research's history, not the run's, so only each provider's newest row counts as unanswered, and a work whose lookup or looked-up copy did not answer is looked up again by the next run; before the review of 2026-09-21 the old row both blocked the second lookup and kept the work undecided, so every later run planned it and none could settle it. All three codes existed already and all three are `unresolved`: **no work is included or excluded by this run** (SW1 point 2), and the user's own decision is skipped, never overwritten.
4. **A verified copy of another declared version gets its own row** (owner's decision). When the record's own version gave nothing, `acquire_for_source(..., other_versions=True)` tries the candidates whose DOI is verified and whose version a provider named, opens a `source_versions` row under the same work carrying that version label (`store.open_lookup_version`, `_insert_other_version`'s pattern: title and authors copied, DOI and abstract not), and attaches the PDF there. D4 holds: nothing is attached to the published record that is not the published record's. The row is a member of the research the way a provider's other versions are, is never a candidate of its own, and does not head the work. A copy of `uncertain` version still waits for the user. The lookup a refused (403 / 404) own link opens inside `_acquire_pdf` is this work's one lookup, so the retrieval run passes `other_versions` through it as well (review of 2026-09-21); an `answer` and a `pdf_collection` run never pass it. Records are shared by every research: a row another research's lookup already opened joins the asking research instead of being missed, and its file is not fetched again. **Named deviation from SW10 point 3:** the versions are tried in label order (`publishedVersion`, `acceptedVersion`, `submittedVersion`), not by who hosts the copy, because a candidate row carries the label and not the host.
5. **The other-copy lookup is opened wider than D35, in this run kind only.** `_needs_other_copy` opens a lookup only after a link answered 403 or 404; here a work with no open link at all — most closed publisher records — is looked up once too, or SW10 point 5's "the twin first, then the author's copy" would never be tried. An `answer` run and a `pdf_collection` run keep the narrow trigger. Web search stays off: it is the user's **Find PDF** action (SW10 point 4).
6. **One matcher, one fetch path, no new downloader.** `match_pdf_to_source` moved from `api/app.py` to `documents/identity.py` and gained `identity.check(text, versions)`, which reads the head of the retrieved text and answers `doi`, `title` or `unconfirmed` against every version of the work. The answer is stored with the work's step and counted in the summary; it neither removes nor sets aside a file, because many PDFs carry no identifier on their first page and the candidate came from a DOI-verified route. **arXiv title search and Europe PMC were not built** (owner's decision): their measured yield on one topic was 2 of 116 and 3 of 118; Europe PMC is noted for slice 14 (source routing).
7. **The plan is frozen and the run is sequential.** `code:fulltext_plan` stores the list; a resumed run reads it back rather than deriving a list that has moved under it, and the step keys carry the head's identifier, never a place in the list. A work whose step is already stored is skipped without touching the limit, the download usage or the summary, and `code:fulltext_summary` totals the run from its stored work steps, not from a live counter — so a resumed run and an uninterrupted one report the same numbers (lesson 1 of slice 09's review). Works are fetched one after another: `deps.limiter` is sized for model calls, and six parallel downloads to one publisher are not acceptable. No second concurrency mechanism was added (lesson 2 of slice 09's review).

**Evidence and limits:** 55 deterministic tests — `tests/test_fulltext_plan.py` (the plan, the result table and the identity check, 31) and `tests/test_fulltext_flow.py` (through `create_app`, 24) — plus a new replay stage `fulltext_plan` and one migration test. Every record, title and file is SYNTHETIC and from two fields; no test touches the network and no model is called anywhere in this slice.

Limits, by name: `sw` only. "Background" is the next run on one worker, so another run means pausing this one, and at `detailed` effort that wait is roughly 25 minutes — **not measured**. **The duration, the share of works that yield an open full text, the version-label order, how much of a wrong PDF the identity check catches, the cost of the work limit and the cost of fetching sequentially were all measured nowhere**: SW10's numbers come from one topic and from scripts outside the product (slice 24). `unconfirmed` identity sets no file aside. A work whose abstract has not been read is not fetched. The requests the other-copy lookups make still do not enter the `provider_requests` counter (the same gap `pdf_collection` has). A fresh `no_fulltext` is not retried by a later run — the user's **Find PDF** and upload paths remain. The version label of a row code opens is the provider's declaration and is not verified against the text. A work that already carries a fresh code of this stage when its own text arrives another way keeps that code until the decision goes stale. There is no gate and no model reading of the text (slices 12 and 23), and no screen shows the counts, the codes or "not reached" (slices 18 and 20). **A stale full-text decision still shadows a newer abstract decision in `work_outcome`**: a work that turns out to be out of scope after a question revision stays `pending` because of an old `not_read_yet`. This slice documents that in a test and leaves the fix to slice 12, which owns the full-text stage.

## D82 — Let the user ask a model for other names of the search terms on the approval card; count every proposal, and let none into the query unless the user adds it

**Status:** accepted; implemented for `sw` researches. **Date:** 2026-09-21.

**Context:** SW2 point 5, SW2 point 6, SW1 point 3, SW14 points 2 and 6, SW17 point 2. The `sw` workflow takes its search words from the question by code (D73) and widens them from the first round's own records (D76). Neither arm can find a name the question does not use and the found records do not repeat, and slice 04b's dry run showed the data arm drifting towards the field's neighbouring topics rather than the question's other names. Since D80 the user sees the terms before the first search and can add one — but only if they already know the name. SW2 point 5 keeps a model for exactly this gap.

**Decision:** The approval card gains one button. Pressing it makes the run ask a model, once, for other names of the phrases the card already holds; code screens and counts what comes back; the card shows the list and the user decides. `legacy` is untouched, an unattended run (`protocol_approval = as_proposed`) never opens the step, and there is no migration. `skill_package_hash` changes, because a new method file is loaded.

1. **No automatic trigger** (owner's decision, 2026-09-21). SW2 point 5 says "when the first round is thin or the user asks"; only the second half is built. No code judges whether a round was thin, and the threshold is left to slice 24's measurement. The model is asked only when `POST /api/runs/{id}/term-suggestions` is called.
2. **The model proposes a term list, never a query.** The new `term_suggestions` task returns at most `MAX_SUGGESTED_TERMS` (12) entries of `{phrase, synonym_of}`; `synonym_of` must be one of the searched phrases it was given, and that is the contract's one error (`phrase_not_in_allowlist`) — without a given phrase behind it a proposal has no block and no anchor. There is no block field and no rationale field: the block is the anchor's, derived by code, and free text cannot be checked.
3. **One call, no repair, no vote.** `term_suggestions` is in `NO_REPAIR_TASKS`, and unlike the labelling (D74) and criterion (D78) steps it is not asked three times: two filters already stand in front of every proposal — the count probe and the user — and a 2-of-3 vote would drop exactly the rare-but-right name this step exists to find. The one call is added to an `sw` discovery run's budget beside `CRITERION_CALLS`; the effort presets themselves are unchanged.
4. **Code drops what cannot enter a query, and says why.** In this order, first reason only: `too_long` (over six words), `already_present` (a phrase the proposal already holds), `contains_claim_word` / `contains_exclusion_word` (SW1 point 3: the phrase carries a claim or exclusion phrase as a contiguous run of words), `duplicate`, and then `zero_results` for a surviving row no record holds. Nothing is edited in place (SW14.2): every proposal stays on record with its reason, and the row order is canonical — the anchor's place in the vocabulary, then the phrase — so the order the model wrote its list in reaches nothing (SW14.6).
5. **Nothing proposed is searched unless the user adds it.** The rows live in the step's output and in the view; they enter the vocabulary, the queries and the protocol only through the `add` operation of D80's correction. A run whose user asked and added none searches the proposal's queries byte for byte.
6. **The origin is derived on the server.** The `add` operation's shape did not change (`op`, `phrase`, `block`). A phrase whose normalised form is one of this approval's stored proposals gets the term origin `model`; anything else gets `user`. The block origin is `user` either way: the user put the phrase in that block. An added proposal goes through the same `edited_extraction` → `build_vocabulary` path as any other correction, and the count the suggestion step already read is handed to it as `known`, so it is never asked for twice.
7. **The model is not asked twice for the same thing** (SW2 point 6). A `ready` list is never re-requested; a card re-asked for the same question, steering and key terms carries the earlier approval's proposals (`carried_suggestions`) without a call, and the reapplied correction keeps its `model` origins. Only a `failed` request may be repeated, under a new step key, and only while the run has not been charged `SUGGESTION_CALLS` calls for this: every started call is charged, a failed one too, so a repeat after a paid failure would be paid for out of the abstract screening's share. The route then answers 409 and the card says the call is spent (`suggestion_call_spent`); a request that failed before any call started (no connection, none ready) costs nothing and may be repeated. An answer that proposed nothing is an answer: the card shows it, it is carried like any other, and the model is not asked again. A carried list is screened again against the proposal it is shown on (`suggestions.carry`), because a later run's labelling may build other phrases: a row may now be `already_present`, carry a claim phrase, or name an anchor that is no longer searched (`anchor_not_searched`); it stays on the list with its reason and keeps the count it was read at (review of 2026-09-21).
8. **The body of a run that asked for nothing is unchanged.** The `approval` record gains a `suggestions` block (requests, proposed, dropped, accepted, and where the list came from) only when the run asked or carried a list; a run that never asked gains no field. Its digest is still not the one from before this slice: the body holds the run's budget, and `max_model_calls` is `SUGGESTION_CALLS` higher for every `sw` discovery run, asked or not.

**Evidence and limits:** 55 deterministic tests — `tests/test_term_suggestions.py` (contract and pure code, 31) and `tests/test_suggestion_flow.py` (through `create_app`, 24) — plus a new replay stage `term_suggestions` and four contract fixtures; four Playwright cases in scenario H. ## D81 — Screen abstracts in an `sw` run with a code stage, two batched model runs whose quotes code verifies, and a read limit that leaves the rest unread rather than dropped

**Status:** accepted; implemented for `sw` researches. **Date:** 2026-09-21.

**Context:** SW9 points 1–4, SW1 points 1, 2 and 6, SW11 points 1, 3 and 4, SW6 point 2, SW5 point 5. Until now an `sw` discovery run screened with the old `screening` contract: one model call proposed `include` or `exclude`, that proposal was written straight onto the selection, and `max_candidates` cut the list. SW9 measured about 1,900 model calls for one round of screening at the old batch size, against a budget of 15 to 20.

**Decision:** An `sw` discovery run replaces that loop with an abstract stage of two steps. `legacy` is untouched: its `screening` contract, its batch loop, its `max_candidates` cut, its protocol body and its digest are unchanged, and it opens none of the steps below. Code looks the quote up with `contracts.locate_anchor` in the abstract the model was shown, counts only an `exact` or `normalized` match of at least `ABSTRACT_QUOTE_MIN_CHARS` (12) characters as verified, and a fixed table turns the two runs into one reason code. A record-level defect — an identifier the step did not send, one sent twice, an empty quote under a label — is a warning that costs that record its proposal for that run only. When the budget runs out the remaining works take `abstract_not_read` and the run **completes** rather than pausing.

Records are shown as short handles (`cnd_C0000001`, D12's pattern), resolved back before validation.

## D80 — Stop an `sw` discovery run before its first search until the user has approved or corrected the vocabulary and the criterion, and freeze what was approved

**Status:** accepted; implemented for `sw` researches, backend and screen. **Date:** 2026-09-21.

**Context:** SW2 point 6 ("the vocabulary is shown to the user with each term's origin, corrected, hashed and frozen; the model is not asked again within the same research"), SW15 point 3 (the user sees the criterion, its parts and its phrases in the same step and can edit them), SW14 points 1 and 2, SW17 point 2, SW11 point 10. Until now an `sw` discovery run read its phrases from the question (D73), let a model label their blocks (D74), widened them from its own records (D76) and had a criterion proposed (D78) — and then searched, without anyone having seen any of it. The dry runs of slices 04a and 04b showed the cost by name: the rule puts a population phrase in the claim list and the term drops out of the query; the second round accepts neighbours of the topic rather than other names for the task. The only correction the product offered was `key_terms`, which has no screen and replaces the whole extraction.

**Decision:** An `sw` discovery run opens a `protocol_approval` step after the criterion step and **before** the protocol is frozen. There is no migration, no new contract, no new method file and no new model call; `skill_package_hash` is unchanged.

1. The step writes the proposal — the vocabulary, the compiled queries, the criterion and the criterion step's failures — into its own output, together with a `proposal_hash` over the phrases, their blocks and the criterion fields, and then pauses the run with `protocol_approval_needed`. The step stays `pending`, so the worker's recovery does not read it as half-finished work. **No `provider_search` step is opened, no candidate is written and no protocol record exists at that moment.**
2. **Count probes run before the approval.** The main plan's condition read "no provider request before the approval"; it is narrowed here to the **search** request. The numbers the screen shows are the probes, and they are what decides whether a term enters the query as its root or as its whole phrase, so they are read while the proposal is being built.
3. A correction is a bounded list of operations on phrases the proposal already holds — `remove`, `move` to one of `setting`, `task`, `outcome`, `claim`, `exclusion`, and `add` — at most `MAX_TERM_EDITS` (40), plus an optional full replacement of the criterion and an optional note. An operation naming a phrase that is not there, or adding one that is, is a 422 with every fault listed, never a silently skipped line.
4. **One code path builds a vocabulary.** A corrected vocabulary is rebuilt from an `Extraction` through `vocabulary.build_vocabulary`; term dictionaries are never patched. The counts the proposal already read are passed to it as `known`: they are recorded as the probes they were and spend none of the probe budget, so only a phrase the user added is really asked about. An approval with no term edit rebuilds nothing and keeps the proposal's queries byte for byte.
5. **The user's correction stands above the model and the rule** (SW17.2). A phrase the user moved or added carries `user` as its block origin, and a phrase the user added carries `user` as its term origin; the labelling runs stay on record beside them. What the user adds meets the same count probe every other term met, so a phrase no record holds drops with `zero_results` and stays on record.
6. **Nothing is edited in place** (SW14.2). The proposal stays in the step output as it was and the approved form is written beside it; a frozen protocol record is never changed. The protocol body gains `approval` (mode, who approved, whether it was edited, the proposal hash, the number of operations, whether the criterion was edited, exclusion words the question itself uses, and the note); `criterion_origin.origin` becomes `user` when the criterion was edited.
7. **Network work runs in the worker, not in the route.** `POST /api/runs/{run_id}/protocol-approval` validates the correction, stores it and queues the run in one transaction; the worker probes, recompiles and freezes. A plain `POST /api/runs/{id}/resume` on a run waiting for the approval is refused with 409: there is no resuming past it.
8. **The user is asked once per question, steering and key terms.** A second discovery run of the same scope, and a revision that changed only the providers, reapply the corrections the earlier approval recorded; an operation whose phrase this run no longer has is skipped and kept in `skipped_edits`. A revision that changed what was asked about asks again.
9. The approval, the corrected vocabulary and the corrected criterion travel to the `protocol` step, `_freeze_expansion`, `_expansion`, `_second_sources` and `_ranking`. An expansion revision built from the proposal would undo the correction and, by changing the criterion fields, mark every decision taken under it stale (SW11.10).
10. `Settings.protocol_approval` (`ask` | `as_proposed`, `DEIXIS_PROTOCOL_APPROVAL`, default `ask`) lets a run nobody attends approve its own proposal. It writes `approved_by: "setting"` into the body, so such a run never reads as one a user approved.

**Evidence and limits:** the Playwright case H (`apps/web/e2e/protocol-approval.spec.ts`, seven cases against a second fixture server in `sw` + `ask` mode) shows the card stopping a run before its first search, a correction being drafted, refused and applied, and the folded summary of what changed; 64 deterministic tests in `tests/test_protocol_approval.py` (pure) and `tests/test_approval_flow.py` (through `create_app`), plus a replay stage `protocol_approval`; the full suite passes except one known, unrelated PyMuPDF memory-limit failure on this machine. Every fixture is SYNTHETIC and from more than one field and no test touches the network, so the tests show workflow behavior, not the quality of anything a user would correct.

Limits, by name: `sw` only; a `legacy` research opens no step, never stops and keeps its protocol body and digest. Count probes run before the approval (point 2). The screen is the approval card in the run's timeline item (slice 08b); what it was not measured on: **how users read this card was not tested with anyone** — no one but the owner has used it, and whether the block correction is understood, and whether the one to two minutes before it are tolerable, are unknown. A draft correction lives in the card alone and is lost when the page is reloaded; a correction the backend refused for leaving nothing to search is stored as `submitted` but is not rendered back into the card after a reload, so the card then shows the proposal again. The card shows a term's own origin and block origin only for the two searched blocks, because the view records them only there. Two states were exercised by hand and not by a test: a correction while it is being checked (the card is locked), and a run whose criterion step produced nothing (the card offers to go on without one or to write one). The approval is asked once per question, steering and key terms and there is **no way to reopen it**: after it has succeeded the route answers 409 and the only way to change anything is a scope revision that changes what was asked about. ## D79 — Order the inspection list by rank fusion of four code signals and an optional embedding signal, store every record's rank in every signal, and never cut by it

**Status:** accepted; implemented for `sw` researches. **Date:** 2026-09-21.

**Context:** SW7 (all points), SW8 points 1, 2 and 5, SW1 point 4, SW14 point 6. Until now an `sw` discovery run inspected its candidates in the provider's own order: `candidates.rank` is the record's place in the query it came from (slice 04c), and `max_candidates` cut by that. Nothing about the question decided which candidate the screening model read first. The signals were measured in `.local/quantum-rank-fusion-2026-09-18/` on one topic with 1,369 records and 20 high-confidence positive works: BM25 alone put the positives at a median rank of 189, the four signals fused at 158, and the three signals without TF-IDF — the combination a research with no verified seed really runs — at 121. The differences are within noise; what the measurement shows is that the fusion is **not worse** than BM25 and that one collapsed signal does not sink a record (g016 was 662nd by BM25 and 31st fused), not that it is better. Dropping a missing signal from the sum instead of ranking it last made the median worse (158 → 171).

**Decision:** In an `sw` discovery run, after the second sources of slice 05 and before screening, `flow._ranking` runs. It is code: no model call, no provider request.

1. Four embedding-free signals are computed over the run's pool and fused by rank with RRF (k = 60, read from `flow.RRF_K`): BM25 of title and abstract against the question's and every queried term's words; concept blocks hit in the title, then distinct block forms in title and abstract; maximum TF-IDF cosine to the verified seeds; bibliographic coupling plus direct citation with the graph seeds. Raw scores are never added across signals (SW7.1).
2. **The order removes nothing and decides nothing.** The step writes no row to `stage_decisions`, `model_proposals`, `selections`, `record_flags` or `record_links`. `max_candidates` was cutting before this slice and still cuts (slice 09, K3); what changed is the order it cuts by. A record outside it stays `pending` and is counted.
3. Every record's rank in every signal that ran is stored in `record_signal_ranks`, with whether the signal was available for it, plus the code-only fused order, the fused order of every signal that ran, and the inspection order itself. A tie inside a signal shares the mean rank; a missing signal is ranked last in that signal and still enters the sum; the last tie is broken by `source_version_id` (SW14.6). The share of records with no reference list is reported with every ranking (SW7.4).
4. TF-IDF runs only with a **verified** seed: a record the user included, or the scope's own seed. A record the model included is not verification. Without one the signal does not run at all and its rows are not written (SW7.5). The graph's seeds are the verified ones plus as many code seeds — the top of BM25 plus blocks — as fill the list to `GRAPH_SEEDS` (15); it does not run when no seed has a reference list. **Mixing verified and code seeds was not measured**: the measurement used either 15 code seeds or 5 verified ones. This is a plan decision.
5. The reference lists come from OpenAlex's `referenced_works`, asked for only on an `sw` read (migration `0044`, `record_references`, `source_versions.references_read`); a `legacy` request's `select` is byte for byte what it was and no extra request is sent. A list read as empty and a list nobody asked for are different states and neither gives a graph signal.
6. Embedding is the fifth signal and the rescue arm (SW8.1): a record outside the top 200 of the four code signals' own fused order but inside the embedding's top 50 goes to the front of the inspection list. **It has no authority** (SW8.2): with semantic search off, with no model or with a failed call, the four code signals produce the same ranks, the run neither stops nor pauses and nobody is rescued; a record the embedding never scored is not rescued by the tail rank it shares. On `sw` the existing `_source_similarity` now runs **before** ranking and over the whole pool instead of after screening over the screened candidates; on `legacy` it stays exactly where it was.
7. Every hand-picked number is a named constant in `workflow/ranking.py` and enters the frozen protocol as `thresholds.ranking`; the body's `signals` list names the five signals and the embedding model the research was configured with. Both the first revision and the expansion revision pass the same model, so a changed setting never rewrites a frozen body. `signals` is outside `decisions.CRITERION_FIELDS`, so changing the embedding setting makes no decision stale.
8. Four deviations from the reference implementation `fuse.py`, each deliberate: the product's own word splitter (`domain.vocabulary.words`) instead of its ASCII regular expression; the block score kept as the pair (blocks in the title, distinct forms) instead of `blocks * 100 + forms`; a block form matched at a **word start**, so a root catches its plural, which is deliberately not `expansion.count_yields`'s two-ended match; and a record with no abstract scored by BM25 on its title, counted as missing only in TF-IDF — SW7.4's "no abstract" example is applied to TF-IDF, not to BM25, because the measurement scored titles this way and the block signal already reads the title.

**Evidence and limits:** 55 new deterministic tests, one of them a replay stage (`record_ranking`); the full suite passes except one known, unrelated PyMuPDF memory-limit failure on this machine. Every fixture is SYNTHETIC and from more than one field and no test touches the network, so the tests show workflow behavior, not the quality of an order. One offline replay put the measurement's real pool through the product's own pure functions with no request and no model (`.local/sw-ranking-replay-2026-09-21/`, expectation frozen beforehand): 1,369 records, no verified seed so three signals, **median rank of the 20 positives 145.5, 8 in the top 100, 12 in the top 200, worst 544**, against `fuse.py`'s `rrf_no_tfidf` 121 / 9 / 12 and against the product's own BM25 alone at 184.75 / 6 / 10; 47.6% of the records have no reference list; the whole computation took 0.49 s, so it is not run in a thread. Writing the reference lists cost the slowest 200-record page 0.72 s against 0.60 s without them (`timing.json`), under the 1 second slice 04c set.

Limits, by name: `sw` only. The order deletes nothing, but `max_candidates` still cuts and now cuts by this order — in the measurement even the best order left 12 of 20 positives outside the top 100, so this slice can reduce or increase that loss and it was not measured. One topic, 20 positives, and the fusion was **not** shown to beat BM25. With no verified seed TF-IDF does not run. Not measured: the mixture of verified and code seeds, the word-start match, scoring a record with no abstract by its title in BM25, and taking the union of a work's versions' references and abstracts. There is no co-citation signal: it needs requests for citing works. The reference lists come from OpenAlex alone, so a record only another provider found has no graph signal. k = 60 was not varied and the rescue arm's 200 and 50 were picked on one data set. The embedding now runs before screening over the whole pool, so it sends more requests than before; the free key's rate limit was not measured and `_source_similarity` still keeps no partial result and does not wait on HTTP 429, which stays where SW8 left it. Survey signals were measured on 1,336 earlier-screened records against an earlier model's `secondary_synthesis` label: a strong title word or a self-describing abstract phrase agreed at precision 0.72 and recall 62%, 150 or more references at 0.83 and 29%, OpenAlex `type = review` at recall 2%. For version identity, Semantic Scholar held 150 of 181 arXiv-to-published pairs as one paper and attached the preprint to a *different* published DOI in 12; arXiv's author-supplied DOI field and a Crossref preprint relation each linked one of the 19 pairs it left alone. What a second source could do for a missing abstract had never been counted.

**Decision:** In an `sw` discovery run, after both search rounds and before screening, three code steps run and no model is called.

1. **Survey flags.** `domain/survey.py` reads a record's own title, abstract and reference count against the field-independent lists in `domain/survey_words.py` and stores every signal in `record_flags`. Only a strong title word takes a record off the screening list, with the abstract-stage decision `survey_title_word` (`unresolved`, next step `seed_pool`); a self-describing abstract phrase or 150 or more references set a flag and the record is still screened (SW9.3 narrowing SW5.4). A strong word the research's own question uses drops out of that research's list and is recorded in its protocol. OpenAlex `type`, venue names and Semantic Scholar `publicationTypes` are not used. The reference count is asked for only on an `sw` paged read, through `Connector.sw_options`; it is stored once and never overwritten. A decision this step wrote is taken back when it stops holding: a record whose abstract arrived later, or whose title word became the subject of a revised question, gets `abstract_not_proposed`, so an earlier revision's survey row cannot keep it away from screening (review, 2026-09-21).
2. **A missing abstract is asked for by DOI.** `providers/lookup.py` asks Semantic Scholar's `paper/batch` endpoint, then Crossref's `works/{doi}`, through the same `send` path as a search, so the D67 gate and the bounded 429 retries apply. The abstract is stored with `abstract_origin` `lookup_semantic_scholar` or `lookup_crossref_jats` beside its payload file. Every answer is recorded per record and source in the library-wide `record_lookups`, so a record is asked once per source by whichever research asks first; only a `failed` row is asked again. Lookup requests and their retries are counted under `lookup_requests`, never under `provider_requests`, and no lookup can pause or stop the run (D18). A record without an abstract is `unresolved` and stays `pending`; it never becomes out of scope by any route, and a head without its own abstract is kept away from the screening model so that the model's `exclude` cannot reach it.
3. **External version links.** A DOI a second source names as another version of a record is stored under a new `linked_doi` scheme, which only the `sw` path reads. Such a link confirms a preprint-to-published merge even when the title differs (`external_link_names_published_doi`), and a preprint naming a *different* published DOI blocks a merge the text would have made (`external_link_names_other_doi`); arXiv's author-supplied DOI field now blocks as well as confirms. A record whose named DOIs disagree confirms nothing (`external_links_disagree`). Every merge goes through the same `save_link` path, so the two-published guard, the `undone` memory and the undo record hold unchanged. A merge already made that a later link contradicts is counted and left merged: only the user undoes a merge (D72).

No selection is written by this decision: every outcome is `unresolved`, which is what a `pending` selection already says, so `derive_selection` is not called and `selections.origin = 'code_rule'` still appears on no row. A `legacy` research is untouched: its provider requests are byte for byte what they were, it opens none of these steps and it reads no `linked_doi`.

**Evidence and limits:** 87 new deterministic tests; the full suite passes except one known, unrelated PyMuPDF memory-limit failure on this machine. Every fixture is SYNTHETIC and from at least two fields, and no test touches the network, so the tests show workflow behavior, not the quality of the survey rule or of the links. One live count was run through `providers/lookup.py` alone, against two stored pools and outside the product database (`.local/sw-abstract-lookup-2026-09-21/`): of the quantum pool's 105 DOI-carrying records without an abstract, Semantic Scholar filled 30 and Crossref another 20, leaving 55 (48% filled, 76 requests, 13 s); of the packet-size pool's 122, Semantic Scholar filled 10 and Crossref 3, leaving 109 (11% filled, 114 requests, 35 s). Of 302 arXiv-DOI records, Semantic Scholar named another DOI for 159. Of the 23 `extended_version` pairs slice 03 left open, Semantic Scholar holds both DOIs in only 6 and reads all 6 as two different papers, so it offers no evidence for merging them.

Limits, by name: this runs only on the `sw` workflow. No seed pool is built (slice 15); the flags are stored and nothing reads them yet. SW5 point 4's path from a full-text survey through the strict-cue gate to the human queue does not exist (slices 12 and 16). A title-word survey is stored as `unresolved` and no screen shows it. The word lists and the 150-reference threshold were chosen on one topic against an earlier model's judgement, so the reported precision measures agreement, not accuracy. The rule that drops the question's own strong word is an addition to SW5 and is not measured; it matches at a word boundary and stems nothing, so a question written in the plural ("not surveys") keeps the singular word in the list. A reference count comes only from OpenAlex's `sw` request and from the lookup answers; a record no source named a count for carries no signal, which is not a count of zero. Semantic Scholar `publicationTypes` was not used, and its documentation states neither that a batch answer keeps the input order nor what an unknown id returns, so an answer whose length differs from the request is refused rather than matched positionally. The second source's fill rate was counted on two pools only, with the numbers above, and the two differ by a factor of four. `MAX_LOOKUP_REQUESTS` was picked by hand: a record left outside one run's limit waits with `no_abstract` and is asked only by a new discovery run. A `not_found` answer is never asked again, so a pair Semantic Scholar links later is missed. Without a key, Semantic Scholar answers 429 often (D67) and the work falls to Crossref. The Crossref preprint relation is read only on records already asked about for an abstract, and the `externalIds` of Semantic Scholar's own *search* records are not used. A contradicted merge is counted, not undone. One article registered under two DOIs (two published records) is still not resolved (slice 20). A head without its own abstract is kept from screening even when another version of its work has one; slice 09 will read the abstract at work level. Links, flags and decisions appear on no screen.

**Status:** accepted; implemented for the `sw` workflow. **Date:** 2026-09-21.

**Context:** After D73 an `sw` research takes its first query from the question alone. If the user did not happen to write the field's common term, the query is narrow and no later step can widen it: the vocabulary step probes the phrases the question holds and nothing else. SW2 point 4 asks for the expansion to come from data first — the author keywords and the title n-grams of the records the first round found — before any model is asked for terms (SW2 point 5, not implemented). The one probe behind the thresholds (`.local/quantum-source-comparison-2026-09-18/expand_from_data.py`) learned from 23 *verified* positives; the product has no verified positive when the first round ends and learns from every candidate, most of them off topic.

**Decision:** A provider record carries the authors' own keywords (`ProviderRecord.author_keywords`, stored in `source_versions.author_keywords_json`, migration `0042`); only IEEE Xplore (`index_terms.author_terms`) and PubMed (the `MedlineCitation` keyword lists whose `Owner` is `NOTNLM`) fill it, and a second provider fills the column only while it is empty. After the first round's searches and before screening, an `sw` discovery run opens one code step, `vocabulary_expansion` (no model call). `domain/expansion.py` takes the candidate phrases from the work heads of the scope revision's candidates: two- and three-word title n-grams whose first and last word is neither an English function word nor a general word and whose every word has at least three letters, and each author keyword whole when it has one to four words. A phrase is accepted when the second count is at least 20 **and** at least 20% of the first; a count that could not be read refuses the phrase (`count_unknown`), because a phrase taken from the data has nothing but its counts behind it. At most 8 phrases are accepted and the rest stay `not_probed`. A vocabulary that does not query both the setting and the task block is skipped whole (`single_block`): the only rule measured is "probe against the setting block, widen the task block". With at least one accepted phrase the run compiles a second round of queries — the same setting block AND the accepted phrases as the task block, through `compile_block_queries` — freezes the protocol again as a new revision with the reason `data_expansion` (`protocol:expansion` step; the first record is never edited, SW14.2) and reads those queries with `_search_pages` at the indices after the first round's, with the request allowance derived over both rounds. The second round's query is the added arm alone: the first round's query is not sent again, so its records are not read twice and what the expansion brought in is counted on its own `search_runs` rows. A failed second-round search is recorded and does not pause a run that already searched (D18). The protocol body of that revision carries `expansion` (every candidate with its two counts and why it was kept or refused), `arms: ["keyword_search", "data_expansion"]` and `thresholds.expansion`. `workflow/expansion.py::term_yields` derives, for every term of the protocol and every expansion term, how many candidate works hold it and how many of those the research included; the expansion step stores one dated snapshot of the record counts as `yield_at_expansion`. With no accepted phrase there is no second round, no second protocol revision and no change to the body of D74.

**Dry run (2026-09-21, `.local/sw-expansion-dry-run-2026-09-21/`):** the 1,369 first-round records of the quantum question, titles only (that file carries no author keywords), gave 20 candidates, all of them real terms of the field, and the live probe (40 OpenAlex count requests) accepted 12 and refused 8, every refusal `below_field_share`: "reinforcement learning" (242,184 / 154), "resource allocation" (213,686 / 203), "communication networks" (105,049 / 487), "quantum computing" (66,151 / 1,406), "quantum entanglement", "quantum communication", "quantum memory", "entanglement generation". No threshold was changed afterwards.

**Review (2026-09-21):** the pool the candidate phrases come from leaves out a record that only an expansion arm found. A second discovery run of the same scope reads the same candidates, and with those records in it each run learned from what the last one had added, so the search drifted away from the question run by run. The yield count now matches a term with one substring search on word-padded text instead of comparing token windows, which took over a second for 3,000 candidates on the thread the API answers from.

**Limits:** `sw` researches only; a `legacy` research opens no step and its protocol body is byte-identical to what it was. **Not measured** (slice 24): the thresholds come from one topic's probe that learned from verified positives, and the condition the product runs in — every candidate of the first round, most of them off topic — has never been measured. The field probe shows that a phrase is used in this field, not that it is a synonym of the task block: in the dry run most accepted phrases were other names for the *setting* ("quantum internet", "quantum repeater"), which the covered-phrase rule removes only when the setting terms entered the query as root words, as they do in a run whose counts were read. Author keywords come from IEEE Xplore and PubMed only: OpenAlex's `keywords` are assigned by its own topic model rather than written by the authors, and asking for them would change the `legacy` request and its stored payload digests; Scopus gives `authkeywords` only in the `COMPLETE` view and the product uses `STANDARD`. The IEEE path was read from one live search (2026-09-21, three records): `index_terms` holds `ieee_terms`, `author_terms` and `dynamic_index_terms`, each with a `terms` list, and only `author_terms` is taken — `dynamic_index_terms` are IEEE's machine-generated terms. Author terms arrive in the authors' own casing and may carry trailing punctuation; they are stored as the authors wrote them and are lower-cased and stripped only when a phrase is read out of them. In an engineering research without an IEEE Xplore key the expansion is in practice title n-grams alone, so **the user is advised to obtain a free IEEE Xplore key** (the screen that says so is slice 08); life-science researches get PubMed keywords without a key. The accepted terms enter the second round without being shown to the user: the confirmation screen is slice 08 (SW2.6). Abstract n-grams are not used. The second round runs at most once; there is no third round. The yields are derived and appear on no screen (slice 08 / 20). The conditional model expansion step (SW2.5) is not built. Screening is still cut at `max_candidates` (slice 09, K3), so the records the second round adds mostly queue behind the first round's. Every test is SYNTHETIC and offline; the only live requests were the dry run's 40 counts.

## D75 — Read an `sw` query page by page up to one named read limit, and count what was not read

**Status:** accepted; implemented for the `sw` workflow. **Date:** 2026-09-21.

**Context:** After D73 an `sw` research sends one broad query per provider, but `flow._search` read only `results_per_query` (at most 25) records of it, because no provider adapter paged: each one sent a single request and took the first page. A gate query OpenAlex still counts as manageable may match thousands of works, and the first round SW7 ranked was 1,369 records, so reading 25 of them made the broad query pointless. SW2 point 3 asks for the whole result set of a query to be read up to a named limit, with the remainder counted rather than silently lost.

**Decision:** Every provider search function takes an optional `cursor` argument and returns `SearchOutcome.next_cursor`. Without a cursor the request, its `request_description` and the returned outcome are exactly what they were, so the `legacy` workflow is untouched. `registry.Connector` records how each provider pages (`paging`: `cursor` for OpenAlex and bioRxiv, `offset` for Crossref, Semantic Scholar, arXiv, PubMed, IEEE Xplore, Scopus and CORE, `single_page` for SerpApi), how deep it can be read (`max_reachable`, set only for Semantic Scholar's 1,000) and how long to wait between two pages of one query (`page_gap`, 3.0 for arXiv). On an `sw` research `flow._discovery` calls the new `_search_pages`, which walks one query page by page: each page is its own `run_steps` row (`search:{index}` for the first, `search:{index}:page:{n}` after it, kind `provider_search:{provider}` throughout), its own `search_runs` row, its own stored payload and its own `record_search` transaction, and the next page's cursor is read from the previous page's stored step output, so a resumed run asks for no page twice. Reading stops at the first of: the provider has no more (`exhausted`), `read_total` reaches `rules.SW_READ_LIMIT` (2,000; `read_limit`), the provider's own reachable depth is reached (`provider_cap`), the provider is read one page only (`single_page`), or the page failed (`page_failed`). The stop reason and `unread_count = max(0, provider_total − read_total)` are written on the stopping page, together with `page_number`, `read_limit` and `read_total` (migration `0041`); an unknown provider total leaves `unread_count` NULL. The read limit never drops a record: `record_search` takes `first_rank`, so a candidate's rank is its place in the query rather than in its page, and every record that was read becomes a candidate. Page requests are not charged to `max_provider_requests`; the allowance is derived from the read limit (`flow.extra_page_requests`). A failed page is recorded with its own row and ends that query's read in this run, but leaves the pages it already read and every other query alone; a normal resume does not retry it and "Search again" (`retry_failed_searches_only`) does, continuing from that page (D18). An `sw` protocol body carries `thresholds.search_read.read_limit_per_query`; a `legacy` body is unchanged. The research view carries the five new fields per search row and a `counts["unread"]`.

**Review (2026-09-21):** the derived request allowance now holds, for every page, the bounded retries that page may need (`1 + MAX_RATE_LIMIT_RETRIES + MAX_TRANSIENT_NETWORK_RETRIES`). Retries are counted as requests, and the first version kept only the unpaged run's four spare requests: a read whose pages each succeeded after one 429 paused with `budget_exhausted` and paused again on every resume. An empty page now ends a query's read even when it carries a cursor.

**Limits:** `sw` researches only; a `legacy` research sends the same single request, opens no `:page:` step and leaves the new columns NULL. `SW_READ_LIMIT = 2,000` was picked by hand — above the 1,369-record first round of SW7, below the vocabulary step's manageable total — and was not measured; the measurement is slice 24. **Screening is still cut at `max_candidates`**, so after this slice an `sw` run finds thousands of candidates and screens at most 250 of them, chosen in the order providers happened to arrive; removing that cut is slice 09 (K3), and the "order does not cut" rule of the plan is only complete with slices 07 and 09. Provider totals are not exact — Semantic Scholar and SerpApi report estimates — so `unread_count` is only as true as the total it was computed from. Semantic Scholar stops at the 1,000 records its relevance search serves and SerpApi reads one page, because every SerpApi page is a billed search (D13). How long an OpenAlex cursor stays valid was not measured; a stale cursor appears as a `page_failed` page and its only way out today is a new discovery run — recovering by re-reading the query and skipping known records was not built. Whether records repeat across pages, and whether a provider's ordering shifts between pages, was not measured. Counting requests: page requests, like the count probes of D73, are charged to a derived allowance rather than to `max_provider_requests`. `unread` appears on no screen (slices 08 and 20). `link_records` runs once per page over all of the research's candidates: measured on this machine at 1,500 candidates in pages of 200, the slowest page's whole `record_search` took 0.75 s, of which `link_records` was 0.25 s, 4.03 s in total over eight pages — under a second per page, so nothing was changed about it. Every test here is synthetic and offline: live provider paging was never exercised, and one provider row (IEEE Xplore's 1-based `start_record`) is not stated in that provider's own documentation.

## D74 — Let a model sort the extracted phrases into concept blocks, bounded to the list code found, and keep the rule as the fall-back

**Status:** accepted; implemented for the `sw` workflow. **Date:** 2026-09-21.

**Context:** D73 takes the search phrases from the question by code and decides which block a phrase belongs to from the word standing in front of it. That rule is wrong about a third of the time and wrong in the expensive direction: `with` marks a method position, so the population of a question phrased "… in patients with X" becomes a claim word and drops out of the query, and multi-word outcome cues never survive an intervening word, so the outcome block was empty in all eight measured questions. SW17 (2026-09-21) measured the alternative before it was built: `deepseek-flash` at effort `high`, three runs over the 28 phrases of 8 questions from 8 fields, expected labels frozen before the first call — the rule labelled 19 of 28 correctly and the model 28 of 28, all 28 phrases got the same label in all three runs, and 24 of 24 calls returned valid JSON with no invented, missing or repeated phrase.

**Decision:** On an `sw` research, `flow._vocabulary` opens an optional `vocabulary_labels` model step three times (`vocabulary_labels_1..3`) between `domain/vocabulary.py::extract` and `workflow/vocabulary.py::build_vocabulary`; `extract` is unchanged and `legacy` opens no such step. The step is given the question and exactly the phrase list code extracted (`vocabulary_target`, each phrase with the block the rule gave it), and the phrase list is its allowlist: it labels each phrase with one of `setting`, `task`, `outcome`, `claim`, `exclusion`, `not_a_term` and may add, split, reword or drop nothing. A phrase outside the allowlist, a missing phrase and a repeated phrase are errors (`phrase_not_in_allowlist`, `phrase_label_incomplete`), and schema repair is off for this task (`rules.NO_REPAIR_TASKS`), so an invalid output drops that run instead of being negotiated. `workflow/vocabulary.py::apply_labels` keeps a label that appears in at least two runs; `claim`, `exclusion` and `not_a_term` keep the phrase out of the query, and the rule's own method position is deliberately not kept as a second veto (SW17.4), because in the measurement it cost both corrected cases. The rule stands wherever the model does not answer: with fewer than two runs the whole rule assignment is used and the run searches exactly what D73 searched, and with enough runs a phrase the runs disagree about keeps the rule's label in its record but enters no list. `block_assignment` is `rule`, `model` or, when the user wrote `key_terms`, `user` — the user's terms skip the step entirely (SW2 point 6), as does a list longer than `MAX_LABELLED_PHRASES` (40). The three calls are counted in `max_model_calls` and a budget-exhausted call is a failed optional step like any other. The per-phrase record (rule block, what each run said in canonical order, the block kept, and whether the rule or the model decided it) is stored with the vocabulary step output, and the frozen protocol body carries `block_assignment` and a `block_origin` per term. A step that already succeeded returns its stored output, so a resumed run labels nothing twice. The method package gains `references/vocabulary-labels.md`, so `skill_package_hash` changed from `sha256:1f519582918c3fee14b248c5a2a578983c5fb821ab1c527d1c6abf11ec55982f` to `sha256:69606986e5bed440781eeee7a742f1137cbe44c4cf19a2346ff6268c27abb246`.

**Review (2026-09-21):** a labelling that leaves no `setting` or `task` term at all — runs that agree on no phrase, or that call every phrase a claim or not a term — is not applied when the rule has such a term: the rule's whole assignment stands and the stored labelling says `fallback = labelling_unsearchable`. Before, such a run paused with `vocabulary_empty`, which only the user's key terms could leave. The labelling may correct the first search's query; it cannot take the search away.

**Limits:** `sw` researches only, and no schema or migration changed. The measurement behind this is 8 questions and 28 phrases, one model, one prompt, one wording, and its expected labels were written by a single annotator after seeing the rule's output, so they are not an independent reference. Only one phrase in that set was a genuine claim, so "does a real claim leak into the query" is essentially unmeasured — and it is exactly the risk taken by dropping the preposition veto. Non-English, broken, multi-sentence and keyword-list questions were never tried. Model failure was never exercised against a live connection: 24 of 24 calls passed, so the fall-back path is covered by unit tests alone. Three runs per research are three model calls and nothing measured whether one would do; all 28 phrases were identical in all three runs, so the majority rule changed nothing there. Phrases that weld two concepts into one (`packet size affect energy consumption`) are an extraction fault and are not repaired by labelling. Nothing here was measured against search results: better blocks were not shown to find more relevant work, which is slice 24. There is no screen that shows or corrects the assignment (slice 08), and `key_terms` remains the only way a user can override it. The dry run of this slice made four live `deepseek-flash` calls on two questions; on the first two the model omitted `schema_version`, because the DeepSeek adapter sends no output schema with the request and only the method text carries the envelope rule, so a line naming the four envelope fields was added to the new method file and the two repeated calls were valid.

## D73 — Take the first search's vocabulary from the question by code, probe each term by count, and keep claim words out of the query

**Status:** accepted; implemented for the `sw` workflow. **Date:** 2026-09-21.

**Context:** The search words of every research came from the `search_plan` model step (D44) and code only compiled the query. So no search ran while the model connection was down, the same question could give different words in two runs, and the words of the claim under test could enter the query — SW1 measured an 11% answer change on identical input, and SW1.3 names claim words as the thing to keep out. SW2 was accepted as design direction on 2026-09-18 and had not been built. Slice 04 of the search-workflow plan was split: this is 04a.

**Decision:** On an `sw` research, `flow._discovery` runs a `vocabulary` code step instead of the `search_plan` model step; `legacy` keeps that model step line for line. `domain/vocabulary.py` reads the question with the hand-written lists in `domain/vocabulary_words.py`: a question is read as English unless something says otherwise (a hint decides when there is one; a non-Latin script, accented letters together with an English function-word share below 0.2, or eight or more words with no English function word at all mean it is not), the asking frame is stripped, the text is split at function words, punctuation and cue words, and a run of content words is a candidate phrase whose leading and trailing general words are trimmed. The cue immediately before a phrase names its block: `in`/`on`/`for`/… setting, `using`/`with`/`by`/… method, `to reduce`/`effect on`/… outcome, `not`/`without`/… excluded, nothing or `of` task. A method-position phrase becomes a claim word and the method block stays empty, so "a claim word is never queried" holds by construction rather than by a rule. The outcome block is stored and not queried. A question that is not English and carries no key terms returns nothing and the run pauses: code does not translate. `scope_revisions.key_terms` (migration 0040, optional in the create-research and revise-scope bodies, 500 characters) is the user's own English terms — `;` between blocks, `,` between synonyms, a `claim:` or `not:` group for the side lists — and replaces the extraction entirely, recording `block_assignment = "user"`.

`workflow/vocabulary.py::build_vocabulary` probes each setting and task phrase and each distinctive word of a multi-word phrase with `providers/openalex.py::count_works`, a count-only request (`per_page=1`, `select=id`, `meta.count`) whose failure gives `None` and stops nothing (D18). A phrase no record holds is dropped; a phrase whose count could not be read enters whole, because unknown is not small. A term's root is its least frequent word and every term starts in the query as its root (SW3.5); when the gate query — the setting OR-group AND the task OR-group — exceeds `MANAGEABLE_TOTAL`, the term with the widest root becomes its phrase and the gate is counted again, until the gate is readable or no term is left to narrow. The counts decide, nothing else. `MAX_PROBES` bounds the count requests; terms left unprobed enter as phrases. A term whose queried form exceeds `VERY_LARGE_COUNT` is marked `and_only`, and a single-block vocabulary of nothing but such terms is `too_broad`. `providers/query_compiler.py::compile_block_queries` (`deixis.query_compiler.v4.blocks`) then writes one query per provider, OR inside a block and AND between blocks, reusing the existing per-provider syntax and rules; terms are trimmed from the end of the last block first, every block keeps one, and what was dropped is recorded on the query. The step's output — vocabulary, queries and compiler version — is stored, so a resumed run repeats no count request and searches the same queries. Three pause reasons stop the run for a scope revision: `key_terms_needed`, `vocabulary_empty`, `vocabulary_too_broad`. The frozen protocol body fills `concept_blocks`, `claim_words`, `exclusion_words`, a per-term `vocabulary` with its counts, and `thresholds.vocabulary`; those counts are the ones the first run read and are never re-probed. Passage ranking reads the queried terms and the outcome terms where it used to read the plan's concepts, and not the claim words.

**Limits:** `sw` researches only. Nothing here was measured; the measurement is slice 24. Block assignment is done with preposition rules, is unreliable, and there is no screen to confirm or correct it (slice 08): a dry run on the two campaign questions put eight phrases of the answer-instruction sentences into the task block and read "by simulation" as a claim. The extraction reads English questions only; another language needs the user's English terms and no screen asks for them. A question in another language written without accents and holding a word that is also an English function word is read as English; only the count probe stands behind that, and a foreign word that OpenAlex counts would be searched. The first language rule (a plain 0.2 share) sent a plain English question with two function words in eleven, and any keyword list, back for key terms; the review replaced it. The method block is empty, so every phrase in a method position counts as a claim and a question whose subject is a method loses it. The general-word list is a short hand-written list and the threshold for reading a question as English, `MANAGEABLE_TOTAL`, `VERY_LARGE_COUNT` and `MAX_PROBES` were all chosen by hand. A count shows a term occurs in the literature, not that it is the right term. The probe order is the setting block then the task block, each in question order, not the question's own interleaving. ## D72 — Link records of one work by title, authors and abstract together, merge only a preprint with its published record, and keep every link undoable

**Status:** accepted; implemented for `sw` researches. **Date:** 2026-09-20.

**Context:** Two records became one only on an equal DOI; without one, a preprint and its published record were put in a single work solely when their titles matched exactly and the first author agreed (D48, `store.same_publication`), and every other similar pair was stored as a bare "may duplicate" flag with no rule, no score and no way back. SW6 points 1 to 3 and 5 to 9 were accepted as design direction on 2026-09-18 and measured without a model call on the 2,055 DOIs of the SW3 source comparison (`.local/quantum-dedup-2026-09-18/`). Slice 02 (D71) had closed.

**Decision:** `domain/record_identity.py` decides what two records are to each other as a pure function: no database, no model, no embedding, so the same two records always give the same verdict. It normalises a title by stripping HTML and LaTeX remnants and accents, compares character trigrams by Jaccard, reads a record kind (`preprint`, `published`, `artifact`, `notice`, `unknown`) from a short list of repository DOI prefixes and notice title prefixes, and compares author surnames after handling "Last, First", reversed name order and diacritics, treating an empty or placeholder list as unknown rather than different. `classify_pair` walks one ordered table of sixteen rows and returns a `Verdict` carrying the link kind, the rule that decided, the three scores, the year gap and, for an artifact or a notice, which record is the parent. An automatic merge needs title similarity at or above 0.85, agreeing authors, abstract similarity at or above 0.8 and kinds preprint plus published or preprint plus preprint; with an abstract missing, identical normalised titles are enough for the same kinds. A preprint that names the published DOI merges whatever the titles say, as D48 already does. Two published records never merge: an alike pair is `extended_version`, a looser one `related_suspected`. Agreeing authors with an agreeing abstract but a lower title score is `probable_version`, which waits for the human queue. A year gap above five blocks a merge and is recorded. Migration 0039 adds `record_links`, keyed by the ordered pair, with the rule, the scores, the source (`text` or `arxiv_doi`), the merge flag and the undo payload; it carries no research identifier, because works are library-wide (D46). `workflow/links.py` writes it: a repeated verdict adds no row, a stronger verdict closes the earlier one as `superseded`, a merged link is never weakened by a later reading, and a link the user undid is closed as `undone` and never made again by a later search. Before any merge, the records of both works are checked and the merge is refused when it would put two published records with different DOIs in one work; the refused pair is stored as `related_suspected` under the rule `work_already_has_published`. `store._join_works`, split out of `_join_if_same_publication` without changing its behavior, returns what the undo needs, and `undo_link` re-opens the dropped work with its own identifier and creation time, moves back only the versions this link moved, restores the short source key when no other work has taken it and otherwise assigns a new one (D59), and settles the head of both works. `Store.record_search` calls `links.link_records` instead of `_flag_suspected_duplicates` when the research's current scope says `search_workflow = 'sw'`; a `legacy` research runs exactly the path it ran before. `link_records` compares the records just found against every candidate through an inverted trigram index, reads abstracts only for the pairs that reach the rule, and processes pairs in a fixed order (the author-supplied DOI first, then the closest titles, then the identifier pair). `build_protocol` writes the five thresholds into an `sw` protocol body under `thresholds.record_identity`; a `legacy` body is unchanged. `tests/determinism_stages.py` replays one search of ten SYNTHETIC records under two shuffles.

**Limits:** Only `sw` researches take this path. Works are library-wide, so a merge made in an `sw` research is visible in a `legacy` research holding the same records, exactly as D48's merges are today. The thresholds 0.85, 0.8 and 0.6 and the author overlap of 0.5 were chosen by hand on one topic of records that all had a DOI; records without one, the case that leans hardest on title matching, were never measured, and nothing is measured inside the product — that is slice 24. Pairs below 0.6 title similarity are not examined at all, so a version whose title changed completely is found only by the external link of slice 05 (SW6 point 4), which is not in this slice. The kind rule is a short prefix list and will miss other repositories and other notice wordings; a notice is recognised only when its prefix is followed by `to`, a colon or the end of the title, so "Retraction of …" reads as an ordinary paper. Which of two published records is the conference paper and which the journal article is not stored, so full-text adjudication preferring the journal article (SW6 point 5) waits for slice 12. Counting an `extended_version` pair once in work-level totals is implemented nowhere (slice 20). Artifacts and notices stay in the candidate list and are only attached to their paper; leaving the list needs a reason code from slice 09. A work's head is still chosen by D48's narrow preprint test, so a non-arXiv preprint DOI counts as published and can head a work. If two published records both want the same preprint, the first pair processed takes it and the second is refused; that one case depends on arrival order and is deliberately absent from the determinism stage. Links and undo are reachable from no endpoint and no screen, and an `sw` research shows no "may duplicate" mark at all. Undoing a merge does not take back the selection the merge copied to the new head, and it re-opens no work when every record it moved has since been deleted or moved on. An undone merge is remembered only by the `sw` rule: a `legacy` research holding the same preprint and published record joins them again through D48, which reads no link. The review read the rule's verdicts on the 127 title pairs of the second topic (`.local/sw-slice03-pairs-2026-09-20/pairs.csv`, authors and years from OpenAlex): the 4 merges are a preprint and its published record or two preprints of one paper and look right; most of the 23 `extended_version` pairs are not a conference paper and its journal article but one paper registered under two DOIs (a versioned repository DOI, a journal that changed its prefix, a proceedings entry listed twice), which stay two works and are screened twice until a link from slice 05 or the count in slice 20 handles them; a front-matter pair ("Table of contents", no authors) is stored as `related_suspected`. Tests run on SYNTHETIC records: they show link behavior, not identity accuracy.

## D67 — Pace Semantic Scholar requests across endpoints

**Status:** accepted; implemented. **Date:** 2026-09-18.

**Context:** Semantic Scholar states that its introductory API-key limit is [one request per second across all endpoints](https://www.semanticscholar.org/product/api). The previous citation-graph pilot used standalone calls and saw HTTP 429; keyed follow-up calls spaced by much more than one second still saw HTTP 429, so pacing is necessary API compliance but not a demonstrated cure for that failure.

**Decision:** Every product request to `api.semanticscholar.org` through the shared provider `send` path uses one process-wide serial gate, for search and any later citation/reference endpoint. The gate waits at least 2 seconds after the preceding attempt finishes before starting another, including 429 retry attempts. **Evidence and limits:** Synthetic concurrent-client tests check that two Semantic Scholar endpoints cannot overlap, their starts are spaced, and a 429 retry uses the same gate; the provider matrix remains passing. The gate coordinates this DEIXIS process, not independent processes or external tools sharing the same API key. A live probe on 2026-09-18 with the configured key put six searches through at each of three intervals: 1.05 s returned one HTTP 200, 2 s returned four, 5 s also four; a request with a bogus key and a keyless request in the same minute were both throttled while the keyed request succeeded, so the key is honored and the account is not blocked. Two seconds reduces the failure rate but does not eliminate it, and the live service was not restarted for this change.

## D62 — Keep the text layer on Marker pages and read only lines with math from the image, checking inline math against the text layer

**Status:** accepted; implemented. **Date:** 2026-09-17.

**Context:** Marker (D52) read the library at about 60–75 s per selected page, so the one-time read of the stored library was estimated at 9–11 hours. Most of that time is Marker's OCR builder re-reading whole math pages from the image, because its layout and OCR-error checks mark those pages' text layer as bad. GPT-5.6 Sol High, consulted on alternatives, proposed Marker's fast settings plus a targeted inline-math pass, with gates set before measuring. Docling 2.128 was tried: its formula model refuses the Apple GPU and took about 300 s per page on CPU; granite-docling through MLX took 22.7 s for 5 pages but mixed text from the neighbouring column into equations. The owner chose the targeted pass after seeing its measurement.

**Decision:**

- On a page with a text layer, Marker keeps the text layer (`LineBuilder_disable_ocr`, `TableProcessor_disable_ocr`) and its OCR builder is replaced (`marker_runner.inline_math_builder`). The builder detects visual lines, takes those with a math signal (a math font, a sub- or superscript, a math symbol, or a character DEIXIS found in a math font or as a script with PyMuPDF, `math_reader.inline_math_marks`), reads them from the page image in math mode with at most 256 tokens, and writes a math segment only when `inline_math.rewrite` accepts it: prose must match the text layer in order, and the segment must use exactly the text-layer letters and digits it replaces (stacked scripts either way round; letters of symbol fonts with broken Unicode masked). A failed segment keeps the text layer. Display equations are read by Marker as before.
- A page without a text layer is read with Marker's default settings in a second conversion of the same request.
- The extraction version stays `…+marker-1.10.2-math-v2`: PDFs already read are not read again. `math_json.inline_math` is true for reads made this way.

**Evidence:** Measured on 11 pages of 4 papers (M1 Pro, 17 September 2026), against 138 inline expressions hand-transcribed from page images (sample and scorer in ignored `.local/math-ocr/`): Marker default 852 s and 72% right, 1 converted wrong; fast settings alone 126 s and 0%; the first targeted version 310 s, 38%, 4 wrong; the adopted version 448 s, 69%, 1 wrong (a scorer artifact: outer brackets). On display equations the fast path matched or beat the default in the cases compared (4–5 better, 1 worse: p_{d_I} read as d_1). Sol's gates were not all met: at least 80% right (the default itself scores 72%), no invented inline math (met on this sample), and at most 2.5× the fast time and at least 2× faster than the default (3.6× and 1.9×). Unit tests: `tests/test_math_reader.py` covers the accept/reject rules (changed letter, prose mismatch, ordering choice, image past the line, symbol-font masking and bracket widening) and the request carrying math marks and pages without text through a fake runner. Backend suite: 563 passed, 2 failed (the memory-limit extraction test that already failed on this machine, and a skill-package test that passes when run alone while another session was editing). ## D47 — Extract PDF text by layout blocks and re-extract every PDF in use

**Status**: accepted
**Date**: 2026-09-16

**Context**: PDF text was the flat page text in MuPDF order (and pypdf's for 56 older files). On an IEEE article the first-page author affiliation footnote sat inside a sentence of the introduction ("challenges in the first T. N. Nguyen is with the Department…"), the arXiv identifier stamped along the margin and page numbers ran into body text, and section headings were not set apart. ## D45 — A replaced PDF or a new text extraction adds passages and shadows the old ones; old evidence keeps pointing at what it read

**Status**: accepted
**Date**: 2026-09-16

**Context**: P5's acceptance condition says a version or index change must not break earlier evidence (implementation plan §9, T03). Evidence links point at immutable passages, but the code had no notion of replacing a file or re-extracting one. A probe on synthetic records showed: `upload_to_source` adds a second PDF with different bytes beside the first; with two copies of the same text, a cell extraction StepInput carried every passage twice (`passage_scope` 4 of 4 for a two-page text) and `_retrieve` chose two passages with the same text and skipped the whole-small-document path; `_insert_passage` returned the old passage ID and old `extraction_version` for the same text written under a new version. Read-only counts on the live library: 67 PDFs in use, none of them twice on one source version; 56 extracted by pypdf and 11 by PyMuPDF `chunks-v1`, none by `chunks-v2` (D43); 44 source versions with a PDF are used by more than one research. Design note: `docs/product/p5-slice2-source-versions.md`. The owner chose the recommended option on all seven open questions.

**Decision**:

- A source version has at most one PDF in use. Adding a PDF where one is in use answers 409; replacing is a separate action. Replacing adds the new file as a new asset (new passage IDs even for identical text) and, in the same transaction, marks the old asset removed with `removal_reason = 'replaced'` and the new asset's ID. Removing a mistaken file records `wrong_file`. Assets belong to the library, so a replacement applies in every research that uses the source; the confirmation shows the affected researches, cells and quotes.
- Re-extraction writes the same asset's pages under the new `extraction_version`, which becomes part of the passage deduplication key, so identical text gets a new passage ID carrying its own version. Each extraction is recorded per asset (`current`, `superseded`, `rejected`). A new extraction becomes current only if its status is not worse, its page count is equal and it has text on no fewer pages; otherwise it is `rejected`, the old text stays in use and the reason is shown. This check guards against visible loss; it does not show the new text is more accurate.
- A passage is shadowed when its asset was removed or its extraction is not the asset's current one. Shadowed passages are never given to a model step again (fill, recheck, answer, column suggestions, semantic ranking) and still resolve by ID. Nothing is deleted, rewritten or moved: cell revisions, evidence links, answers and reviews keep the passages they recorded (D37).
- Views compute an evidence status per passage: `current`, `pdf_removed` (text only), `pdf_replaced` (text, and the old PDF read-only in a research whose evidence cites it) and `text_superseded` (text and the same PDF). Cells split `pdf_withdrawn` into these marks; `include_stale` fills also plan cells whose evidence is shadowed, as proposals only. An answer shows `source_text_changed` when a passage its StepInput was given is no longer current; replacement and re-extraction do not bump the selection revision.
- Re-extraction is started by the user: per source, or in bulk from `deixis reextract` with a `--dry-run` that writes nothing. On the live library it runs first on a copy, and the bulk run needs the owner's approval.
- Replacement and re-extraction answer 409 while any research using the source has a queued, running or pause-requested run.
- The chunker does not change in this slice. Quotes that cross a chunk boundary stay a separate decision; page-relative character ranges (`payload_ref`) are kept so a later version can locate a quote across adjacent chunks.

**Evidence**: Migration 0027 (`asset_extractions`, `removal_reason`, `replaced_by_asset_id`, the one-PDF-in-use index). `Store.reextract_asset` and `deixis reextract` were written under D47; this decision adds `Store.replace_asset` and `asset_impact`, `PUT …/assets/{id}`, `POST …/assets/{id}/extractions`, `GET …/assets/{id}/impact`, the computed `evidence_status`, cell flags `pdf_removed`/`pdf_replaced`/`text_superseded` (replacing `pdf_withdrawn`), the answer's `source_text_changed`, and the Sources, report, cell and passage labels. Tests with synthetic records and the scripted fake adapter: `tests/test_source_versions.py` (migration from 26 and its refusal with two PDFs in use, the new deduplication key, one PDF in use, shadowed passages, re-extraction), `tests/test_asset_replacement.py` (after a replacement with identical text a recheck StepInput and `_retrieve` carry each text once — the probe before this change found every text twice; old cell evidence unchanged; refusals for the same file and an active run; API and CSRF; backup/restore keeping both files, both extractions and the old evidence; deleting another research keeps a replaced file that is still cited), `tests/test_evidence_status.py` (each cell mark, a stale fill that only proposes, answer and passage status, the old PDF opening only where cited). Backend suite 452 passed, 1 failed (the known memory-limit test). Web build passes; lint adds no warning. Playwright: a new case replaces a cited PDF through the confirmation (1 research, 0 cells, 1 quote) and opens the quote on the previous file's text and PDF at desktop width and 390 px; in two full runs the main flow stopped once at case B (a label the committed source panel redesign removed) and once at case C (while D46–D48 version grouping was in progress in the same working tree), neither in code this change touches.

**Limits**: Evidence tables' new labels are covered by backend tests and a build, not by a browser run. The replace confirmation uses the shared destructive-style dialog although nothing is deleted. The equal-page and text-page check is an unmeasured default. Replacing a file does not check that the new file is the same publication version; that stays the user's responsibility as in D33. The same file recorded under two different works (seen twice on the live library) is an identity-matching problem outside this decision.

## D44 — Compile provider queries from the search plan's concepts instead of letting the model write them

**Status**: accepted
**Date**: 2026-09-16

**Context**: The `search_plan` model step wrote every provider query string itself; code only checked provider syntax and sent failures back for repair. In the live run `res_WXhsHdb9BaYOSUFZMofB` (an entanglement routing question) the model wrote queries such as `"quantum network" AND (decoherence OR "quantum memory" OR "time-dependent")` that dropped the discriminating core term. Their provider totals were 1.9K and 616 while only the top 25 of each were read, so those searches mostly added records off the question to screening (the owner's reading of the run, not a counted relevance judgment). The same plan held a good concept vocabulary (roles and synonyms), which was used only for BM25 source ordering. TODO.md's deferred "Search query generation" section had named moving query composition into code as the fix for a query-side miss; the owner chose to implement it now.

**Decision**:

- `SearchPlan` becomes `deixis.search_plan.v2` (`contracts/research/search-plan.schema.json` bumped in place, as the answer draft went from v2 to v3). The model returns `question_interpretation`, `concepts`, `providers` (an ordered subset of `enabled_providers`), `scope_boundaries` and `search_rationale`; `queries` is gone and there is no free-text query extra. A concept's `synonyms` are its search terms, in the literature's language; its `label` is display text in the research language and is never searched (a first compiler version searched labels too, and a live plan with Turkish labels gave Turkish Semantic Scholar and Crossref queries). `contracts._check_search_plan` asks for a repair when the plan has not exactly one `core` concept (`core_concept_count`), the core has no synonyms (`core_without_synonyms`), names a provider that is not enabled or twice, names only SerpApi, or yields no compilable query (`no_compiled_query`). The per-query syntax repair round is removed.
- `providers/query_compiler.py` (`deixis.query_compiler.v1`) builds the queries. Families are the non-core concepts with at least one synonym; `adjacent_field` concepts are used only when no other family is given, because they name another field's words for the same idea rather than a condition to pair with the core. Family terms that repeat a core term are dropped; with no family, the query is the core group alone. Each query is `core group AND family group` in the provider's form: OpenAlex, bioRxiv, IEEE Xplore and CORE boolean; Scopus the same inside `TITLE-ABS-KEY(...)`; arXiv with `abs:` on every term; PubMed with `[Title/Abstract]` on every term; Semantic Scholar and Crossref the plain words of the first core synonym and the first family synonym (at most eight); SerpApi the quoted first core synonym before the family's OR chain, at most one query. Multiword or non-word terms are quoted; quotes, parentheses and brackets are removed from terms. A query uses at most six terms (five operators), the core keeping up to two when its family has more; terms are trimmed from the end of the family group, then the core group, until the query passes `query_rules.query_issues` (syntax, unparenthesized OR, OpenAlex shape) and 300 characters, otherwise it is skipped. Queries take the next family and the next provider that family has not had, round-robin, skip repeats of a provider-and-text pair, and stop at the run's `max_provider_requests`. Each carries a rationale naming the core and family labels, shown under the query.
- `flow._discovery` compiles once after the plan step succeeds and stores the queries and compiler version in that step's output, so a resumed run searches the stored queries and repeats no model call. A v1 plan's model-written queries are still searched when an old run is resumed, and `views.research_view` shows query text and rationale for both versions. The OpenAlex OR and shape checks moved from `contracts` to `query_rules`.
- The method file's search-plan section now asks for vocabulary, one discriminating core concept and the provider choice; synonyms are to be written in the literature's language, best search term first; the per-provider syntax prose and the date-limit instruction were removed (the compiler adds no date limits).

**Evidence**: `tests/test_query_compiler.py` (the concepts of the live plan `run_xhrRwLM8U9xIG3LkBm1Z`, Turkish labels and English synonyms: every query for all ten providers contains a core synonym, no label, and passes the provider rules; exact forms, round-robin order under a budget, one SerpApi query, family selection, trimming), `tests/test_contracts.py` (one core concept with synonyms, no compilable query, provider checks), `tests/test_provider_flow.py` (stored queries searched after a pause, a v1 plan still shown and searched). Backend suite: 424 passed, 1 failed (the pre-existing memory-limit test named in D43). Only synthetic fixtures ran; no model or provider call was made.

**Limits**: No recall measurement has been done. This is a structural guard against queries that drop the core term, not a shown improvement in which papers are found; the six-term and round-robin rules are unmeasured choices. A model that names a broad field as the core still gets broad queries. No behavior case has been run with the new method wording. Trimming keeps the first synonyms of a concept, so synonym order now matters, and a model that writes synonyms in the question's language still gets queries in that language. The "wide fetch, local rank" branch of TODO.md stays deferred.

## D37 — Keep evidence table cells as append-only revisions that only the user can change

**Status**: accepted
**Date**: 2026-09-16

**Context**: P5 requires an editable evidence table where a human edit is never overwritten, "Recheck this cell" produces a new proposal tied to the right source, version and passage, and version or index changes do not break earlier evidence (implementation plan §6.2, §9; api-and-data "Priority requirement"). The design note `docs/product/p5-slice1-evidence-table.md` left six questions open. The owner asked Claude to answer them (2026-09-16).

**Decision**:

- A table belongs to one research. Its rows are listed explicitly (`table_rows`): a new table starts with the included sources, and the user adds or removes the research's sources. Narrowing the Sources selection, as in D34, does not shrink the table.
- Columns carry a short name, an instruction written for a human annotator and an answer format: options, number and unit, yes/no, or short text (at most 500 characters). A changed definition is a new column revision; values made under an earlier revision stay and read as `stale_column`. Columns can be saved as a library-wide template.
- A cell is an append-only list of revisions (`model_fill`, `model_proposal`, `system_fill`, `human_edit`, `accept_proposal`, `dismiss_proposal`) and points at the revision it shows. Revisions, their evidence links and column revisions are immutable; only permanent deletion of the research removes them. A trigger refuses evidence from any source version other than the cell's own, including another version of the same work.
- A model result becomes the value only of an empty cell and only when it is structurally valid. Every other model result, including every recheck result, waits as a proposal; only the user's accept or dismiss decides it. Accepting copies the proposal's value, reading depth and evidence (with the StepInput that gave each passage) into a revision authored by the user.
- Human writes carry the cell version their screen showed and are refused with 409 when it changed. Creates and cell writes accept an `Idempotency-Key`; a replay returns the same record.
- Cell states stay distinct: `value` (with linked evidence), `not_verified` (a value without linked evidence), `unknown`, `not_reported`, `not_applicable`, `inaccessible`, `not_found_in_inspected_scope`. A source with no stored text gets `inaccessible` from the system without a model call.
- For the model step still to be built: a recheck does not show the model the current human value; no cell gets `full_text` reading depth and the model may not write `not_reported` until OCR and page checks exist (T10); fills run one call per source, at most 25 sources and 8 columns per call.
- Table work runs as runs of kind `table_columns`, `table_fill` and `cell_recheck` (stage `extraction`). Migration 0019 rebuilds `runs` for the new kinds; `db.migrate` runs a file whose first line is `-- deixis:foreign-keys-off` with foreign keys off and checks them before the commit.

**Evidence**: `tests/test_evidence_tables.py` (20 tests) covers the `runs` rebuild on a database at migration 18 (rows, idempotency key and foreign keys kept), rollback of a foreign-keys-off migration that leaves an orphan, T09 scenarios a–i and l with synthetic model outputs, superseded and invalid proposals, immutability and the same-source trigger, explicit rows, a withdrawn PDF whose evidence still resolves, answer-format validation, the API (versions, idempotency, CSRF, cross-research 404, templates, trash), permanent deletion and backup/restore of a table with a human edit. **Status**: accepted
**Date**: 2026-09-15

**Context**: The owner asked (2026-09-15) whether text embeddings affect the source list's "Most relevant" order. Scores are not shown as percentages or qualitative bands because their scale depends on the embedding model.
- Only this order reads the score. Screening decisions and answer retrieval do not. It shows closeness to the question, not that a source is relevant or supports a claim.
- A failed embedding request is recorded as a failed `similarity:<model>` step and does not stop the run.

A research-level selection revision is stored with answer StepInputs and answers, so later selection changes mark answers `stale_selection`. Model-session and search results commit in the same transaction as their step outcome, and answers and screening proposals are applied at most once per step. The package hash covers only the instruction files loaded into model steps. The Codex process receives an allowlisted environment without provider keys. The API accepts only loopback peers, and attachments only when the source scope includes them.

**Impact**: Migration 0003. Answers created before it keep question-only applicability. The version-family source model, locator assertions inside claim text, upload/extraction memory limits and DNS-rebinding protection remained open review items (see D6).

## D4 — Attach an open-access PDF only to the source version it belongs to

**Status**: accepted  
**Date**: 2026-09-14

**Context**: In the first live run, OpenAlex described a record's primary location as `publishedVersion` while its best open-access PDF was a `submittedVersion` manuscript. DEIXIS attached that manuscript to the published record, so a PDF page citation was labeled with the wrong version.

**Decision**: Store the open-access location's version (`source_versions.oa_pdf_version`, migration 0002) separately and fetch the PDF only when it equals the record's `version_label`. A PDF of another version is shown as "different version · not used" until separate version records exist. Search uses OpenAlex `search.title_and_abstract`; plain `search=` also matches full text and returned off-topic records in probing.

**Impact**: Fewer PDFs are retrieved. Records created before migration 0002 have no stored OA version, so their already-attached PDFs are not re-checked.

## D3 — Run Codex in a DEIXIS-owned Codex home with explicit models

**Status**: accepted

**Context**: Probing showed that the user's `~/.codex/AGENTS.md` was loaded into app-server threads despite `project_doc_max_bytes=0`, and that the resolved default model differed between runs.
