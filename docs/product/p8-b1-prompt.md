## Decisions taken where the design is open (use these; never ask)

1. **Names.** Task type `owner_review`; contract name `OwnerReview`, file `contracts/research/owner-review.schema.json`, version `deixis.owner_review.v1`; migration `0064_owner_reviews.sql`; package `backend/deixis/workflow/review/` with `snapshot.py`, `stale.py`, `store.py` and a read-only facade `reader.py`. Constants `REVIEW_TASKS = ("owner_review",)` in `contracts.py`. The model's evidence field is `passage_handle` and the quote field is `anchor`, as in the design; after resolution the backend stores them as `passage_id` and `anchor_text` (below).
2. **Target refs are snapshot-local labels, not D12 handles.** `claim_ref`: an answer claim's `label` (`c1`) or a report claim's `claim_key` (`III.2`); `section_ref`: the report `section_id` (`III`); `element_ref`: a candidate element label `e1..eN` (B8 fills it; the schema and checks accept it now). The snapshot maps each ref to its record ID (`claims.id`, `report_claims.id`, `report_sections.id`); building a snapshot **fails closed** (a named exception, nothing stored) if two claims of one report share a `claim_key` or two answer claims share a label. Only passages, sources and cells use D12 handles (`psg_P`, `srv_S`, `cel_L`); add `review_citation_handles`, `REVIEW_INPUT_ID_FIELDS` and `REVIEW_OUTPUT_ID_FIELDS` next to the report equivalents and number passages first, then sources, then cells, as `report_citation_handles` does.
3. **`review_input` is a new optional top-level property of the StepInput schema** (closed object, present iff `task_type == "owner_review"`, absent otherwise, checked in `check_step_input` with a `review_input_mismatch` issue, and no other `*_target` field and no `candidates` allowed with it). Fields, every string and array bounded (`maxLength`/`maxItems`): `review_snapshot_id` (`^rvs_[0-9A-Za-z]{8,40}$`), `target_kind` (`answer`, `report`, `candidate`), `focus` (`source_support`, `assumptions_and_consistency`), `owner_note` (string up to 500 characters, or null), `group_index`, `group_count` (`1 <= index <= count`), `claims[]` (`claim_ref`, `section_ref` or null, `text` (up to 4000), `text_origin` `model` or `human_edit`, `support_type` `source_stated` or `analyst_inference`, `citations[]` of `{passage_id | null, cell_id | null, anchor_text | null}` with exactly one of the two ids), `sections[]` (`section_ref`, `title` text or null, `status`), `elements[]` (`element_ref`, `position`, `text`, `kind`), `cells[]` (`cell_id`, `column_id`, `source_id`, `state` as the cell states, `value_text` string up to 4000 characters or null, `evidence[]` up to 8 of `{passage_id, quote up to 600}`) and `columns[]` (`column_id`, `name` up to 200, `answer_format` enum): review-specific shapes with their own bounds, **not** the `report_target` shapes (those are unbounded in places and must not change). The cell `value` is rendered to compact JSON text; `review_step_input_parts` raises a named `ReviewInputTooLarge` if a rendered value exceeds the bound (B2 records the group as not reviewed; nothing is truncated silently), `candidate_statement` (text or null; B8 may extend the candidate part, nothing stored depends on it yet), and `passage_ids[]` (the passages in this call, which must equal the top-level `passages` and `allowlist.passage_ids`). The `allowlist` gains optional `claim_refs`, `section_refs`, `element_refs` arrays (patterns as in decision 2) beside the existing optional `cell_ids`. For `owner_review` the allowlist may hold only `candidate_ids` (empty), `source_ids`, `passage_ids`, `cell_ids`, `claim_refs`, `section_refs`, `element_refs`, and the ref lists must equal exactly the refs present in `review_input` (a typed allowlist: a section ref is never accepted where a claim ref is expected). `target_kind` answer allows claims only (`section_ref` null, no sections, no cells); report allows claims, sections, cells, columns; candidate allows elements and `candidate_statement`. Citation integrity is checked in `check_step_input` and each item has a negative test: every `citations[]` item carries exactly one of `passage_id`/`cell_id`; a cited passage is in `passages` and in `allowlist.passage_ids`; a cited cell is in `review_input.cells` and in `allowlist.cell_ids`, its `source_id` is a shown source and in `allowlist.source_ids`, its `column_id` is in `review_input.columns`; every cell evidence passage is a shown passage; `review_input.passage_ids` equals `passages` and `allowlist.passage_ids`; passage count at most 48 per call (the answer path's limit); refs unique. `owner_note` that is empty or only whitespace is refused (the schema allows null; code rejects blank, as design section 4 says) and one over 500 characters is refused by the schema.
4. **Output contract `owner-review.schema.json`** exactly as design section 4: closed, every property required, nullable where optional, strict-compatible (`contracts.strict_compatibility_issues` is empty, also on the wire schema from `step_output_schema`). `findings[]` (max 50): `finding_handle` (`^f[0-9]{1,3}$`), `target_ref {kind: claim|section|candidate_element|whole, ref: string|null}`, `kind` (the seven values), `evidence[]` (max 5 of `{passage_handle, anchor}`), `rationale` (max 1200), `possible_impact` (max 600), `suggested_fix` (max 1500 or null), `uncertainty` (max 600). `supported_points[]` (max 100): `target_ref`, `evidence[]` with `minItems 1`. `context_limits[]` (max 50): `{code: passage_missing|only_abstract|not_enough_context|outside_provided_scope, target_ref, text (max 600)}`. Echo fields (`schema_version` const, `step_input_id`, `scope_revision`, `skill_package_hash`) and `notes` (max 1200). An empty `findings` list is valid. `anchor` max 600 characters like `quote` elsewhere. "Located" for owner review is **stricter than for answers**: the design asks for an exact contiguous quote with the answers' normalization, and `locate_anchor` also returns `kind == 'fuzzy'` (a fuzzy match can differ from the passage by a word: a quote with `increases` was matched to a passage saying `decreases`). Owner review calls `locate_anchor` unchanged (do not change it, answers, cells and candidates depend on it) and accepts only a result whose `kind` is `exact` or `normalized`; a `fuzzy` result is the distinct issue `review_anchor_not_exact`, a `None` result is `review_anchor_not_in_passage`. The backend stores the passage's own words as `anchor_text` and the kind as `anchor_match`. One test shows a one-word-changed quote is refused with `review_anchor_not_exact`; the decision text records this as a deliberate tightening of the answers' rule, consistent with D180 section 4, and says a located anchor shows the quote is in the passage, not that the finding is right.
5. **Code checks `_check_owner_review`** (all through `Issue`, so the existing bounded repair path carries them): `target_ref.kind` must match the target kind of the StepInput (answer: `claim`/`whole`; report: `claim`/`section`/`whole`; candidate: `candidate_element`/`whole`); `ref` is null exactly when `kind == whole`; `ref` is in the matching allowlist (`claim_refs`/`section_refs`/`element_refs`) of **this call**; every `passage_handle` (after D12 resolution) is in `allowlist.passage_ids`; every `anchor`, in findings and supported points, is located by `locate_anchor` in the stored text of that passage with kind `exact` or `normalized` (decision 4); a repeated `finding_handle` is rejected; kinds `unsupported`, `partially_supported`, `overstated` need at least one evidence item; other kinds may have none; repeated `(target_ref, passage, anchor)` inside one finding's evidence is rejected; the generic UTF-8 scan `_check_utf8_text` and the diagnostic escaping at the end of `validate_model_output` run for `owner_review` as they do for candidate tasks (an escaped lone surrogate such as `"\ud800"` in `rationale`, `notes` or `suggested_fix`, or in an extra key of a schema-invalid draft, must become a `text_not_encodable` issue and a storable diagnostic, not an error at SQLite write time; test both); the same checks run best-effort on a schema-invalid draft (add `OwnerReview` to the list of code paths in `_semantic_checks_best_effort` as the other review tasks are). The code never applies `suggested_fix`. Issue codes are new and distinct (e.g. `review_target_kind_mismatch`, `review_ref_unknown`, `review_ref_without_kind`, `review_passage_not_allowed`, `review_anchor_not_in_passage`, `review_anchor_not_exact`, `duplicate_finding_handle`, `finding_without_evidence`, `duplicate_review_evidence`); keep each rejection path covered by a test.

## Backup and purge coverage (item 8; read before coding)

What the code does today (checked on `8e4bb5d`/`3bbc59a`):

- **Backup.** `create_backup` copies the whole database file with the SQLite backup API, so the four new tables are inside every backup and restore automatically; no table list needs the new names. `backup.py::_referenced_files` then lists the **files** to copy from fixed queries: `source_assets.storage_path` (papers, with `sha256` verified) and, for provider payloads, `search_runs.raw_payload_path`, `source_versions.provider_payload_path`, `kill_search_queries.raw_payload_path` and abstract `passages.payload_ref`. B1 therefore **adds no query to `backup.py`** unless a test shows a gap. Edit `backup.py` only if such a test fails, and say so in the report. `_referenced_files` in `backup.py` already covers these paths, so `backup.py` stays unchanged unless a coverage test fails. The backup round-trip test (below) shows the coverage: snapshot, review, finding and decision rows survive `create_backup`/`restore_backup` unchanged, and a snapshot-referenced source file is present in the backup and restored with its hash. - **Purge.** `Store.cited_source_versions` (`workflow/store.py`, near line 2358) lists the source versions that evidence still cites (answer links, table rows, cells, report links, lineage, claim matrix); `purge_sources` (near line 2372) refuses a source in that set (`RevisionConflict`), and `purge_research` (near line 279) keeps a source's passages, assets and file when another research still holds it (`corpus_memberships`, `candidates`, kill-search records).
