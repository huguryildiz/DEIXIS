# P8 — Review by another model and publication follow-up: design note

**Date:** 3 October 2026. **Status:** design only; nothing in this note is implemented. Reviewed by gpt-6.1-sol at medium effort in three rounds (D180). **Base:** `origin/main` at `c5db475` (P9 H8). The checkout the owner works in may carry later local commits that this note did not read. **Scope of the change:** this note and decision D180. No code, migration, contract or method file changes.

**In short.** P8 has two parts that share no feature code (they share the run machinery, `flow.py` dispatch, `api/app.py` and the migration sequence; section 9). Part one lets the user pick a finished answer, report or candidate, pick any available model, and get a separate list of findings about an immutable copy of that target. The review never writes into the answer or report; the user can accept, dismiss or defer each finding, and accepting one can only open the existing claim editor with the finding's suggested text prefilled. Part two lets the user switch on follow-up for a research: a check that re-reads the research's frozen search queries and the works citing its included sources, and lists records that are new to the library. It runs when the user presses "Check now", or, if the user opts in, on a schedule that fires only while DEIXIS is running. If the computer was off, DEIXIS says when it last checked and makes one bounded catch-up check on the next start; it does not claim to have watched in between.

Sources of requirement: `docs/product/implementation-plan.md` (P8 row at line 298; lines 226, 249, 280, 350; T14 and T16 at lines 375 and 377), the "optional review by another model" section of `docs/methods/research-methods.md`, `AGENTS.md` ("Optional review is a separate versioned assessment"), and the README paragraph on optional review. The plan is in Turkish; quotations below are paraphrased.

## 1. Scope and non-scope

**In scope**

1. **Owner-requested review.** Target: an answer, a report, or (last batch) a candidate version with its kill-search matrix. The user picks the model (connection, model, reasoning effort) at request time, a focus, and an optional short note. The result is a separate record with findings.
2. **Immutable snapshot.** The review reads a stored copy of the target as it was when the user pressed Start. The same copy is what the model receives.
3. **Findings feedback.** Per finding: accept, dismiss (with a reason), defer. Accepting never edits anything by itself; on a report claim it can open the existing editor prefilled.
4. **Stale marking.** A review whose target changed after the snapshot says so. The mark is computed when read; it is not a status.
5. **Follow-up (watch).** Per research, two tracked sources of new records (section 7), a manual check, an opt-in interval, a list of new records, an honest "not checked while closed" account.

**Non-scope (each is a stated limit, not a hidden gap)**

- No automatic review, no standing generator/reviewer pair, no discussion loop between the main model and the reviewer (`AGENTS.md`). The existing automatic claim check (section 2) stays as it is and is not renamed.
- No extra retrieval for a review. A review reads the passages and cells already stored. "Review with new search" is a later decision (question Q3).
- No review verdict such as "approved", "novel", "publishable", and no numeric score. A review is "an additional model assessment", never peer review or independent verification.
- No retraction or correction watch for included sources (question Q4); no email, no operating-system notification, no background service that runs while DEIXIS is closed (P10 owns process lifetime).
- No change to the report or answer text, the evidence table, source selection or counts by a review or a watch. New watch records do not enter the library until the user adds them.
- No second user, no sharing of review results.

## 3. How the existing automatic claim check relates

The automatic checks stay: `answer_review` after an answer (when a reviewer is configured), `report_review` after a report. They answer "does each claim match what it cites", they run without a user request, and they keep their tables and contracts. P8 reviews are different in four ways: the user starts them, the user picks the model per request, they read an immutable snapshot, and they can be repeated. The UI keeps two labels: "Claim check (automatic)" and "Review by another model (you asked)". P8 does not migrate, rewrite or delete the old rows, and a P8 review never replaces them.

## 4. Review: model boundary and contract

**New task type `owner_review`.** It follows the existing rule set; nothing about the boundary is relaxed.

- **StepInput.** The usual envelope (`step_input_id`, `scope_revision`, `skill_package_hash`) plus: `review_snapshot_id`, `target_kind`, the snapshot's claims (stable labels or claim keys, effective text, support type, cited passage handles), the passages those claims cite (text, locator, reading depth), report sections or candidate elements as the target needs, `focus`, and `owner_note`. The allowlist holds claim handles and passage handles from the snapshot only. The model reads the stored snapshot, not live rows; a test changes live rows after the snapshot is written and shows the stored StepInput is unchanged.
- **Focus.** A closed list. `source_support`: does each claim follow from what it cites. `assumptions_and_consistency`: unstated assumptions, internal contradictions, scope claims wider than the evidence. Findings under the second focus are labeled "reviewer inference". Prior-art comparison is not offered, because it needs retrieval (Q3).
- **Owner note.** Up to 500 characters of the user's own text. It cannot widen the target, cannot ask for tools or retrieval, and is passed as the user's instruction, while passages stay data (`AGENTS.md`: titles, abstracts and passages are never instructions). Code rejects an empty or oversized note; wording is not policed.
- **Model choice.** The user picks connection, model and reasoning effort from the existing pickers; the request is validated the way `check_role` validates a role. The record keeps the requested model and, per call, the model that answered; a different model is recorded as `model_mismatch` and its output is never used, with no fallback. The same model as the main work is allowed; the screen does not claim that a different model is more independent.
- **Closed input object.** `step-input.schema.json` forbids extra properties, so B1 adds a closed `review_input` object (`review_snapshot_id`, `target_kind`, `focus`, `owner_note` up to 500 characters, the target's claims, sections or candidate elements with typed handles, the handles of the passages in this call, and the call's group index and group count), with maximum lengths on every text and array, and the matching typed allowlist (claim handles, section handles, element handles, passage handles). `context_limits[]` carries a `target_ref` so each limit is tied to something. `whole` means "all content supplied in this call", not the whole report across calls; each finding records which group it came from, and the screen shows the group's coverage next to it.
- **Output contract `owner-review.schema.json` (`deixis.owner_review.v1`), closed, every property required, nullable where optional.**
  - `findings[]`: `finding_handle`; `target_ref` (`kind` is `claim`, `section`, `candidate_element` or `whole`, and `ref` is an allowlisted handle or null for `whole`); `kind` (`unsupported`, `partially_supported`, `overstated`, `missing_context`, `inconsistent`, `assumption_unstated`, `other`); `evidence[]` (up to 5 items of `{passage_handle, anchor}`); `rationale`; `possible_impact`; `suggested_fix` (text or null); `uncertainty`.
  - `supported_points[]`: `target_ref` and `evidence[]` with at least one item, so "checked and fine" is never stated without a located anchor. A reviewer that read something and has no anchor to show uses `context_limits`.
  - `context_limits[]`: closed codes (`passage_missing`, `only_abstract`, `not_enough_context`, `outside_provided_scope`) plus text, so insufficient context is stated instead of padded with faults.
  - The echo fields every contract carries: `schema_version` (`deixis.owner_review.v1`), `step_input_id`, `scope_revision`, `skill_package_hash`, checked against the stored StepInput exactly as for the other steps; a mismatch is an envelope mismatch and goes to the bounded repair path.
  - `notes`.
  - An empty `findings` list is valid. The prompt does not ask for faults.
- **Code checks (fail-closed, in `domain/contracts.py`).** `target_ref.ref` and every `passage_handle` come from the allowlist of that call and resolve to record IDs; `target_ref.kind` must match the kind of the handle (answer: `claim` or `whole`; report: `claim`, `section` or `whole`; candidate: `candidate_element` or `whole`); every `anchor`, in findings and in supported points, is an exact contiguous quote located in that passage's stored text with the same normalization as answers; a repeated `finding_handle` is rejected (several findings about one target are allowed); findings of kind `unsupported`, `partially_supported` or `overstated` need at least one located evidence item; a finding of another kind may have none and is shown as "reviewer inference, no located evidence". Unresolvable handles, missing anchors or an unlocatable anchor go through the existing bounded repair; if repair fails, the review is stored as `failed` with the draft kept and is not shown as a result. The code never applies `suggested_fix`.
- **Method package.** A new `references/review.md`, a `SKILL.md` row, and `owner_review` in `domain/skill.py::RUNTIME_FILES`. This changes `skill_package_hash` (every later StepInput echoes the new value; stored reviews keep their own hash, T13). Behavior cases for the new file are in batch B4.
- **Size, preview and calls.** Every target takes the same chunked path, which is new behavior (today's report review is one step): claims (and, for a report, sections) are grouped so that each call's fully serialized StepInput stays inside the same approximate 30,000-token budget, measured on the serialized text and not inferred from claim counts. A claim group that cannot fit alone is recorded as not reviewed with a reason, never dropped silently. The first release builds the groups from the snapshot only: `flow._step_input` reads source metadata and scope from live stores today, so B2 adds a review-specific builder that derives each call's StepInput from the stored snapshot, and its allowlist is the subset of handles that call actually carries. The preview shows three numbers: logical steps (one per group), the bound with schema repair (`MAX_SCHEMA_REPAIRS` is 1, so at most twice the steps), and the bound on total sends including rate-limit resends (`_call_adapter` resends up to `MAX_RATE_LIMIT_MODEL_RETRIES`, 2, when a limiter is passed, so at most three sends per attempt); a repair message is larger than the first input, so the group budget leaves headroom for it. The input size is an estimate: `report/selection.py::_estimated_tokens` assumes four serialized characters per token, so the 30,000-token budget is a character budget in practice and the screen calls the figure "estimated". The preview also shows the provider the content goes to, and says that cost is not estimated, because DEIXIS holds no price table and not every connection reports usage. The preview builds the snapshot in memory and returns a fingerprint over the snapshot's `content_sha256`, the connection, model, effort, focus and note; Start rebuilds the snapshot and refuses with 409 `target_changed` if the hash differs.

## 5. Review: snapshot, separation and the stale rule

**Data model (migration numbers are placeholders; the next free number at implementation time applies).**

- `owner_review_snapshots(id, research_id, target_kind, target_id, content_json, content_sha256, markers_json, created_at)`. `content_json` is one consistent read, copied, not referenced. It holds the research question and scope statement as of the target's scope revision, the language, and for each source version the metadata the model steps read (title, authors, year, DOI, version label, reading depth and access state). For an answer: claims with text, support type and cited passages (id, locator, reading depth, text). For a report: each section's claims with the effective text at that moment (human edits included), the effective citation set, the cited passages and cell quotes, section statuses and `report_version`. For a candidate version: claim statement, conditions, matrix cells and their evidence. `markers_json` holds the comparison tokens of section 5.3. Update and delete are blocked by triggers, as for `step_inputs` and `report_claim_revisions`; deletion needs the research purge authorization, like `research_candidates`. A conflicting INSERT, REPLACE or upsert on the same id or key is blocked too, with the `no_conflicting_insert` triggers `0060_candidates.sql` uses, for snapshots, findings and decisions alike; B1 tests each path and the purge exception.
- `owner_reviews(id, research_id, snapshot_id, run_id, focus, owner_note, requested_connection, requested_model, requested_effort, failure_reason, sections_not_reviewed_json, idempotency_key UNIQUE, created_at)`. The review has no state column of its own, because the API's cancel (`api/app.py`, which writes only the run row, also for a queued or paused run), a worker failure (`worker.py::_write_failure`) and recovery (`Worker.recover`) all change only the run. The state shown is derived at read time from the run: `queued`, `running`, `pause_requested`, `paused` and steps `outcome_unknown` as they are; `cancelled` and `failed` as they are; a run with status `completed` (the run enum is `queued`, `running`, `pause_requested`, `paused`, `completed`, `failed`, `cancelled`; `succeeded` is a step status, not a run status) is shown as `completed` when `sections_not_reviewed_json` is empty and at least one group was reviewed, as `partial` when some groups were not, and as `failed` (`nothing_reviewed`) when none was. `sections_not_reviewed_json` and `failure_reason` are facts written by the step transactions themselves, so nothing has to run at cancel time. A test walks every terminal and non-terminal run status, reached through the API cancel, a worker error and recovery, and requires the view to return a defined state and never a blank or a stale "running". The models that actually answered are read from the review's `step_inputs` and model sessions, not from one summary field, because a report review has several calls.
- `owner_review_findings(id, review_id, ordinal, finding_json, step_input_id)`. Immutable copy of the validated model output with evidence already resolved to passage and record IDs by the backend.
- `owner_review_decisions(id, finding_id, decision, reason, applied_ref, created_at)`. Append-only; `decision` is `accepted`, `dismissed` or `deferred`; `reason` is required for `dismissed` (a user choice keeps its recorded reason, `AGENTS.md`); `applied_ref` is a report claim revision id or candidate version id that exists and that the user saved from the prefilled editor, checked against the stored revision's text before the decision row is written; otherwise null. The current decision is the latest row; a finding with no row is "open".
- `runs.kind` gains `review`. The CHECK list is closed, so this is a table rebuild like `0059` and `0060`, including recreating triggers and keys; the migration test lists triggers and foreign keys before and after and shows every old row survives. `contracts/research/step-input.schema.json` has a closed `task_type` enum and no free properties, so `owner_review` and its input object are added there too (section 4).

**5.1 Run lifecycle.** A review is a `review` run, so it uses the existing machinery and its limits:

- `Store.create_run` allows one active run per research, where active means `queued`, `running` or `pause_requested` (`ACTIVE_RUN_STATUSES`); a `paused` run does not block a new run, but a paused run cannot be resumed while another run of the research is active (`resume_run`). A review start therefore returns 409 `run_active` while a run of that research is queued, running or pause-requested, and the sheet says "another run is active". This replaces a separate per-target rule. Making paused runs block new work would be a behavior change outside P8.
- Pause, resume and cancel use the run's own. After a crash, `Worker.recover` marks a `running` or `pause_requested` run `paused` (`backend_restarted`) and a running step `outcome_unknown`; a `queued` run stays queued; the review resumes through the existing resume path, steps that already succeeded return their stored output, and an `outcome_unknown` step is not retried by itself. - `flow.py` dispatches on `run["kind"]` and sends an unrecognized kind to `_table_columns`. B2 adds an explicit `review` branch and a test that an unknown kind fails loudly instead of running as a table run.

**5.2 Separation from the main data.** Writes are split in two lists. *Allowed control and provenance writes:* `runs` and `run_steps`, `step_inputs`, `model_sessions`, events, `researches.updated_at` (which `create_run` touches for every run kind), and the four `owner_review_*` tables. *Forbidden scientific-data writes:* answers, claims and claim links, reports, sections, report claims and their revisions and links, `report_snapshot`, evidence tables, rows, columns, cells, cell revisions and cell evidence links, sources, source versions, passages, corpus memberships, selections, candidates, candidate versions, kill-search and matrix tables. The review code gets read access to those through snapshot builders and no write handle: it receives a reader facade and the review store, not `Store` or `ReportStore`. Guards, each a test, none a runtime guarantee about code written later:

1. An import scan fails if the review package imports a write function of the answer, report, candidate or evidence stores or calls `conn.execute` outside its own store.
2. A SQLite authorizer installed in the test connection denies INSERT, UPDATE and DELETE on every table outside the allowed list during a full review, a failed one and a cancelled one.
3. Row hashes of the forbidden tables before and after the same three runs must match. This detects a write the authorizer list forgot; it is not stated as a guarantee for tables the list omits.
4. The only path from a finding to main text is the user opening the existing editor and saving through the existing route, which creates a human-edit revision with its optimistic version check. That route is not called by the review code. The decision row keeps the revision id.

An answer has no edit path today (a new answer is a new run), so for an answer target "accept" records the decision only and the screen says "no change was made". Feeding accepted findings into a new answer run as extra input would change StepInput for the main workflow; it is outside P8 (Q2).

**5.3 Stale rule.** `stale` is a read-time mark with reasons, not a status. It compares tokens stored in `markers_json` with live rows; it does not reuse the key set of `evidence_changes`, because that set depends on acknowledgements (`open` shrinks when the user acknowledges) and counts added sources and revised columns without keying them. A review is shown with a banner "The [answer / report / candidate] changed after this review" and the reasons. Findings stay readable.

| Target | Tokens saved at snapshot time, compared with live rows |
|---|---|
| answer | the latest answer id of the research; the scope revision; the set of included source versions and the latest selection update time |
| report | the report id and `report_version` and the latest valid report version; per claim, the current revision id and `version`; per cell, `current_revision_id`; the table's included row set; per column, `current_revision`; the scope revision |
| candidate | the candidate's current version; the scope revision; the id of the kill-search the snapshot read, with a content token over its matrix cells, assessments and outcome (the stored code appends assessments and updates the outcome under the same kill-search id, so the id alone is not enough); the latest owner status override id. A snapshot is taken only from a kill-search in a terminal state |

B1 starts by listing the markers that exist in code and fixes the final list; the table is the minimum. Rules that follow:

- A change in model, skill package or provider records does not make a review stale (T13). Both are displayed as recorded.
- A finding written against claim text that differs from the live text is labeled "written against an earlier text". Applying it opens the editor showing the snapshot text and the live text together; the editor's version check still applies.
- Passage extraction is not compared (as with `evidence_changes`) and the banner says "passages not checked".
- A scope revision that arrives while a review runs does not stop it. `_checkpoint` checks the revision only when the caller passes `scope_revision`; the review run does not pass it, because it reads only its snapshot. It finishes with the old revision label and is marked stale. Pause and cancel still stop it. B2 tests this (T18 variant).
- A trashed target or research hides its reviews with it and purges them with it.

## 6. Review: user experience

- **Entry.** "Review with another model" on the answer card, the report header and the candidate detail (when B8 lands). It opens a sheet, not a new page (`.impeccable.md` sheets): target (fixed), focus, model picker with the existing connection icons, optional note, and a disclosure block: what will be sent (claim count, passage count, characters), to which provider, estimated calls and input tokens, "cost not estimated". Start is disabled until the preview returned and the user has seen the block.
- **Review sheet.** Header says "Additional model review", the model's display name with its connection icon, time, focus, and the line "This is an assessment by a model. It is not peer review and not independent verification." Stale banner when applicable. A progress line while running, with the run timeline entry as for other runs. Report reviews list "sections not reviewed" with reasons.
- **Findings.** Grouped by target (claim or section). Each card: the finding kind, the claim text from the snapshot, evidence chips that open the stored passage exactly as citations do (`citations.tsx`, the highlight is only the located anchor), rationale, possible impact, suggested fix (plain text, never rendered as HTML), uncertainty. Source-stated evidence, reviewer inference and "no located evidence" are visually distinct. "Supported points" and "context limits" are collapsed sections, not hidden. Controls: Accept, Dismiss (reason field opens), Defer. On a report claim, an accepted finding offers "Open in editor with this text". On an answer, accept shows "recorded, no change made".
- **On the target.** A small "Reviewed: N reviews, M open findings" line on the report header and answer card; it never colors or badges a claim as verified or flawed.
- **Copy rules.** English keys through `t()` and Turkish map in `i18n.ts`; nothing says verified, approved or validated; "located in the passage" never reads as "supports the claim".

## 7. Follow-up (watch)

**What is followed.** Two kinds, both optional per research, both reading providers the research already used:

1. `protocol_queries`: the frozen search queries of the research's protocol (`protocol_records`, `search_runs`) re-run with a small page budget per query and provider.
2. `citing_works`: works citing the research's included sources, through the OpenAlex `cites:` read that citation chaining already uses, with a cap on sources per check; sources over the cap roll to the next check and the check says so.

Each check is a `watch_check` run, so it has recorded provider requests, failures kept visible (D18), pause and cancel, and `outcome_unknown` after a crash. It gets its own `runs.kind` (another table rebuild, separate from the review one) and its own explicit dispatch branch in `flow.py`. Because `create_run` allows one active run per research, a check cannot start while another run of that research is active: a manual "Check now" returns 409 `run_active`, and the scheduler skips the tick and tries again at the next one; a check never preempts or pauses another run.

**Baseline.** Turning a watch on makes a first check. For every provider and query it reads successfully, the records returned are written to the seen set (below) with origin `baseline` and nothing is announced. A provider or query that failed during the first check has no baseline yet: its first successful read later is its baseline and is not announced either, so a provider that comes back after an outage cannot flood the list with old records.

**Seen set and identity.** Announcements are decided against a research-level seen set, separate from the announced items:

- `watch_seen(id, research_id, identity_key, record_json, merged_into, first_seen_check_id, origin, created_at)` and `watch_seen_alias(research_id, alias, seen_id)` with `UNIQUE(research_id, alias)`. An alias is a namespaced stable identifier (`doi:…`, `openalex:W…`, `arxiv:…`, a provider's own id). `record_json` keeps the normalized provider record (title, authors, year, abstract if returned) so the identity code can compare a baseline record that never became an item. A record matches the seen set if any of its aliases is there; a DOI that appears later on a known provider id is added as an alias and does not count as new. If a new record's aliases hit two different seen rows, the rows are merged only when the existing identity rules allow automatic merging (`classify_pair` can return `merge=True` on similarity rules, so this is not proof of identity); the older row stays the key, the other row gets `merged_into`, its aliases move to the key, and, because `watch_items` is unique per seen row, two existing items are not collapsed: the older item stays, the other is marked `status = merged` with a pointer, and the decisions on both are kept and shown. A doubtful pair stays two rows and is shown as "may be another version".
- A record is checked, with the existing identity code (`record_identity.classify_pair`, which weighs version-family relations beyond equal identifiers), against both the seen set and the whole library. Matches the identity rules allow to merge automatically are "already in library" or "already seen". Matches it treats as suspected are not merged: the item is announced with "may be another version of [work]" (`AGENTS.md`: a suspicious match is not auto-merged, and versions are not independent corroboration).
- A record with no DOI and no stable provider id gets a key from the provider, normalized title and year and is marked "identity uncertain"; if the title or year changes it may be announced again, and the limit is stated on screen.
- Announcement uniqueness is per research, not per watch: a work found by both watch kinds is announced once. `watch_items` carries `kind` and a list of the watch kinds that found it.

**What is announced.** A record not in the seen set and not certainly in the library, and not a correction, retraction or withdrawal notice by the existing title rule. Notices are listed apart as "notices", not counted as new papers, and the screen does not say that retractions of included sources are watched (Q4).

**Storage (placeholder numbers).**

- `watches(id, research_id, kind, mode, interval_days, enabled, protocol_record_id, scope_revision, baseline_json, last_checked_at, last_success_at, next_due_at, created_at, disabled_at)`. `mode` is `manual` or `interval`; `interval_days` is 1, 7 or 30. Default: `manual`. `baseline_json` records, per provider and query or source, whether its baseline is done.
- `watch_checks(id, watch_id, run_id, trigger, period_start, requested_from, requested_to, observed_json, missed_periods, provider_status_json, counts_json, created_at)` with `UNIQUE(watch_id, period_start)`. `trigger`: `manual`, `scheduled`, `catch_up`. There is no stored outcome: as for reviews, the state is derived from the run (`queued`, `running`, `paused`, `cancelled`, `failed`, steps `outcome_unknown`), and a run with status `completed` is shown as `partial` when `observed_json` shows a cut or unknown coverage and as `succeeded` otherwise; if every provider failed it is shown as `failed` with the per-provider reasons. `pause_requested` is shown as it is. The run's `idempotency_key` is `watch:{watch_id}:{period_start}` (`runs` has `idempotency_key`; `operation_key` is a step field, and the check's steps have their own); the `UNIQUE(watch_id, period_start)` pair makes the period durable. `period_start` is the due time being served for a scheduled check, the latest missed due time for a catch-up (the number of missed due times goes to `missed_periods`), and `manual:` plus the queue time for a manual check, so a manual check never collides with a scheduled period and a double click is stopped by the request's idempotency header.
- `watch_items(id, research_id, check_id, seen_id, record_json, kind, found_by_json, status, created_at)` with `UNIQUE(research_id, seen_id)`. `kind`: `new_record`, `notice`. `status`: `new`, `dismissed`, `added`, `merged`. `record_json` is the normalized provider record with its provider ids and retrieval date. Items live apart from `sources`, search-run records and corpus tables, so found, unique, screened, included, inspected and cited counts are untouched (`AGENTS.md`). The watch has its own counts: checked, new, already in library, dismissed, added.

**Atomic queueing and completion.** Queueing is one transaction: the `runs` row with its `idempotency_key`, the `watch_checks` row and the watch's new `next_due_at`. Completion is one more transaction that also finishes the run: the new seen rows and aliases, the new items, the baseline markers in `baseline_json`, the position of the citing-source cap, the observation fields, the completion step's `succeeded` record, the run's move to `completed` (or `failed` when every provider failed), the events, and `last_checked_at` and `last_success_at`. Nothing that announces an item is committed apart from the run's terminal state, so a crash cannot leave published items on a paused check, and a rerun cannot redo a baseline that was already written. A crash between the two leaves a run that was `queued` (recovery does not touch it; it is picked up when the worker starts) or `running` (`Worker.recover` pauses it with `backend_restarted`), no items, and an already advanced `next_due_at`, so the old due time cannot produce a second catch-up. A paused scheduled or catch-up check stays visible and can be resumed or cancelled; the scheduler cancels it with the reason `superseded` in the same transaction that queues the next check of the same watch. A replay of the same period returns the stored check by its unique key and changes nothing. UI events are deduplicated by `event_id` as in plan section 6.3.

**Notification.** In app only. The research sidebar and the research header show the number of items with status `new`; there is no email and no operating-system notification (Q5). "Only on new events" is enforced by the research-level unique key plus the seen set: a record is announced at most once per research however many checks, catch-ups or restarts return it, within the limits of identity above (T16). A check that finds nothing writes its `watch_check` row and no notice.

**Adding an item.** The user can dismiss an item or add it. Adding must use an existing path that takes one provider record into a research or the library. Batch B5 verifies whether the screening code can take a record outside a discovery run. If it cannot, v1 ships items with "open at publisher" and "copy DOI" only, and adding becomes a separate small design item; this is risk R6.

**Coverage, stated apart from the request.** A check stores what was requested (`requested_from`, `requested_to`) and what was observed (`observed_json`: per query pages read, whether the result list was exhausted or cut by the cap, the sort used, and the oldest publication date reached). Re-running a query and diffing against the seen set shows what is new in the pages read; it does not show that a time window was covered. OpenAlex documents sorting by publication date and filtering by publication date (<https://help.openalex.org/api/sorting/>, <https://help.openalex.org/api/filtering/>); filters on record creation or update date need a paid plan, so the design uses neither. B5 re-reads both documents before building and quotes them with the date.

- Where the provider sorts by publication date descending, a query is "covered back to D" if the last page read ends at or before D or the list is exhausted; otherwise the check is `partial` and shows the date it reached.
- Where a provider has no date sort, coverage is "unknown" and the check is shown as `partial` with that reason.
- Records indexed late with an old publication date, and records ranked below the page cap, can be missed; the screen states this limit.

**Scheduler (opt-in, in process).**

- Only the process that holds the worker lock schedules. A once-a-minute tick compares wall-clock UTC `now` with `next_due_at` of enabled `interval` watches. If due and the research has no active run, it queues one `watch_check`; if a run is active it does nothing and tries at the next tick, and `next_due_at` is unchanged. One period gives one check (`UNIQUE(watch_id, period_start)`).
- `next_due_at` moves in the queueing transaction to `queue time + interval_days`, whatever the check's later result, partial or failed; a failed check shows its failure and "Check now" stays available, and the scheduler does not retry sooner. A manual check on an `interval` watch also resets `next_due_at` to now plus the interval.
- Wake from sleep: the tick compares clocks, so a sleeping laptop is not special.
- **Closed or asleep.** DEIXIS checks only while it is running. If the app was closed or asleep across one or more due periods, the first tick after start queues exactly one check with `trigger = catch_up`, stores `missed_periods` computed from timestamps, and the screen says "Not checked between A and B". The catch-up uses the same page budget as a normal check. If the budget cannot reach back to the start of the gap, the check is `partial` and says so. A published record the budgeted read does not return is not found; the screen never says "nothing new happened while you were away".
- A clock that jumps backwards delays the next check until `next_due_at`; a clock that jumps forward triggers one catch-up. Neither is hidden.
- A crash mid-check leaves a paused run and an `outcome_unknown` step (existing rule); neither is retried by itself, and the next due period queues a new check; repeats are absorbed by the seen set.
- There is no scheduler for `manual` watches; "Check now" is the only trigger and also works on `interval` watches.

**Provider and key behavior.** A connector that needs a key and has none is skipped and recorded as `not_configured`, as in discovery. Rate limits and pacing reuse `providers/pacing.py`. Enabling a watch shows which providers and which query terms will be sent again and how often. Caps (pages per query, sources per citing check) are frozen in B5 before any measurement and recorded in `counts_json`.

## 8. User experience: follow-up

- **Where.** A "Follow-up" tab in the research view (next to Sources and Evidence) and a count on the sidebar row of the research.
- **Panel.** Per watch: kind, mode, "Check now", last check time and outcome, next due time or "manual", and the standing line "DEIXIS checks only while it is running." After a gap: a visible, dismissible-by-acknowledgement banner "Not checked between A and B" with the catch-up outcome. Turning on `interval` opens a short dialog with the providers, the terms and the frequency.
- **Items.** A list of `new` items with title, year, provider, DOI, and Open, Add, Dismiss; "notices" and "already in library" counts below. Dismissed items stay reachable.
- **Honesty.** Counts say how many records the check read and how many pages were budgeted; a `partial` check shows the word. No word such as "up to date" appears anywhere.

## 10. What this design does not show

- No real model has read a snapshot yet. Until B4 runs, nothing is known about how many real faults a reviewer finds, how often it invents a fault, or how often it misses a planted one.
- A located anchor shows the quote is in the passage; it does not show the finding is right (`structurally_valid` is not semantic support).
- The stale mark covers the reasons listed, not every possible change to a passage or a source.
- A watch is a bounded re-read, not a literature alert service. A page budget can miss records; a long gap can exceed it.
- Nothing runs while DEIXIS is closed.
- The model-free tests show workflow behavior with a scripted model and mocked providers, not live provider access.

## 11. Risks

1. **R1, a reviewer that finds faults to look useful.** Mitigation: empty findings valid, `supported_points` and `context_limits` first-class, prompt never asks for faults, evidence required for support findings. Measured only in B4.
2. **R2, snapshot size.** A report snapshot with all cell quotes and passages can be large. Mitigation: the existing per-call budget decides what is reviewed, the rest is recorded as not reviewed; the snapshot stores what the review used plus the key sets for the stale rule. If a snapshot is larger than expected, B1 reports the size before B2 starts.
3. **R3, `runs.kind` rebuilds.** Two rebuilds of the largest control table; a missed trigger would weaken a guarantee silently. Mitigation: the migration test lists triggers before and after, as the `0059` and `0060` batches did.
4. **R4, the scope-revision checkpoint.** A review that does not pass `scope_revision` to `_checkpoint` can finish after the owner revised the question. Mitigation: it still honors pause and cancel; its result is marked stale and carries the old revision label; a test covers it.
5. **R5, provider capability.** Date sorting may not exist or may differ per provider. Mitigation: B5 reads the documents first; where a provider cannot sort by publication date, coverage is recorded as unknown and the check is `partial`. Diffing against the seen set shows what is new in the pages read, not that a window was covered.
6. **R6, no add path.** The screening code may not accept a record outside a discovery run. Mitigation: ship items without Add and write a small design item (section 7).
7. **R7, a cost surprise.** A report review is several calls on a paid connection. Mitigation: preview shows calls and tokens before Start; there is no money figure and the screen says so.
8. **R8, notice fatigue and false "new".** Identity can fail on records without a DOI or stable provider id. Mitigation: aliases, a title and year fallback marked "identity uncertain", and the research-level seen set; a changed title or year can still re-announce such a record, and the screen says so.
10. **R10, one active run per research.** Review starts and watch checks wait behind any other run of the same research, and the scheduler can skip many ticks while a long run goes on. Paused runs do not block. Mitigation: visible 409 messages and an unchanged `next_due_at`; changing the one-run rule is outside P8.
9. **R9, review debt elsewhere.** P9 batches from H0c on carry a GPT re-review debt because gpt-6.1-sol was out of quota (`p9-acceptance-record.md` section 7). That debt is separate from this note and is not cleared by it.

## 13. Acceptance for P8 as a whole

P8 closes only when, with the evidence that ran written in `p8-acceptance-record.md`:

1. a review leaves the tables named in section 5.2 unchanged (guards 2 and 3, including failed and cancelled reviews; this covers the listed tables, not every table that could ever exist);
2. a stale review is marked with its reasons after each kind of change in section 5.3;
3. no finding reaches main text except through the user's own save in the existing editor;
4. a missed period is shown, one catch-up is bounded, and a record is announced at most once per research within the identity limits of section 7 (T16);
5. candidates can be reviewed (Q10), or the owner has deferred that in writing and the record says candidates are not reviewable;
6. the B4 real-model behavior cases ran and are reported (Q11). The planted-error catch rate and the false-finding rate are either measured with denominators or recorded as a debt with a named owner, a target batch and the line "review quality not measured";
7. the known limits of section 10 are carried into the record, and build and lint show 0 errors and no new warning (the baseline is 17 lint warnings, so "clean" is not claimed).

A model-free pass shows workflow behavior; it is not a measurement of review quality.

## 14. Binding items from the fourth review round

The fourth gpt-6.1-sol review (medium effort, 3 October 2026) found 0 high and three medium issues and one low issue. They are not yet written into sections 1 to 13. The named batches must settle each one before they are accepted:

1. **B5: exact identifier match first.** When a shared alias reaches two `watch_seen` rows, an exact DOI or provider-id match decides before the similarity rule. Today `classify_pair` returns `merge=False` even for two published records with the same DOI, which would leave alias ownership unresolved and show a work already in the library as new. Test: a later DOI joins two published records.
2. **B5 and B6: a scope change.** A watch keeps the scope it was created with. When the research's scope revision or protocol changes, the watch is marked as following an old scope, and the user rebinds it explicitly; it never runs old protocol queries under the new scope label. Test: the scope changes while a check is running.
3. **B5: deterministic check outcome.** A check succeeds only if at least one provider read succeeded. Failed, skipped (`not_configured`) and deferred (quota) sources are recorded separately, and the rule for `partial` is written down for mixed results. A check that made no request is never `succeeded`.
4. **B1 and B2: separation-check scope.** If the SQLite authorizer covers the whole review lifecycle, it allows the worker's `worker_owner` heartbeat write narrowly. The separation tests run normal, failed and cancelled reviews through the real worker and API paths, not only around `flow.execute`.

## 15. Binding items from the comparison with the second P8 plan

A separate session wrote a second P8 plan (commit `081cad4`, never pushed, slices R1 to R3 and W1 to W3). gpt-6.1-sol (high effort, read only, on `29db85e`, 3 October 2026) compared it with this design and listed fifteen points where this design is missing a rule or states it more weakly. This design stays the only P8 line; the second plan is not adopted. The items below are binding for the named batches in the same way as section 14. They are not yet written into sections 1 to 13. Items that the second plan states differently on purpose (it requires a different model, and it marks a review stale when only the method hash changes) are not adopted: this design defines both differently and keeps the old model and method visible.

1. **B2 and B3: applying a finding checks its dependencies in one transaction.** Saving a finding through the editor checks, in the same transaction, the expected claim version and a fingerprint of the snapshot's target, selection, effective citations and evidence dependencies; a mismatch answers 409, and the human revision and its `applied_ref` link are written together. Today `ReportStore` checks only the claim `version`.
2. **B1: no REPLACE through the rowid.** Immutable snapshot, finding and decision tables are `WITHOUT ROWID`, or a BEFORE INSERT guard also refuses a rowid conflict. The guard is tested with `recursive_triggers=OFF` by REPLACE cases on the id, on the unique key and on the rowid.
3. **B5 and B7: work, version and notice identity are separate.** A DOI merges two records only when it confirms the same version; similarity is never automatic proof of identity; an alias or event type resolved later attaches to the existing notice and keeps its decision and read state. (This extends section 14 item 1.)
4. **B2, B5 and B6: the budget is checked before every send.** Before every first send, retry and repair the stored remaining budget and the deadline are checked again; the reservation of a send with an unknown outcome is kept; a restart or resume does not reset the model-send, total watch HTTP, record or time limits. Today the inner resend loop does not repeat the outer budget check.
5. **B5: a partial baseline completes against a fixed cut.** Each provider and query's baseline is closed by the query, window and upper cut frozen at the first check, and only when paging finished without error; after a page limit or an error it continues from the same cursor, and works published after the cut never join the silent baseline.
6. **B6: a paused or unknown check is not superseded.** While a watch has a check that is `paused` or `outcome_unknown`, the scheduler opens no new check, does not cancel the old one as `superseded`, and a send with an unknown outcome is repeated only after the user resumes. This replaces the rule in section 7 that cancels a paused check in the next period.
7. **B1, B2 and B3: a stale manifest for passages, files and extractions.** The review snapshot stores the original report evidence apart from the current state of its dependencies, and produces a target-bound stale reason when a used passage's content, an asset hash, an extraction id or the existence of a dependency changes. This replaces the exclusion of passage changes in section 5.3. `Store` already derives `pdf_replaced`, `pdf_removed` and `text_superseded`; `report/edit_check.py` already has a passage content digest.
8. **B1, B5 and B7: snapshot and watch dependencies are covered by backup and purge.** Sources, passages, files and payloads that a review snapshot or a watch provenance row refers to join the backup and restore manifest and the purge protection, and can be deleted only by an authorized purge of their research. Today `backup.py` collects files from a fixed table list and `purge_research` protects only from the existing citation tables.
9. **B5 and B6: an immutable watch config revision.** Each check stores an immutable config revision with the full query, providers, window, cursor and budget. A change of query or provider scope opens a new baseline; a change of cadence, budget or catch-up keeps the continuation; after the watch is turned off or the scope changes no new send is made.
10. **B5, B6 and B7: the success boundary is per provider and query.** A failed or deferred read does not move that boundary; unread ranges are stored and shown; "checked" covers only provider results that were actually read. A single `last_success_at` per watch is not enough.
11. **B5 and B7: publication, version and local times are separate.** A watch stores the publication time, the confirmed version time and the local `first_seen_at` apart, never derives a missing date, and does not label an old record indexed late as a new publication. Today arXiv keeps only the year and OpenAlex does not request the full publication date by default.
12. **B6 and B7: catch-up on opening is its own setting and is capped.** Automatic cadence and catch-up on opening are separate explicit settings; by default catch-up makes at most one combined check per research for at most three researches per opening, and the user's own work keeps priority in the queue.
13. **B2, B3 and B5: idempotency keys are bound to content.** New write commands bind the idempotency key to the research, the target, the expected revision and the request content; the same key with different content answers 409, and an exact replay writes and sends nothing new. `ReportStore`'s request hash check is the model.
14. **B2: the size limit covers the real message.** Every first call and repair is checked against the frozen serialized size limit after the full message set (prompt, schema, repair text) is built; content over the limit is recorded as not sent and is never cut silently.
15. **B5 and B7: a toast needs a backend claim.** If a watch shows a toast at all, it shows it only after the foreground tab's atomic, stored claim on the notice id succeeds; a reload or a second tab cannot claim it again, and the stored list survives a crash after the claim. This design does not have to add a toast.
