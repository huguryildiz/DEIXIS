# P9 H7 finding 2: evidence-preserving asset re-extraction design

**Date:** 3 October 2026. **Status:** proposed design only, not implemented; revised against the user-supplied independent Claude review (verdict "düzeltmeyle hazır", 0 high). Each finding was checked by local static inspection; these revisions have not received another independent review. **Base inspected:** detached `main` commit `a4deebfd511993335dda4992e6e39151f40e3644`. **Change scope:** this document only. No accepted decision, code, migration, model contract, method package or interface is changed.

The proposed recovery has two explicit outcomes: restoring the file's expected bytes, and publishing a new text extraction. A same-hash upload can do the first without doing the second. The user then requests one bounded local extraction attempt. Each attempt has its own identity even when its extractor profile is unchanged. Promotion preserves every earlier passage and evidence link, and records which extraction future work will use. A password diagnosis can replace an obsolete empty-text diagnosis without claiming that text was recovered.

Requirement sources: [D165 and D169](../decisions.md), particularly D165's Limits and D169's "Not fixed" list; the H7 item ledger; D45 and D47's retained-passage rule. Organization follows [the P8 design note](p8-review-watch-design.md). Repository authority comes from [AGENTS.md](../../AGENTS.md), [the documentation map](../README.md) and [layout](../layout.md). File-and-line references below describe this base, not a running service.

## 1. Scope and non-scope

1. Retry the embedded text layer of an in-use asset whose current extraction is `failed`, `partial` or `no_text`, including an asset using today's extractor profile. Retry is a user action, not a new automatic loop.
2. Distinguish a known-hash file repair from a successful, partial, rejected or interrupted text retry. Preserve the identity of the asset, bibliographic source version and work.
3. Retain old passages, cited anchors, locators, extraction diagnostics and frozen inputs. Future retrieval reads only the promoted extraction. Earlier artifacts retain their evidence and acquire explicit freshness or provenance notices.
4. Support an empty-text legacy password diagnosis through a narrow diagnostic exception. No password entry, decryption or password storage is proposed. An unlocked copy with different bytes uses the existing replacement workflow.
5. Include migration, backup, restore, purge, race guards and model-free acceptance requirements before the feature may close.

Outside scope: automatic text recovery during ordinary uploads, startup or answer generation; retrying a healthy same-profile extraction; increasing parsing limits; OCR, Marker or arXiv retrieval within the recovery operation; rewriting answers, reports or cells; changing inclusion decisions; interpreting a hash check as scientific verification. Existing extractor-upgrade, OCR and equation workflows keep their product policies, with the identity adaptations specified in section 4. After promotion, the existing D52 background reader may pick up an eligible asset; that later operation remains separate from recovery.

No runtime operation is authorized by this note. Its proposed tests belong in isolated temporary data directories. This design session used no network, provider or model call, did not start the application, and did not inspect the real library or port `8765`.

## 3. Recovery rules

### 3.1 File bytes and extracted text are separate state

Keep `source_assets.sha256` and `byte_size` as the **expected** content identity. Restoring those bytes must not rewrite the source title, DOI, origin, retrieval timestamp, source version or an earlier extraction's input provenance. Record new observations separately: actual digest and size, when observed, and whether they matched the expected identity.

A known hash is scoped to the chosen asset/source, not the first result from `Store.asset_by_sha` (`backend/deixis/workflow/store.py:1462`). Several rows can share one physical file. A physical repair must consider all rows referencing that stored path/hash; a text retry targets one in-use asset. Other affected rows show "File restored; stored text has not been retried" until separately retried. Upload reuse keeps its existing membership policy; repair itself does not include, exclude or restore a source.

On a same-hash upload, stage and verify the incoming PDF under the existing limits. If the stored file is whole, record reuse without rewriting it. If it is absent or corrupt, restore it and record the file outcome. Offer a text retry for eligible existing rows. Do not report text recovery merely because `store_upload` completed or backup now accepts the file. Different incoming bytes still require attachment or the existing explicit replacement path; they never repair the old asset in place.

Route every replacement of a non-whole hash path through one `restore_file(op)` that takes the shared file lock, writes a repair receipt and retains available damaged bytes before replacement (section 5.2). Both `store_upload` and `store_pdf_file` must delegate to it. This includes generic/source uploads, ordinary and SW matching uploads, waiting attachment, both Zotero paths, acquisition/candidate attachment, fetch inside a running run and Replace PDF. Initial storage at an unowned absent path remains attachment, but a pre-existing torn file still requires observation and retention. Membership checks or an existing-asset shortcut at one caller do not protect another caller sharing the same physical hash path.

Replace PDF must decide same-hash reuse versus file restoration before its `SameFile` refusal. A whole same-hash file keeps the refusal; a non-whole same-hash file returns the recorded file-only repair outcome without replacing the asset or promoting text. A run-time fetch (`backend/deixis/workflow/flow.py:2689`) that encounters a torn stored file held by an active run, including its own run, marks the fetch step `failed` with outcome code `fetch_file_repair_refused` before mutation. The run continues without that PDF; the fetch does not parse or attach the damaged file. It has no implicit lock or active-run bypass. New attachment and whole-file reuse keep their ordinary behavior.

### 3.2 One bounded attempt per request

Extend the existing extraction endpoint with an explicit `mode = retry_failed_or_partial`, `expected_current_extraction_id` and a required idempotency key for that mode. The ordinary older-profile upgrade remains available. A fresh click creates a fresh key; a transport retry uses the original key. Same key plus changed asset, baseline or mode returns 409 `request_conflict`, never a second extraction.

Keep the current no-body POST compatible with ordinary upgrade/healthy `unchanged` behavior. The explicit recovery body and result union need typed API/client definitions, including operation ID, file outcome, text outcome, candidate status, decision code and coverage. Use 404 for missing membership/file, 409 for active operation/run or changed baseline, 422 for an ineligible recovery request and the existing 507 storage refusal. A completed parse with a rejected candidate is an operation result, not an HTTP success claim that text was recovered. The CLI adds a single-asset recovery option with an explicit baseline; its default library-wide upgrade selection does not silently expand to all failed rows. Its recovery dry run opens no application and writes no migration, operation, passage or event; plan from an already compatible schema or refuse a required migration. The existing upgrade CLI dry run migrates on open (`backend/deixis/__main__.py:143`), so that stronger recovery promise needs its own test.

Eligibility is current status in `{failed, partial, no_text}` on an active member's in-use asset. A healthy current-profile asset returns `unchanged` with reason `already_current`; an explicit recovery request there is refused as `not_retryable`. Validate the file before any unchanged claim about an available file. `pending` requires resolution through its owning operation, not a parallel retry. No unrestricted `force` switch is proposed.

Use the normal embedded-text parser and chunker once, without invoking acquisition, OCR, equation reading, embedding generation, providers or models. Same-profile failures and rejections do not consume eligibility permanently. Further attempts require further user clicks. A scan that remains `no_text` gets the separate existing OCR option only when appropriate; a password diagnostic disables that option.

The call boundary is "the recovery operation makes no call" to OCR, Marker, source retrieval, providers or models. After it completes and releases its reservation, an eligible `succeeded`/`partial` asset can be selected by the existing D52 `next_asset` background reader. That later read is expected under the existing installation/route, active-run and retry guards, carries its own baseline and outcome, and is not counted as recovery work. Test both boundaries separately; an application-wide assertion of zero automatic equation calls would contradict current policy.

### 3.3 Promotion and diagnosis

Evaluate against the exact current extraction under the final write lock. Let `P_old` and `P_new` be sets of physical pages with nonempty stored chunks. Persist the decision code, old/new counts and missing-page set. Do not infer preservation from the number of passages: chunk boundaries can change.

| Baseline and candidate | Proposed decision |
|---|---|
| Healthy extraction upgraded to a different profile | Retain D45's rank, equal page count and nondecreasing text-page rules; also require `P_old` to be a subset of `P_new`. |
| `partial` baseline with usable passages; new `partial` or `succeeded` | Require verified expected bytes, equal page count, no lower status rank and `P_old` subset of `P_new`. More pages read or a changed passage manifest may be promoted. |
| `failed` or `no_text` baseline with **zero passages**; candidate `partial` or `succeeded` with text | Promote verified expected bytes as `recovered_text`. Do not use the failed/empty baseline's page count as a veto. The candidate supplies its own bounded physical-page locators. |
| Failed baseline with usable passages, or a partial baseline known to have read corrupt bytes | The page-count exception is allowed only with an extraction-time observation proving mismatched input, verified repaired bytes, all old text pages still represented and a nondecreasing rank. Record `recovered_from_corrupt_input`. A `legacy_unknown` input with passages retains the equal-count rule; a changed count is rejected as `legacy_page_count_untrusted` and is unrecoverable by this design (section 10). Same-byte Replace PDF is not an escape path. |
| Legacy `no_text` with zero passages; candidate is `failed` with exact parser reason `password-protected PDF` | Publish a new **diagnostic-only** current extraction as `password_diagnosed`, despite the rank drop and changed count. The old diagnosis remains superseded. No text is added and no text-repaired outcome is emitted. |
| Empty baseline; candidate `no_text` after a complete readable parse | May update an obsolete diagnosis as `no_text_diagnosed`; it remains an empty-text limit. Identical diagnosis/counts are `no_change`. |
| Candidate fails, loses an old text page, changes a trusted page count, or removes OCR/Marker/LaTeX content | Reject with the specific code. Earlier current text and diagnostics stay in use; the failed attempt's own diagnostic remains visible separately. |
| Same text, locators, text-source labels, profile, status and diagnostics | Store the attempt as `outcome='rejected'`, `decision_code='no_change'`; retain the current extraction and its passage IDs. The operation reports no change. An idempotent replay creates no additional attempt. |

The corrupt-input exception concerns page-count reliability, not semantic validity. It never relabels old text as extracted from the repaired bytes. A same-size mismatch also needs an actual digest observation; filename and size alone are insufficient.

The complete passage manifest includes ordered page/label, offsets, text hash, text source and relevant OCR/math provenance. An unchanged manifest does not prevent a genuine diagnostic update. A partial baseline containing OCR, Marker or LaTeX passages cannot be replaced by a plain text-layer retry that drops those contributions even if its page count and rank pass. Reject as `augmented_text_would_be_lost`; a later design may add an explicitly previewed merge. No merge is inferred here.

Keep the extraction outcome vocabulary `current`, `superseded`, `rejected` from `0027_asset_extractions.sql`; `no_change` is a decision code, not a fourth outcome. Adding an outcome would require a table rebuild and changes to B1's owner-review tests; neither is proposed.

## 4. Occurrence identity and migration

**Default: preserve the existing unique key and version-based passage selection.** Introduce a separate `extractor_profile` field for the tool/version/parameters and keep `extraction_version` as the immutable identity of a stored extraction occurrence. Existing values remain byte-for-byte unchanged. For new recovery occurrences use `<extractor_profile>+reextract-<operation_id>`. The suffix records identity, not a new algorithm or an artificial library-wide version bump. The existing `asset_extractions.id` is the canonical row reference; APIs carry that ID as the optimistic-concurrency baseline.

This additive option avoids rebuilding passages and retargeting every current-passage SQL predicate. Keep `UNIQUE(asset_id, extraction_version)`: P8 B1 decision 10 resolves `passage_extraction_id` through that pair and records the separate `current_extraction_id_at_snapshot`. Removing uniqueness or substituting `passages.extraction_id` would break B1's lookup unless its reader, manifest and tests were redesigned together. Q2's alternative is therefore outside this repair scope.

## 5. Execution, races and interruption

### 5.1 Text retry

1. Validate research/source/asset membership, request mode, baseline and idempotency. Acquire a cross-process advisory lock for the expected file hash, shared by every application-controlled writer/reader that can repair or extract that file. Under a short `BEGIN IMMEDIATE`, recompute all affected memberships, active runs and current extraction; reserve the operation. A replay returns its stored result; an in-flight replay returns the operation state without invoking a parser.
2. Resolve the file inside the configured papers directory, refusing traversal, symlinks escaping it and missing/nonregular files. Hash and size-check it in a worker thread. Missing or mismatched bytes produce a controlled file refusal; extraction is not attempted. Extract from a private, verified stable copy under temporary application storage while holding the file lock. Record that copy's actual digest/size as the extraction input. Keep temporary paths and private content out of error messages and Git.
3. Parse once under the current limits. Compute the full manifest, candidate status and promotion reason. No SQLite write transaction spans hashing, copying, parsing or any `await`.
4. Under the final transaction, re-read the asset, baseline, memberships, active runs and operation ownership; verify the stable input is still the expected file identity. Refuse a removed/replaced asset, revised request context, newer head or newly active run. Append candidate passages/extraction and the terminal operation record. On promotion, supersede the exact old head and update all mirrored fields. Write events to each affected research in that transaction. On refusal, keep the head and evidence unchanged and record the reason.
5. Release the lock and temporary input; return authoritative operation and view state. Failure to persist the result is a storage failure, never a successful repair response. Full-disk handling follows the existing coded refusal (`backend/deixis/api/app.py:515`; `backend/deixis/storage/db.py:142`).

The user recovery path has no `allow_run_id` bypass. Any `queued`, `running` or `pause_requested` run in any research holding the source blocks it. Paused runs may remain paused; their frozen passage IDs and freshness checks must stop late publication from using stale inputs. Existing internal OCR/equation ownership exceptions remain separately guarded.

A file restore checks active runs across **every asset sharing its physical file**, before replacement, including when `Flow._fetch_pdf` is the caller. Whole-file reuse can proceed because it changes no bytes. All paths that create runs or publish evidence must respect a reserved recovery operation until it ends, or the final transaction must refuse promotion; a start-time check alone is insufficient. R2a defines the shared Store/run reservation policy; R2b applies it to every writer through `restore_file(op)`.

### 5.2 File restore and available old bytes

`restore_file(op)` is the sole replacement path for a non-whole stored file, including matching, imports, acquisition, run-time fetch and Replace PDF. It acquires the cross-process file lock before inspecting/replacing the target, reserves a file-restore operation under the shared active-run policy, and rechecks integrity under that lock. For a corrupt file still present, copy its observed bytes to a private retained file named by their actual digest, verify and durably finalize it, and persist the observation **before** replacing the expected hash path. Retention failure, including ENOSPC, refuses the replacement. An absent file has no old bytes to preserve. An old extraction whose input was not observed remains `legacy_unknown`; observing a corrupt file immediately before repair does not prove that the old parser read that exact content.

The file replacement and SQLite commit cannot be one transaction. Use the reserved operation and this ordering: retain old bytes and commit their observation; finalize the verified upload with same-directory atomic replacement and file/directory durability; observe the result; complete the file-restore receipt. A crash after replacement but before receipt completion leaves a recoverable operation, not a success toast. Reconciliation verifies the path and records what is present without re-extracting. A leftover unreferenced staging file is not evidence and is not automatically promoted or purged by this design.

If D165 already replaced corrupt bytes before this feature existed, they cannot be reconstructed. Preserve the old text and say "Earlier extraction input was not recorded; the PDF shown is the restored file." A retained corrupt blob may not render as a PDF; retain its bytes and offer the stored text, with an explicit unavailable-preview reason. Never make the repaired PDF appear to be the verified original input of that old text.

### 5.3 Recovery after interruption

The current worker recovers runs/steps, not these proposed operations. Extend recovery under the process ownership lock: stale `running` text operations become `interrupted`; they do not re-run automatically. Reconcile file-restore operations from recorded observations and actual hashes. Do not mark another live process's operation interrupted: ownership must be established with the same cross-process lock. The CLI must acquire that lock too. A duplicate request after an interruption returns `interrupted`; a fresh user retry has a new key.

Crash tests bracket reservation, retained-byte commit, replacement, candidate insertion, supersession, mirror update and event commit. Each recoverable boundary must leave either the old extraction current or the complete new extraction current. No mixed passage set, half-updated mirrors or event claiming promotion without promotion may survive.

## 8. Backup, restore and purge

Current backup snapshots the entire SQLite database and copies every asset path, including removed assets, against its expected hash (`backend/deixis/storage/backup.py:52`, `70`). Restore verifies the manifest and refuses a pre-existing library or conflicting files (`148`), verifies the staged database hash (`197`) and places files atomically (`133`). Keep these refusals. Never weaken backup to tolerate a corrupt file under its expected hash name.

Extend `_referenced_files` to include retained observation files under `papers`, verified against their **observed** digest. Paths must remain flat and inside the configured directory; retained filenames can use an observation prefix to avoid collision with a real asset. A shared filename with contradictory recorded hashes is refused, not resolved by dictionary overwrite. Temporary verified extraction copies are not backed up. A backup taken during recovery must either have every file its snapshot references or refuse explicitly; it may not silently omit retained bytes or report an incomplete operation as completed. Serialize backup file collection with the recovery file lock or refuse while recovery is active, with a synthetic concurrency test.

Restored operations retain IDs, observations, statuses, occurrence identities and all old evidence. Opening the restored copy does not auto-retry. A formerly running operation is reconciled only under exclusive recovery ownership and remains visibly interrupted/uncertain where necessary. A newer-schema library keeps the existing older-code refusal (`backend/deixis/storage/db.py:120`).

Owner-review snapshots and their `sources`/`evidence_manifest` dependencies round-trip unchanged, including `passage_extraction_id`, `current_extraction_id_at_snapshot`, hashes and recorded evidence states. Backup/restore must keep their original passages, extraction rows, assets and applicable retained observations even when a later extraction is current. A snapshot-only dependency is sufficient protection; it must not depend on an answer/report citation also remaining present.

`Store.purge_research` deletes unshared source records, passages and extraction rows, then returns unreferenced files (`backend/deixis/workflow/store.py:279`, `389`, `403`). `purge_sources` refuses cited sources and retains those held elsewhere (`2372`, `2387`, `2418`); `cited_source_versions` covers answers, tables, reports, lineage and matrices (`2349`). Extend their explicit authorization and deletion order for recovery operations/observations. Deleting an initiating research must not erase a shared asset's recovery history. Retained bytes stay while any remaining asset/recovery observation or surviving historical artifact references them.

The purge reference list also includes B1's `snapshot_referenced_source_versions`: union it into `cited_source_versions` and treat another research's snapshot reference as shared in `purge_research`. Use B1's JSON-parsed, fail-closed dependency scan inside the same purge transaction, including snapshots of trashed researches. Unknown snapshot versions, malformed JSON or malformed dependency shapes stop deletion with the named error. Authorized purge of a snapshot's own research removes its owner-review rows first under B1's rules; surviving snapshots continue to protect their source versions, passages, extractions, assets and retained repair bytes. Do not weaken these hooks when adding recovery deletion order.

Also inspect passage IDs embedded in StepInputs, report snapshots and gap basis JSON when determining orphanhood; those are not all relational citation FKs. A surviving frozen record that mentions a passage prevents its unreviewed deletion. Do not silently drop a snapshot to make purge succeed. Clear self-references/recovery links in authorized dependency order before deleting the asset. File unlinking remains after database commit through `backend/deixis/api/app.py:899`, and returns paths it could not remove. Repair itself never invokes purge or deletes old evidence. Explicit authorized permanent deletion remains available; preservation here is not an indefinite-retention policy after that action.

## 10. What this design does not show

It does not show that the feature works: there is no implementation or executed recovery test here. It does not establish how many real rows need repair, the quality or completeness of recovered text, semantic support for an old or new claim, or unchanged numeric/equation meaning. Page coverage and status are operational checks only. Hashes establish byte identity relative to the stored expected digest, not the bibliographic correctness of that identity.

The design cannot recover corrupt input bytes already overwritten, prove which bytes an unobserved legacy parser read, unlock PDFs, or distinguish every cause of partial text. It does not change the existing scientific-validation boundary, clear P8 review debt, or close the other items in D169's not-fixed list. Actual recovery duration, retained storage growth, cross-platform locking/durability behavior and compatibility with unusual PDFs remain unmeasured.

A `legacy_unknown` partial/failed row with usable passages and a changed candidate page count is unrecoverable under this design's promotion rules. Same-byte Replace PDF is refused for whole bytes and only repairs non-whole bytes; it cannot bypass that rule. No owner-confirmed preview override is defined here. A future explicit override would need its own evidence-preservation decision; an unlocked or other different-byte copy can use the existing replacement workflow, with its distinct asset identity.

## 11. Risks and trade-offs

1. **Occurrence/profile confusion.** Keeping legacy `extraction_version` as occurrence identity minimizes passage-schema change but requires auditing every suffix-based tool lookup. Mitigation: one profile accessor, exact historical metadata lookup and the existing OCR/equation/withdrawal regressions. A one-line shortcut removal is insufficient.
2. **False preservation claims.** Equal counts and page-set inclusion can retain all page numbers while changing or losing words. Keep old evidence and mark supersession; do not claim semantic equivalence. Refuse automatic augmented-content loss and unknown-input page-count exceptions with passages.
3. **Filesystem/database gaps and shared files.** Atomic rename does not make file observations and SQL atomic, and several rows may share bytes. Retain observable bytes first, reserve ownership, guard all application writers and reconcile only under exclusive ownership. Out-of-band file edits can still force a controlled integrity refusal.
4. **Retention cost and permission failures.** Keeping old corrupt bytes plus rejected passages consumes disk and may make a full-disk repair impossible. Refuse rather than discard evidence; report storage cost when measured. Authorized purge may remove unreferenced history, never a repair shortcut.
5. **Broader evidence dependencies.** Reports and JSON snapshots can reference passages without direct citation FKs. A partial dependency scan risks a false fresh state or orphan deletion. R3 must exercise every declared artifact class; unresolved references stay explicitly unknown and block unsafe deletion.
