## Design (decided by Claude Opus 5.5 with gpt-6.1-sol medium, to be recorded in D207 by the orchestrator; not yet in `docs/decisions.md`)

1. Prefer moving checks earlier. Every blocking assembly rule must be one of: (A) a code-derived invariant (the model cannot cause it: code persists the value), kept at assembly as an assertion only; (B) model-correctable and now also enforced at section validation as a blocking `issues` entry, so the existing single repair fixes it where it occurs. No rule may stay model-correctable and assembly-only. If a rule needs input the section's StepInput does not carry, ADD the needed fields to that section's StepInput (and update contracts/fixtures/`tests/fakes.py` as CLAUDE.md says) or make the violation impossible deterministically (for example duplicate `claim_key` across concurrently generated sections: check whether the key syntax can bind the key prefix to the section id and enforce that at section time). Recording a Limit is not enough. StepInput additions: you may edit `contracts/research/step-input.schema.json` (its `report_target` is closed) and the serialization and handle code. Shapes to define compactly: for VII, the accepted VI gap records (id, kind, text, basis keys) including stated limitations and conflicts, plus the basis cells with their evidence passages; for counts and corpus absence, a compact frozen count context (applicable full-text cells per column, exactly what assembly needs) kept distinct from citation permissions (validation context must not widen what the model may cite). Bound it: define a size cap for the added fields, and an explicit failure policy when exceeded (fail the section with a recorded reason, never silently truncate). Never weaken a rule to a warning to get completion. Known gaps to close: VII receives no gap candidates (`sections.py:125`, `flow.py:5327`) so its gap allowlist is empty; count and corpus-absence checks use the full snapshot while sections receive selected evidence; duplicate detection against prior summaries misses concurrently generated sections (`sections.py:287`).
2. Code does no autonomous substantive rewriting: model-proposed replacements (phrase repair, `phrasing.py:165`), recorded removals and transactional restoration are allowed; code never invents math, citations, quotes or claims, never weakens a check into a warning, never alters stored evidence. Dropping an offending claim by code is allowed only with a recorded reason (D198 no-silent-loss); prefer sending it to the model.
3. After any later modification of a section (anchor patch, phrase repair, review reversion) the COMPLETE section validator runs again on the merged result, against the ORIGINAL section StepInput (not the phrase-repair input). Anchor patches already get full validation (`flow.py:5631`): keep it and add a regression test. Review reversion lives in `report/store.py:578` / `report/review.py`: it already runs assembly before and after the mutation and rolls back on failure, and review runs after finalization where a valid report cannot be demoted (`sections.py:310`, `store.py:663`); the policy is: an invalid reversion is REFUSED transactionally (rolled back, the rejected restoration recorded, the valid section and report state preserved; NOT `section_failed`, which is for generation, anchor patch and phrase repair only); keep that and make sure the complete section validator against the original input is part of the check. `store.py` and `review.py` are therefore allowed for this. If it fails there during generation, anchor patch or phrase repair, the section ends `section_failed` with the issues recorded (no second repair loop; bounded). Review reversion is the exception: it never uses `section_failed` (see below). The phrase-repair prompt must state that the hard rules (own-work wording, banned words, equation origin rules) still apply to its rewrite.
4. No new assembly-stage repair is built (not needed for B's failures); assembly checks stay as final assertions.
