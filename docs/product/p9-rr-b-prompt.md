### B. H8 high 2: an orphaned child has no memory limit

`backend/deixis/documents/pdf.py::_arm_lifetime` and `_watch_memory`: the parent's watcher (`_run_watched`) dies with the parent, the child's 100 s `SIGALRM` bounds time only, and the in-child Python thread cannot run while MuPDF holds the interpreter lock in a C call (D138, `scripts/p9/gil_diagnosis.py`). Required: a memory guard that works without the parent and without the child's GIL, for every child that calls `_watch_memory` (pdf, ocr, jats, arxiv source), and a process test (`tests/process/test_p9_children.py`) that proves it.

Facts from Sol's plan review (verify, do not trust): on macOS 27.0.1 `setrlimit(RLIMIT_AS)` (the same constant as `RLIMIT_RSS`) and `RLIMIT_DATA` are accepted when the limit is at least the current virtual size plus a little, and a later `mmap` over it fails with `ENOMEM`; lowering below current use raises `EINVAL`, which Python reports as "current limit exceeds maximum limit". But they limit **virtual size**, and an arm64 macOS Python process already maps hundreds of GiB of address space (about 466 GiB measured for a 18 MiB resident process), so they cannot express a 1 GiB resident limit. Confirm with the product interpreter (`/Users/huguryildiz/Documents/GitHub/DEIXIS/.venv/bin/python`; this worktree has no `.venv`) and write down the numbers. Unless you find a form that really bounds resident size, rlimits are not the guard.

Design to implement (change it only if measurement or code reading says so, and say why):
1. A small separate **guard process** per child (new stdlib-only module, e.g. `backend/deixis/documents/child_guard.py`, run as `python -m`; it must not import PyMuPDF; move `_resident_bytes`/`_libproc` there and re-export from `pdf.py` so existing names and tests keep working). It is started by `_watch_memory` (so pdf, ocr, jats and arxiv-source children all get it), with `stdin`, `stdout` and `stderr` set to `DEVNULL` (a guard that inherits the child's pipes can hold EOF open and delay a parent that waits for the stream) and in its own session.
2. Identity, not bare PIDs: the guard is given the child's pid, the child's start time (read from `proc_pidinfo` `PROC_PIDTBSDINFO` on macOS, `/proc/<pid>/stat` field 22 on Linux) and the original parent's pid and start time (**passed down by the parent**: the PDF path (`_run_watched`) and the arXiv path put `DEIXIS_PARENT_PID` and `DEIXIS_PARENT_START` in the child's environment from their own pid and start time; only for OCR and JATS, whose launchers you may leave unchanged, the child falls back to `os.getppid()` read as the first statement of its main, and the report says that a parent that died before that statement makes the child look parentless-from-birth and what the guard then does: treat a recorded parent that is already gone at guard start as an orphan). It acts on a pid only after it re-reads the start time and it matches. Accepted bound, write it into the module docstring and the report: macOS has no `pidfd`, so a window of microseconds remains between the final start-time check and `kill()`; the guard re-reads the start time immediately before the signal and signals once, and nothing else is done to close that window. The child is the guard's only target; a pid that now has another start time ends the guard without a signal.
3. Orphan rule: the guard enforces the limit only when the original parent is gone (its pid no longer exists with that start time, or the child's current parent pid differs from the recorded one). While the parent lives, the parent's own watcher is the authority where one exists: **only the PDF path (`_run_watched`) and the arXiv path (its own watcher task) have a parent watcher; OCR (`ocr.py` about line 65) and JATS (`jats.py` about line 76) call `subprocess.run` with only a timeout**. Do not claim the guard closes those two while the parent lives.
4. Lifecycle contract, written in the module docstring and tested: the child starts the guard and waits for a readiness byte over a pipe (with a short timeout) before it does any work; if the guard cannot start or does not report ready, the child exits with a distinct code (fail closed, a clear `ERROR_*` the parent already maps or one new code mapped the same way) and does not extract; the guard ends when the child is gone (it polls the child's identity), on normal exit, on child crash, on timeout of the parent and on SIGKILL of the child; it also has its own absolute deadline equal to the child's lifetime alarm plus a small margin, computed from the same value (`DEIXIS_CHILD_LIFETIME_SECONDS` or `CHILD_LIFETIME_SECONDS`), so a short job never leaves a guard that sleeps for 100 s; if the guard dies early the child is unprotected: the child's own watchdog thread cannot run while MuPDF holds the interpreter lock, so it cannot be relied on; require the best effort (the watchdog thread checks the guard's identity between C calls and the child exits with a distinct code when the guard is gone), test that path with a guard killed while the child is idle, and write down in the docstring and the report that a guard killed during a long C call leaves the child unguarded until the next check, as a known limit of the design. If the resident size cannot be read for `WATCH_LOST_TURNS` turns in a row and the parent is gone, the guard kills the child (fail closed).
